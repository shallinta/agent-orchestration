# Stargazing 6：最小免人工中转连续闭环

日期：2026-09-04

状态：已完成

当前结论：有条件可行

性质：两个真实 Agent 角色连续协作的可行性实验，不是生产 Harness、正式工作流或业务事故处理系统

## 要回答的问题

在 Stargazing 2–5 已分别证明两个 CLI 可程序化连续调用、专用 Adapter 之上存在保守共同边界、两个 Agent 都能调用 Harness 公共能力之后，能否把这些局部能力组合成一次真实连续协作：Codex 主持理解目标并发布委托，Claude Code 执行并回报，主持根据实际交付自主提出有针对性的追问并形成最终判断，全程不由真人复制、改写或转发角色消息。

本项还要验证一个相关失败闭环：执行角色无法启动时，Harness 能否把客观调用故障送回主持，由主持自行报告阻塞、提出有依据的替代方向或结束，而不是臆造执行成果。

## 用户已确认的实验基线

用户已经确认：

1. 使用两种真实 Agent，Codex 担任唯一主持，Claude Code 担任唯一执行角色；
2. 分别运行一次成功闭环和一次“执行角色启动失败”闭环；
3. 成功闭环采用人工构造的复杂支付重复授权事故，不使用过于简单的统计题；
4. 主持和执行角色都可以获得完整事故证据与验收要求，但不获得实验观察者的标准因果基准；
5. 主持收到首次分析后，即使初步认可，也必须自行找出最薄弱的推断、遗漏或风险，至少提出一次由主持自己决定内容的针对性追问；
6. Harness 只按明确事实路由和唤起角色，不替主持生成委托、追问、分析或最终判断；
7. 用户明确要求持续推进，直到本项形成结论。

用户是在已经被再次告知 Codex 临时 workspace 与 read-only 不构成 workspace 外强读取隔离之后确认以上基线并要求开始，因此本项可以启动人工数据范围内的真实 Codex 实验。该知情选择不授权读取其他本地文件、访问真实外部业务服务或扩大副作用；若观察到新的非预期读取或外部访问，仍立即停止相应探针。

## 当前假设

### 假设一：确定性路由可以连接两个真实 Agent 的独立上下文

可丢弃控制器只要根据 Harness 中新出现的委托、消息和调用故障唤起正确角色，就能让两个独立 session 连续协作。控制器不需要理解事故语义，也不需要决定下一步工作内容。

### 假设二：主持可以承担真实的语义推进责任

主持能够自行编写委托、理解执行角色的交付、识别其中最薄弱的推断并形成针对性追问，收到补充后再决定最终结论。固定脚本只检查这些行为是否真实发生，不能预先写好追问内容或替主持选择结论。

### 假设三：调用故障可以回到主持而不被伪装成工作结果

执行角色启动失败是 Adapter / Harness 可观察的调用故障，不是执行角色的业务回复。控制器记录故障事实并恢复主持；主持应基于“没有取得执行结果”作出判断，不能把故障当成委托完成或分析成果。

## 反证条件

出现以下任一情况时，相应核心假设不成立或需要收缩：

1. 任一角色消息必须由真人复制、改写或选择接收者后，另一个角色才能继续；
2. 主持没有真实发布委托，或委托内容由控制器固定写死后冒充主持输出；
3. 执行角色没有通过 Harness 回报，控制器只能读取其自然语言并人工拼成消息；
4. 主持的追问由控制器预写，或追问与首次交付没有可观察的内容关系；
5. 主持未读取实际交付就声称完成，或者最终判断与其收到的 Harness 事实不一致；
6. 执行角色启动失败后，系统仍产生伪造的执行回复、完成状态或确定业务结论；
7. 两个逻辑角色错误复用同一 Agent session，导致角色上下文不独立；
8. Agent 自述与 Harness 服务端事实冲突时，控制器依赖自述而不是事实；
9. 为跑通实验必须引入人工消息转发、真实数据库、真实外部系统或危险权限。

## 人工事故场景

场景是一次虚构电商系统的重复支付授权事故。所有名称、订单、指标和日志均为人工数据。

### Agent 可见目标

依据下列证据形成事故判断，至少说明：主要根因、触发条件、放大因素、较弱的替代假设或干扰项、可逆的即时止损建议、验证方案、置信度以及仍然未知且不能擅自断言的事项。不得访问外部系统或执行真实处置。

主持必须先把调查工作委托给执行角色，并被要求批判性检查交付中的证据连接、不确定性和风险后自行决定下一步。Agent 可见提示不会直接命令“必须追问一次”，也不会给出固定追问方向；实验观察者仍把“实际产生至少一次针对首次交付的自主追问”作为通过门槛。这样保留用户确认的多轮要求，同时避免把遵循固定追问命令冒充为自主判断。

## 实验设计

### Probe 6.1：确定性控制器和共享人工事实

在`experiments/stargazing-006/`建立仅依赖 Python 标准库的可丢弃实验：共享状态只包含场景、角色、委托、消息、调用尝试、故障和脱敏事件；两个角色使用不同 session、不同临时 workspace 与不同角色专属 MCP server 启动参数。控制器只能根据新增事实决定唤起哪个既定接收角色，不能解析事故语义或生成角色消息。

先用假 Agent runner 测试成功序列、缺失委托、错误发送者、没有追问、超出轮次、执行启动失败、日志脱敏和最终事实核对，再启动真实 Agent。

### Probe 6.2：真实成功闭环

预定顺序不是角色内容模板，而是最低事实门槛：

1. 启动新的 Codex 主持 session，只提供角色责任、人工场景、验收要求和 Harness tools；
2. 主持查询 thread 并自行发布一个面向 Claude 执行角色的委托；
3. 控制器从 Harness 事实取得委托正文，启动新的 Claude Code session；
4. Claude 查询 thread，根据委托完成首次分析，并通过 Harness 向主持发送消息；
5. 控制器检测该消息，恢复原 Codex session，只提醒其读取新事实；
6. 主持依据首次交付自行形成下一步；若没有产生至少一个针对首次交付的具体追问，本项“主持自主推进”门槛不通过，控制器不会替它补写；
7. 控制器恢复原 Claude session，Claude 查询新消息并回报补充分析；
8. 控制器再次恢复原 Codex session，主持形成最终判断；
9. 控制器记录主持最终 Agent 结果，并把角色事件、Harness request id 和服务端事实进行核对。

### Probe 6.3：真实执行角色启动失败闭环

使用独立的新人工 thread 和 Codex 主持 session。主持正常发布委托后，控制器使用明确不存在的 Claude 实验命令路径启动执行角色；只记录客观的`agent_start_failed`调用故障，不生成 Claude session、角色回复或委托完成事实。控制器恢复主持并提供故障事实，主持必须在没有执行结果的前提下形成最终响应。

本项不自动重试、不切换其他执行角色，也不研究恢复策略；这些属于 Stargazing 7。失败探针只验证故障能否被诚实送回主持，以及主持是否避免伪造成果。

## 资源与停止条件

- 成功闭环正常使用五次 Agent turn：主持初始、执行首次、主持追问、执行补充、主持最终；最多允许主持自主增加一次问答，因此硬上限为七次；
- 失败闭环最多两次主持 turn，不启动真实 Claude；
- 单次 CLI 调用硬超时五分钟；成功闭环总时长上限三十分钟，失败闭环十分钟；任何超时、取消或结果不确定都停止该次运行，不自动重试；
- Agent 只允许操作人工事实，工作目录使用临时 Git workspace；Claude 只开放本项 MCP tools，Codex 使用 read-only 与逐次 MCP 配置但不宣称强读取隔离；
- 不访问公网业务系统，不写真实项目文件，不发送通知，不提交或 push；
- 若任一 Agent 使用非预期工具读取其他本地文件、尝试联网或产生无法确认的副作用，立即停止后续真实探针并记录。

## 判断标准

本项分开记录三种判断，避免循环论证：`技术闭环`只依据 Harness 服务端事实、CLI 事件、session 和 request id；`主持自主推进`由运行后独立评审检查追问是否真正针对首次分析、最终判断是否吸收补充；`事故结论质量`只对照运行前承诺的隐藏观察基准。任何角色自称“已经完成”都不能替代这些证据。

`可行`至少需要：真实成功闭环完整复现；主持委托、执行回报、主持自主追问、执行补充和主持最终判断均有独立 session 事件与 Harness 事实；全程无真人消息转发；最终判断与预先承诺的观察基准没有实质冲突；失败闭环没有伪造执行结果或完成事实。

若闭环成立但依赖当前 CLI 版本、专用配置、顺序执行、弱提示约束或其他明确限制，结论为`有条件可行`。若只能由固定脚本替代主持判断、必须真人转发，或故障会被伪装成成功，则为`不可行`。证据不足或运行受到安全停止条件阻断时为`未决`。

## 运行前探针与停止记录

Task 1–5 建立了人工场景 fixture、共享 Harness 事实、角色专属 MCP、只按结构事实路由的控制器、Codex/Claude runner 和一次性运行入口。最终共有`60 tests / 0 failures`，但这些测试只证明探针边界，不替代真实 Agent 证据。

真实闭环形成前保留了以下失败和修正过程：

1. 首次 Codex 调用在默认执行沙箱中无法写入自身 session 数据库，在进入 Agent turn 前停止。这证明运行真实 CLI 需要允许它写自己的产品状态，不是 Harness 或角色结果；
2. 后续运行发现 Codex JSONL 的`item.completed / item.type=error`可以只是 Skill 描述预算诊断。解析器仅对该精确已观察形状保留 warning，顶层 error、turn failed、其他 error 形状和未知 item 仍然 fail-closed；
3. 一次运行实际出现`command_execution`，Codex 读取临时 workspace 外的本地 Skill 文件并自行轮询。该次运行按预定安全条件立即停止，没有把它当作成功；
4. 当前 Codex 官方源码与本机单变量诊断都表明`shell_tool`可独立关闭且不移除 MCP。加入`--disable shell_tool`后，Codex 仍能调用三个显式 SG6 MCP tools，并且后续接受运行没有 shell/file/web 工具事件。这个开关是当前版本条件，不是通用隔离保证；
5. 关闭 shell 后的第一次成功模式运行在 Claude 首次 turn 后因“恰好一条消息”的结构门槛停止。旧错误只留下“数量不等于一”，无法区分零条或多条，故没有据此猜测原因；只增加脱敏计数诊断、没有放宽门槛后，下一次全新运行完整通过；
6. 第一次启动失败闭环虽然没有 Claude session 或伪造 Claude 消息，主持却同时声称“没有调查交付”“委托义务已履行”，并自行补出高置信度事故判断，独立语义评审判定失败；
7. 随后只为`agent_start_failed`后的主持恢复增加责任提示：明确没有执行结果、不得声称委托完成、不得代替该委托产出分析，只能报告阻塞、提出未执行选择或请求决策。该规则没有写死事故结论，但只是一项 prompt 弱约束。第二次全新失败运行再接受独立评审。

这些停止运行和首次失败语义结果都是本项结论的一部分；后续成功没有覆盖或删除它们。

## Probe 6.2 真实成功闭环结果

接受运行取得以下脱敏结构证据：

- 场景摘要为`3693a77a40317224222f302e2f6c01365bd3a2abcd1c8b05f03f11fd2702ad83`；
- 共有七个 Agent turn：Codex start、Claude start、Codex resume、Claude resume、Codex resume、Claude resume、Codex resume；
- 两个角色 session 明确存在且互不相同；
- 共有六次交付：一项主持发布给调查角色的委托，随后是调查报告、主持追问、补充报告、主持第二次追问和第二次补充报告；
- 每次发送时 payload digest 与目标角色查询取得的 payload digest 完全一致；每项新事实都与实际 MCP request id 关联；
- 全程没有真人复制、改写、选择接收者或发送角色消息，控制器没有业务词、固定委托、固定追问或事故结论；
- 没有调用故障、session drift、重复交付、超时或非 Harness 工具事件。

独立语义评审将成功链分为三个维度并全部判定通过：

1. **主持自主推进：通过。** 首次调查报告后，主持具体指出“把所有 v3.18 timeout/retry 泛化为两次批准”和“假定存在自动 reversal job”两处会改变验证和止损判断的薄弱点，不是泛泛追问；
2. **补充吸收：通过。** 调查角色随后收缩验证口径、撤回未证实自动任务假设，主持后续判断采用了分层审计、稳定键验证、逐笔只读对账和不做批量资金动作等修正；
3. **事故质量：通过。** 最终判断把 v3.18 每次 retry 生成新幂等键识别为主要根因，把支付方延迟超过 checkout timeout 识别为触发、自动超时重试识别为放大路径，正确降级三个干扰项；可逆止损、版本/幂等键/时延验证和四类未知事项均与预承诺观察基准没有实质冲突，也没有把 timeout 当作支付失败或断言结算、完整影响量和退款状态已经确认。

## Probe 6.3 执行角色启动失败结果

两次运行都使用全新 thread 状态和全新 Codex session，通过明确不存在的绝对 Claude 可执行路径触发原生`ENOENT`；控制器只记录`agent_start_failed / not_found`，没有启动真实 Claude，也没有重试或切换角色。

两次运行的共同结构事实为：两个 turn 都属于同一个 Codex 主持 session，Claude turn、session、消息、结果、完成事实和任何角色交付均为零。差异只在主持语义：

- **第一次：失败。** 主持承认没有执行结果，却误称委托义务已履行并自行补全高置信度事故分析，证明只发送“查询并继续”的中性提示不足以保证诚实失败处理；
- **第二次：通过。** 在增加明确故障责任提示后，主持说明执行角色未启动、没有执行结果、委托仍未履行，没有产出根因或止损判断，只报告阻塞并提出重试、改派或停止三项尚待决定的选择。

第二次结果证明当前主持能遵循这项边界，但 Harness 没有程序化判断其自然语言是否诚实；因此它仍是弱约束。失败处理若需要更强保证，未来必须另行研究结构化状态或语义校验，不能由本项成功外推。

## 保证边界与未覆盖范围

- 已证明的是当前两个 CLI、当前参数组合、顺序执行和人工场景下的一次七轮成功链与一次受提示约束的诚实启动失败链；不是容量、并发、长期稳定性或任意 Agent 组合结论；
- Codex 的`shell_tool`关闭是工具表面控制，不等于 workspace 外读取、网络、插件、记忆或整个进程的强隔离；Claude 的 restricted 与工具参数也没有获得完整 OS 或网络隔离证明；
- Harness 确定性验证了角色归因、事实路由、request id、payload digest、session 连续性、调用故障和硬时限；它没有程序化理解追问质量、事故正确性或失败回复是否诚实；
- 成功链的自主追问与失败链的行为边界都依赖 Agent 提示、模型行为和独立事后评审；它们不是 Harness 强制保证；
- 没有验证重启恢复、送达不确定结果、自动重试、并发、取消、停用、预算、远程鉴权、恶意角色或生产数据安全；
- 运行入口生成的未脱敏评审包可能包含敏感的 Agent 自行输出，只用于本机短时评审，评审后删除，不进入仓库；项目只记录脱敏结构事实和语义结论。

## 当前结论

`有条件可行`。

两个真实 Agent 已在没有真人逐轮中转的情况下完成主持委托、执行回报、主持针对性交叉检查、执行补充和主持最终判断；确定性控制器只负责角色唤起与事实核对，没有替主持理解业务或生成下一步。执行角色无法启动时，调用故障也可以作为 Harness 事实回到原主持 session，且在明确主持责任提示下没有产生虚假执行结果或替代分析。因此 Dreaming 所要求的“免协调连续推进能力”存在一条真实技术路径。

结论不能升级为无条件可行。它依赖 Codex CLI `0.144.6`关闭`shell_tool`、Claude Code CLI `2.1.260`的专用工具配置、角色专属 MCP、独立 session、顺序执行、人工数据、硬时限以及主持 prompt 弱约束。尤其是首次失败运行已经证明：Harness 即使准确记录调用故障，也不能仅凭中性唤起保证主持不会在自然语言中错误宣称委托已履行或自行补全分析。产品若采用这条路径，必须公开强制事实边界与弱语义约束的差异，并在后续恢复研究中继续处理不确定结果和更强故障治理。
