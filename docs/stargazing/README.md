# Stargazing：核心技术可行性探索

`Stargazing` 是 Dreaming 之后的核心技术可行性探索阶段，本目录用于记录该阶段的问题、证据、试验、结论与进展。“观星”意味着在进入具体产品设计与实现之前，先通过真实证据辨认当前技术边界和可能的方向。

它回答“现有技术边界能否支撑已经确认的产品核心，以及主要限制是什么”，不直接回答完整产品怎样实现，也不自动形成 `v0.0.1` 范围或正式架构决定。`Stargazing` 是阶段名称，不改变其技术可行性探索的性质。

## 为什么单独建立这个目录

Dreaming 0–54 已经明确产品问题、核心用户旅程、主要功能版图和责任边界，但有些关键判断只能由真实技术证据回答，例如：目标 Agent 是否能够稳定地被程序化调用并持续交互，Agent 能否可靠调用 Harness 公共能力，Harness 重启后能否恢复协作事实，以及权限、预算和取消能力究竟能提供多强保证。

这些结论容易随 Agent 版本、运行环境和调用入口变化，也可能包含失败实验和被推翻的假设。将它们与 Dreaming 历史记录、正式产品决定和未来实现文档分开，可以保留证据和变化过程，而不把一次实验结果过早固化成长期架构。

## 调研原则

1. **先研究阻断性问题。** 优先回答“不成立就无法形成核心闭环”的问题，再研究性能优化和外围能力。
2. **证据优先。** 结论尽量同时依据当前官方资料、实际安装版本和可复现的最小实验；第三方材料只作补充。
3. **记录时间与环境。** CLI、协议和模型能力可能变化，任何能力结论都要记录验证日期、版本、平台和必要配置前提。
4. **区分观察、推断和建议。** 命令输出或实验现象是观察；对原因与范围的解释是推断；技术方向是建议，三者不能混写成同等事实。
5. **允许可丢弃实验。** 为回答问题可以编写最小探针或实验程序，但实验代码不是产品实现，也不能仅因跑通就成为正式架构。
6. **正反结果都保留。** 失败、条件成立、能力缺失和结论变化同样是调研成果，不能只记录成功路径。
7. **保证强度必须真实。** 对权限、审批、预算、取消和沙箱等能力，必须说明是 Harness 强制、外部机制强制、提示词弱约束还是尚未覆盖。
8. **保护敏感信息。** 凭证、token、环境变量值、私有内容和不可公开的完整输出不得写入调研记录或提交仓库。

## 记录结构

- `plan.md`：探索目标、事项顺序、证据要求和阶段完成条件。
- `logbook.md`：像观星日志一样按时间追加总体进展、重要变化、当前阻塞和下一步。
- `NNN-<topic>.md`：单项探索记录，文档标题使用 `Stargazing N`。编号表示首次开始记录的顺序，不表示永久优先级。
- 如需保存可提交的脱敏原始证据，后续按调研项建立 `evidence/<NNN-topic>/`；不为了空目录提前创建结构。
- 如需实验代码，另行决定项目内位置并在对应调研记录中链接；默认不把产品源代码与调研文档混放。

## 单项记录最低内容

每份单项调研至少说明：

1. 要回答的技术问题，以及它为什么影响 Harness 核心；
2. 当前假设和能够推翻假设的结果；
3. 验证环境、版本、资料来源和实验步骤；
4. 可以复核的观察证据；
5. 结论及其适用条件、已知限制和时效性；
6. 对后续调研、产品边界或设计候选的影响；
7. 尚未回答的问题。

单项结论统一使用以下一种表达：

- `可行`：当前证据足以支持核心需要；
- `有条件可行`：只有在明确前提或限制下可行；
- `不可行`：当前边界不能支持核心需要，且已有足够反证；
- `未决`：证据不足或相互矛盾，暂时不能下结论。
