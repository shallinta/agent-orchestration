# Stargazing 7：持久化、进程重启与不确定结果

日期：2026-09-04

状态：已完成

当前结论：有条件可行

性质：Harness 恢复事实与诚实表达不确定性的技术可行性实验，不是生产存储、容灾、高可用或通用幂等方案

## 要回答的问题

当 Harness 已经发起一次 Agent 执行、但尚未持久化可靠终态时自身退出，新 Harness 进程能否恢复已经确认的 thread 事实，并把无法确认的执行诚实地保持为`结果未知`，既不伪造成功或失败，也不自动重试。

这个问题比“重启后 Agent 还能不能继续跑”更基础。如果 Harness 无法先恢复事实和不确定性边界，即使底层进程或 session 仍然存在，也可能造成重复成本、重复副作用、虚假完成或错误失败。

## 用户已确认的首轮边界

用户确认先验证一个最小、可反驳的崩溃窗口：

1. Harness 已持久化执行尝试；
2. 假 Adapter 已明确接受该次执行，Harness 也已持久化接受事实；
3. 尚未取得或持久化任何可靠终态；
4. 此时强制终止 Harness 进程；
5. 新 Harness 进程读取同一份持久化事实并执行恢复。

首轮不混入真实 Agent、真实外部副作用、子进程接管、MCP 请求中断、并发、自动补偿或生产级数据库。用户随后明确授权持续推进，直到 Stargazing 7 形成结论；这不改变每个新增探针仍须先有明确问题、反证、安全边界和停止条件。

## 与相邻语义的边界

- `结果未知`：已经确认 Adapter 接受执行，但没有可靠终态证据；不能由此声称成功、失败或仍在执行。
- `送达未知`：执行请求可能已经交给 Adapter，但 Harness 没有持久化可靠接受或拒绝事实；它比首轮窗口更早，不能与结果未知合并。
- `进程存活未知`：Harness 重启后不知道旧 Agent 或 Adapter 进程是否仍存在；它是运行载体事实，不等于结果或外部副作用状态。
- `外部副作用未知`：文件、网络、费用或第三方写入可能已经发生；Agent 进程存活或死亡都不能单独证明副作用状态。

这四类未知不能互相推导。Probe 7.1 只主动制造第一类。

## 已有证据

1. Stargazing 2 已观察到 Codex 取消后进程退出码为`0`但缺少 Agent turn 终态，因此退出码不能替代可靠终态；
2. Stargazing 3 已观察到 Claude Code 被外部停止后没有 final result，进程退出本身同样不能证明工作失败或成功；
3. Stargazing 4 已把`结果未知`确认为专用 Adapter 之上的一等共同语义，并明确未知时默认不能自动重试；
4. Stargazing 5 已证明 Harness request id 和服务端事实可以与 Agent 工具结果关联，但没有证明服务中断后的不确定写入和安全重试；
5. Stargazing 6 已证明顺序协作闭环和调用故障路由有条件可行，但其临时 JSON 状态明确不具备 crash durability 或跨进程恢复结论。

这些证据说明本项问题真实存在，但不能替代新的跨进程恢复实验。

## 当前假设

### 假设一：最小已确认事实可以跨 Harness 进程恢复

只要角色、委托、执行尝试、Adapter 接受事实和事件在崩溃前分别完成事务提交，新进程就可以恢复它们之间的关联，而不依赖旧进程内存。

### 假设二：缺少可靠终态时只能产生结果未知

恢复逻辑看到“Adapter 已接受”且不存在可靠 Agent 终态时，应把本次执行恢复为`结果未知`。进程退出、超时、没有输出或旧进程消失均不能把它升级成成功或失败。

### 假设三：恢复本身不能重新派发工作

恢复逻辑只整理已有事实，不调用 Adapter、不创建新执行尝试，也不把旧尝试改回可执行状态。如果用户以后决定重试，必须另行创建新的执行尝试，并保留与旧未知尝试的关系。

### 假设四：恢复结论必须幂等且可审计

对相同持久化状态重复运行恢复，只能得到同一`结果未知`结论；对应恢复事件最多一条，不能因进程多次启动重复产生事实。

## 反证条件

出现以下任一情况时，首轮假设不成立：

1. 新进程丢失已经提交的角色、委托、执行尝试或 Adapter 接受事实；
2. 缺少终态时被恢复为成功、失败、完成、取消或可靠运行中；
3. 恢复流程再次调用 Adapter，或隐式创建另一执行尝试；
4. 恢复产生 Agent 结果、角色消息、委托完成、验收或目标完成事实；
5. 旧执行尝试能够回到可执行状态或被重新启动；
6. 重复恢复生成多个未知事件、不同结论或不一致计数；
7. 只有读取 Agent 自然语言才能判断恢复状态；
8. 为跑通首轮必须引入真实 Agent、外部服务、危险权限或人工修复持久化数据。

## 候选实验路径

### 路径一：假 Adapter + 真实跨进程恢复（采用）

用确定性假 Adapter 精确确认一次接受，在接受事实提交后强制退出 Harness，再由新进程恢复。它能直接检验事实持久化、未知分类、禁止重派和幂等，且没有真实 Agent 成本或副作用。

### 路径二：直接杀死真实 CLI 调用（暂缓）

真实性更高，但同时引入子进程继承、管道断开、session 存储、输出回收和取消机制，难以定位失败原因，并与 Stargazing 8 的控制边界重叠。

### 路径三：只验证数据库重开（否决）

它只能证明数据仍在，不能证明 Harness 会形成正确未知结论并阻止再次派发，无法满足本项核心门槛。

## Probe 7.1：已接受、无终态时的跨进程恢复

### 最小事实链

1. 第一个 Harness 进程在 SQLite 中创建人工 thread 的两个角色、一项委托和一次执行尝试，并分别提交；
2. Harness 以执行尝试 id 调用假 Adapter；
3. 假 Adapter 在独立账本中记录本次调用及`accepted`结果并返回接受回执；账本记录每次调用，重复调用会留下`duplicate`记录；
4. Harness 持久化 Adapter 接受事实与对应事件；
5. 进程使用仅供实验识别的固定退出码立即退出，不运行正常清理，也不产生终态；
6. 第二个 Harness 进程打开同一 SQLite，执行确定性恢复；
7. 恢复逻辑将该尝试标记为`result_unknown`，写入至多一条恢复事件，不调用假 Adapter；
8. 第三个进程再次运行相同恢复，用于证明结果和事件幂等。

### 实验存储边界

使用 Python 标准库`sqlite3`和显式事务提交，只为了验证进程退出后已经提交的事实能由新进程读取。实验不选择正式数据库，不宣称已证明：

- 操作系统崩溃或突然断电后的磁盘持久性；
- 磁盘损坏、文件系统语义或 SQLite 配置组合；
- 多机复制、主从切换、备份恢复或高可用；
- 并发 writer、锁竞争、跨进程竞态或生产吞吐；
- schema 演进、数据保留、加密或访问控制。

### 通过条件

- 新进程恢复两个角色、一项委托、同一执行尝试及 Adapter 已接受事实；
- 执行尝试最终恢复标记只能是`result_unknown`，确定终态为空；
- 假 Adapter 账本始终只有一次调用：一次`accepted`、零次`duplicate`；因此错误重派即使被 Adapter 拒绝也不能隐藏；
- 没有 Agent 结果、角色消息、委托完成、验收或新执行尝试；
- 恢复事件与原执行尝试关联且最多一条；
- 重复恢复返回相同结论，不改变事实计数；
- `result_unknown`分类只来自 Harness 数据库中的`accepted`且无可靠 terminal 事实，不读取假 Adapter 账本；账本只供实验观察者验证初次调用与没有 redispatch，所有判断均不依赖自然语言。

## 后续探针决策门槛

Probe 7.1 通过后，再按阻断性决定是否追加：

1. **Probe 7.2：送达未知。** 在假 Adapter 已记录接受、Harness 尚未持久化接受回执时退出；恢复必须表达`delivery_unknown`并禁止自动重派。它与 Probe 7.1 使用不同状态和断言；
2. **Probe 7.3：可查询终态的对照。** 如果 Adapter 能按执行尝试 id 提供可靠、不可歧义的终态查询，恢复可通过查询补录结果；若不能，则保持未知。该能力不能假定所有 Agent 都有；
3. **真实 CLI 跨 Harness 进程继续 session。** 仅当已有 Codex/Claude resume 证据不足以回答集成问题时进行；正常两 turn 之间重启与执行中杀进程必须分开；
4. **真实在途 Agent 进程。** 只有前述确定性语义成立后才考虑，并严格区分进程存活、结果和外部副作用。它可能与 Stargazing 8 合并研究。

是否追加由当前证据缺口决定，不把“所有探针都跑过”当作完成标准。

## 安全边界与停止条件

- 首轮不启动 Codex、Claude Code 或其他真实 Agent；
- 只在系统临时目录建立 SQLite、假 Adapter 账本和人工数据；
- 不访问网络、真实项目文件、凭证、用户数据库或外部服务；
- 不执行真实消息、委托、通知、文件业务变更或付费调用；
- 子进程有明确超时，退出码、stdout、stderr 和数据库事实分别记录；
- 实验生成物由临时目录拥有，测试结束清理，不提交运行实例；
- 任一测试出现无法解释的额外进程、重复派发、非临时路径写入或结果伪造时停止后续探针。

## 判断标准

`可行`至少要求已提交事实能跨进程恢复、未知状态分类正确、恢复不自动重派且重复执行幂等；如果依赖特定存储事务、假 Adapter、单 writer 或其他明确限制，则为`有条件可行`。

若恢复只能依赖旧进程内存、会把未知伪装成确定终态、会自动重派或无法保留已提交事实，则为`不可行`。证据不足、实验边界不能代表 Harness 恢复问题或安全条件阻止验证时为`未决`。

本项允许局部问题继续未决；最终结论必须明确说明哪些窗口已经验证、哪些只由既有证据支持、哪些仍留给 Stargazing 8 或未来实现阶段。

- 日期：2026-09-04；
- 平台：macOS `26.5.2`，`arm64`；
- Python：`3.14.4`；

这些版本只标记本次证据坐标。实验没有检查登录、模型、插件、MCP、网络、真实 workspace 或用户数据库。

## 实验观察

### Probe 7.1 的实际结果

端到端入口在同一个临时目录内依次启动三个独立 Python 进程：计划崩溃进程、首次恢复进程和二次恢复进程。实际脱敏结构摘要为：

```json
{"adapter_counts":{"accepted":1,"duplicate":0,"total":1},"fact_counts":{"acceptances":1,"agent_results":0,"attempts":1,"delegation_completions":0,"delegations":1,"events":6,"messages":0,"roles":2},"idempotent":true,"planned_crash_observed":true,"redispatch_count":0,"schema_version":"stargazing-007-probe-v1","states":{"dispatch":"accepted","recovery":"result_unknown","terminal":null},"unknown_event_count":1}
```

这组结果表明：

1. 第一个进程只有在 Adapter 的一次接受已写入独立账本、Harness 接受事实已提交且能由新数据库连接重开确认后，才以固定退出码`73`退出；
2. 第二个进程从 Harness SQLite 恢复两个角色、一项委托、同一执行尝试和接受事实，并在没有可靠终态时写入`result_unknown`；
3. 第三个进程取得与第二个进程相同的恢复摘要和数据库快照，未知恢复事件仍然只有一条；
4. Adapter 账本只有一次`accepted`、没有`duplicate`，因此恢复没有重新派发；
5. 恢复没有产生 Agent 结果、角色消息、委托完成或新的执行尝试。

恢复程序只有数据库路径输入，不读取假 Adapter 账本、旧进程状态、stdout、stderr、时间或自然语言。Adapter 账本只由实验观察者用来核对初次接受和调用总数。

### 正反路径与实验修正

自动测试共`21 tests / 0 failures`，覆盖已提交事实跨实例读取、固定事实关系、外键、重复写入、假 Adapter 首次接受与重复拒绝、计划崩溃位置、协议异常、恢复与重复恢复，以及三进程端到端摘要。

负例确认：

- Adapter 超时、非零退出、畸形 JSON、错误 attempt id、重复接受或无法从新连接确认提交时，不能产生计划崩溃证据；
- 尚处于`prepared`的执行不会被标记成结果未知；
- 已有可靠终态不会被恢复覆盖；
- 畸形数据库，或字段与事实事件不一致的数据库，会在修改前 fail closed；
- 非法写入和失败恢复不会改变原有事实。

实现审阅曾发现，初版实验存储允许把`None`写成“可靠终态”事件，也允许在 Adapter 尚未接受时写入终态，随后可能让同一执行同时拥有终态事件和`result_unknown`。先用失败测试复现后，实验同时增加方法校验和 SQLite 约束：终态只允许`succeeded`/`failed`中的固定值、必须发生在`accepted`之后，并与恢复状态互斥。修正后的独立复审通过。这个过程也说明，恢复结论不能只依赖事件名，持久化字段与事件之间必须维持可检查的一致性。

## 分析与判断

Probe 7.1 已满足本项核心门槛：在接受事实已经可靠提交的前提下，新 Harness 进程可以恢复已确认的 thread 关系，对缺失终态的执行诚实表达`result_unknown`，不自动重派，并保持重复恢复幂等。

本项不追加 Probe 7.2 或 Probe 7.3。原因不是这些问题已经解决，而是它们不是当前核心门槛的必要证据：

- 更早的“请求可能送达、接受事实尚未提交”窗口仍应表达为`delivery_unknown`，但尚未通过跨进程实验验证；
- 如果具体 Adapter 将来提供按执行尝试 id 查询可靠终态的能力，恢复可能补录终态，但本项没有证明任何真实 Agent 具备这种能力；
- Codex 与 Claude Code 的 session 恢复已有各自单项证据，但本项没有把真实 session 与 Harness 重启组成一条集成链路。

把这些缺口如实保留，比为了覆盖原始清单把送达、真实 Agent、进程接管和外部副作用混入同一探针更能保持结论可解释。后续只有在产品设计需要相应保证时，才应为每个窗口单独建立假设和反证。

## 适用条件与未证明范围

结论仅在以下条件下成立：

- Harness 先持久化执行尝试，再调用 Adapter；
- Adapter 接受事实在 Harness 退出前已经事务提交；
- 恢复只依据可校验的 Harness 持久化事实；
- 未知执行不会在恢复时自动重派；
- 当前实验使用确定性假 Adapter、SQLite、顺序单 writer 和受控`os._exit`进程退出。

当前证据不证明：

- Adapter 接受而 Harness 尚未提交接受事实时的送达判断或安全重试；
- 真实 Codex、Claude Code 或远程 Agent 的在途执行接管和终态查询；
- 旧进程是否存活，以及外部文件、网络、费用或第三方副作用是否发生；
- 突然断电、操作系统崩溃、磁盘缓存丢失或文件系统损坏下的耐久性；
- 并发 writer、恢复竞态、多机复制、备份恢复、吞吐或生产高可用；
- 正式数据库、生产 schema、迁移、数据保留、加密和访问控制。

## 对后续探索的影响

Stargazing 8 可以建立在一个更清楚的前提上：取消、超时或强制停止若没有可靠终态，不得仅凭进程退出或控制动作把执行写成成功、失败或已取消；恢复层必须保留未知。并发恢复、竞态、在途 Agent 进程和外部副作用仍属于后续问题，不能引用本项结论宣称已经受控。

本项实验代码保存在[`experiments/stargazing-007/`](../../experiments/stargazing-007/)，它是可丢弃探针，不是正式 Harness 实现或存储选型。

## 当前结论

`有条件可行`。

确定性跨进程实验已经证明：对于“Adapter 已接受、Harness 已提交接受事实、但没有可靠终态”这一最小窗口，Harness 能从持久化事实恢复为`result_unknown`，不伪造确定结果、不自动重派且重复恢复幂等。条件和未覆盖范围如上，尤其不能外推到送达未知、真实 Agent、断电耐久、外部副作用或生产容灾。
