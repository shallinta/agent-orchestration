# Stargazing 4：异构 Agent 的共同接入边界

日期：2026-09-03

状态：已完成

当前结论：有条件可行

性质：基于 Stargazing 2、3 实证的共同边界探索，不是 Adapter 接口设计、生产实现或架构决定

## 要回答的问题

在 Codex CLI 与 Claude Code CLI 都已经被证明能够有条件地承担 thread 内 Agent 角色之后，Harness 能否在保留每种 Agent 专属适配逻辑的前提下，只依赖一组足够小、与产品名称无关的共同调用事实。

本项不追求让不同 Agent 使用相同命令、事件格式、会话机制、权限参数或取消行为。真正需要判断的是：专用 Adapter 之上是否存在足以支撑 Harness 调度角色的共同语义；如果不存在，Harness 是否会被迫理解每种 Agent 的产品细节。

## 用户当前倾向

用户当前认为每一种 Agent 应当拥有单独、专用的 Adapter，同时同意继续探索共同接入边界。

这项倾向是本轮需要尊重并检验的起点，不预先写成最终架构决定。这里所说的“共同边界”如果成立，指向的是 Harness 面对各专用 Adapter 时可以依赖的最小语义，不代表共享 Adapter 实现，更不代表用声明配置抹平所有产品差异。

## 三种候选方向

1. **单一通用 Adapter。** 主要依靠命令模板、字段映射和声明配置接入不同 Agent。复用程度最高，但 Codex 与 Claude Code 已观察到的 session、事件、启动上下文、权限和取消差异可能迫使通用层不断加入产品特例。
2. **专用 Adapter + 最小共同边界。** 每种 Agent 独立处理启动、连续性、事件解析、权限参数、诊断和停止，再向 Harness 暴露少量共同事实。这与用户当前倾向最一致，也是本项优先检验的方向。
3. **完全产品专属调用。** Harness 直接理解每种 Agent 的全部差异，不设共同边界。它最忠实于产品行为，但会让角色调度、状态维护、持久化和后续公共能力实验都与具体 Agent 耦合。

当前建议先检验第二种；若共同语义无法在不失真的前提下成立，则向第三种收缩，而不是退回第一种强行统一。

## 当前假设

### 假设一：专用 Adapter 是必要边界

Codex CLI 与 Claude Code CLI 在命令构造、连续会话、机器事件、运行上下文、工具权限、诊断、资源统计和取消终态方面存在实质差异。这些差异需要由各自专用逻辑处理，不能仅靠一套静态命令模板与字段重命名可靠消除。

### 假设二：专用 Adapter 之上仍存在最小共同语义

Harness 至少需要共同表达：一次请求是否被 Adapter 接受、对应哪个逻辑角色和执行尝试、底层是否出现开始或终态证据、是否建立或继续了逻辑连续性、是否取得 Agent 结果、调用边界是否故障、结果或送达是否未知、停止请求产生了什么可确认事实，以及有哪些资源统计和能力限制可供参考。

这里的共同语义不要求底层证据相同；同一个共同结论可能分别由 Codex 事件组合和 Claude Code 事件组合得出。

### 假设三：Agent session 只应作为不透明的连续性凭据

Harness 可以依赖“后续输入能够继续同一逻辑角色上下文”这一能力，但不应把 Codex thread id、Claude session id、长驻 streaming input 或未来由接入层携带历史的远程会话假设成同一种原生机制。共同边界只需要保存 Adapter 提供的不透明连续性引用及其适用条件。

### 假设四：结果语义与调用事实必须分层

Agent 声明的`完成`或`受阻`属于工作结果；进程退出、协议终态、权限拒绝、外部停止和 session 恢复失败属于调用事实。专用 Adapter 可以综合产品专属证据，但不能把 Agent 文本直接升级成客观成功，也不能在缺少可靠终态时把结果未知伪装成失败。

### 假设五：能力差异适合显式暴露，不适合用最低公分母隐藏

共同边界应允许 Adapter 声明经过验证的能力及其限制，例如连续输入方式、结构化结果、工具控制、资源统计和停止保证。Harness 只能依赖 Adapter 明确证明可用的部分，不能因为另一种 Agent 支持某项能力就推断所有 Agent 都支持。

## 共同追踪单位

本项暂称 Harness 提交的一次具体输入处理为一次`执行尝试`。它只是为了区分证据范围的调研用语，不是在此确定正式领域术语或数据实体。

执行尝试不等同于底层进程、transport 连接或 Agent session：

- Codex 当前主要表现为一次 `exec` / `resume` 对应一个新进程和一个 turn；
- Claude Code 既可逐次 resume，也可由一个长驻 streaming 进程在同一 session 内先后处理多条输入并产生多个 result；
- session 表达逻辑连续性，一个 session 可以承载多次执行尝试；
- 进程或连接存活只表示承载机制尚在，不能直接证明 Agent 正在处理某次工作。

专用 Adapter 需要把具体输入、原始事件与对应执行尝试关联起来。现有 Claude Code 实验只证明同一长驻进程按顺序处理两条消息的最小路径，没有证明同一连接内多个输入并发、乱序结果关联或 exactly-once 语义。

## 反证条件

出现以下任一情况时，应收缩或否定相应假设：

1. 为了表达一次正常执行尝试，Harness 仍必须判断 Codex 或 Claude Code 的原始事件、退出码或命令参数；
2. 共同状态会把 Agent 正常受阻、调用故障和结果未知合并，导致 Harness 作出错误重试、错误完成或错误失败判断；
3. 共同连续性语义要求所有 Agent 都具有原生 session id、长驻进程或同一种 resume 行为；
4. 某个对 Harness 核心调度必要的事实只能用产品专属概念表达，抽象后会丢失决定性信息；
5. 能力声明只能描述“理论支持”，无法同时携带当前版本、运行条件、保证强度或未知范围；
6. 专用 Adapter 的差异实际上可以被一套简单声明和通用执行器完整、可靠地覆盖，从而没有必要承担独立实现及维护成本；
7. 当前两种 CLI 的共同点只是一种偶合，无法形成面向未来接入对象的最低资格要求。

## 验证方法与计划证据

### 1. 证据复核

- 复核 Stargazing 2、3 的实验矩阵、成功与失败路径、成立条件和未覆盖范围；
- 重新确认当前 macOS / 架构及两个 CLI 版本，避免把版本已经变化的证据直接视为当前事实；
- 复核当前官方程序化调用、session 和结构化输出资料，只用它们确认公开能力，不替代本项目实测。

### 2. 差异矩阵

围绕启动、逻辑连续性、输入、事件与结果、工作受阻、调用故障、结果未知、停止、权限、资源统计、并发和运行条件建立逐项对照：

- 原始机制是否不同；
- 专用 Adapter 必须理解什么；
- Harness 是否确实需要知道该差异；
- 若可以统一，共同语义的最小含义是什么；
- 哪些限制必须原样向上暴露。

### 3. 反向推演

从 Harness 的真实需要反推，而不是从两套 CLI 参数求交集。至少检查以下 Harness 行为能否只依赖共同事实：

- 为角色启动一次工作并传入后续输入；
- 判断某次执行尝试是否观察到开始或终态、已经返回、调用故障或结果未知；
- 请求停止并诚实记录可确认范围；
- 保存逻辑连续性所需引用；
- 在调度前查询当前 Adapter 已证明的能力与限制。

### 4. 最小边界压力检查

使用 Stargazing 2、3 已出现的反例检查候选共同语义：

- Codex 取消后退出码为 `0`，但缺少 turn 终态；
- Claude Code 取消后退出 `143`，但同样缺少 final result；
- Codex 会出现不阻止完成的 error item；
- Claude Code 会出现非致命诊断、权限 denial 和 Agent 文本伪造工具成功；
- 两者都能产生结构化 completed / blocked 声明，但都不能据此证明真实成果质量；
- 两者的连续性入口、权限参数和启动上下文条件并不相同。

如果共同边界无法同时忠实表达这些样例，则继续缩小，不通过增加产品特例来维持表面统一。

### 5. 本项不会做

- 不编写正式 Adapter、接口、类、schema 或生产代码；
- 不决定实现语言、进程模型、插件体系或用户自定义 Adapter 机制；
- 不假设 Codex 与 Claude Code 的共同点已经代表所有未来 Agent；
- 除非复核发现现有证据缺口，不重新消耗 Agent 调用执行已经完成的 Stargazing 2、3 探针；
- 不开始 Stargazing 5 的 MCP、CLI 或 IPC 通道实验。

## 预定判断标准

核心门槛成立至少需要：

1. 每种 Agent 可以继续拥有专用 Adapter，并由它负责产品专属事实解释；
2. Harness 无需读取产品专属原始输出，也能区分一次执行尝试已观察到开始、已观察到终态、尚无终态、取得结果、调用故障与结果未知；
3. Agent 正常受阻不会被误判为调用故障，Agent 声明完成也不会被包装成客观验收；
4. 逻辑连续性不依赖某一种 session 实现，但其丢失或恢复失败能够明确暴露；
5. 停止只表达请求及可确认结果，不虚构副作用撤销或确定终态；
6. 差异能力和保证强度能够保留，不被最低公分母静默隐藏；
7. 能提出未来 Adapter 的最低证明要求，同时明确当前结论只由 Codex CLI 与 Claude Code CLI 两个样本支撑。

若共同边界成立但必须依赖专用 Adapter、能力声明和保守未知状态，本项结论为`有条件可行`。如果只有了解具体产品的 Harness 才能正确推进，则结论为`不可行`；证据不足以判断时为`未决`。

## 当前观察

### 兼容性坐标复核

2026-09-03 重新执行最小坐标与本机 help 查询，结果仍为：

- macOS `26.5.2`；
- `arm64`；
- Codex CLI `0.144.6`；
- Claude Code CLI `2.1.252`。

版本和平台没有相对 Stargazing 2、3 发生变化，因此既有探针仍可作为本项的当前实证来源。本轮没有读取账号、凭证或认证配置，也没有重新启动 Agent 工作探针。

当前官方资料仍分别声明：Codex `exec --json` 提供 JSONL 事件并可用明确 session id `resume`；Claude Code `-p` 提供 JSON / stream-json、session id、结构化输出，并可用明确 id `resume`。这些官方声明与既有实验方向一致，但共同边界结论以下仍以 Stargazing 2、3 的本机正反证据为主。

### Probe 4.1：产品差异与共同事实矩阵

| Harness 需要面对的事项 | Codex CLI 已观察事实 | Claude Code CLI 已观察事实 | 专用 Adapter 必须负责 | 可向 Harness 提供的最小共同事实 |
| --- | --- | --- | --- | --- |
| 启动工作 | `codex exec`；JSONL；Git / trusted directory 前提 | `claude -p` 或 streaming input；启动上下文可能影响模型与认证 | 构造并校验各自命令、环境和安全基线 | Adapter 是否接受请求；底层是否另有实际开始证据；若没有，区分启动故障与尚未确认 |
| 逻辑连续性 | 明确 thread id + `resume` | 明确 session id + `resume`，或同一长驻 streaming 进程 | 保存、恢复并验证产品自己的连续性机制 | 一个 Adapter 域内不透明的连续性引用；继续成功或恢复失败 |
| 后续输入 | 每次 resume 启动一个新进程 | 可逐次 resume，也可向存活进程持续写入 | 选择产品支持且已验证的输入路径，并把每条输入与执行尝试相关联 | Adapter 已接受、观察到开始、明确未送达或送达未知；写入成功不自动等于 Agent 已消费 |
| 运行事件 | thread / turn / item / error / usage | init / assistant / tool / denial / result / usage / diagnostics | 解析事件层级和产品专属组合规则 | 相关执行尝试已观察到开始、已观察到终态或尚无终态；“尚无终态”不自动等于仍在执行 |
| Agent 最终输出 | agent message；可用 output schema | result / structured_output；可用 JSON Schema | 提取原始输出并校验所请求结构是否真正取得 | 已取得一次 Agent 结果及其结构化程度；不认证内容质量 |
| 正常受阻 | schema 中由 Agent 声明 blocked，CLI turn 正常完成 | schema 中由 Agent 声明 blocked，CLI 调用正常完成 | 把 Agent 语义声明与调用事实分开 | Agent 返回了“无法完成”的工作结果；不是调用故障 |
| 调用故障 | 无效 session、非 Git 前提失败；非零退出且未进入 turn | 无效 session、启动上下文认证失败；可能无 final result | 联合原始事件、stderr、进程和预期终态判定 | 已有足够证据确认本次调用边界失败；可附已知原因，但可重试性允许为未知，Harness 不自行猜测 |
| 结果未知 | 外部取消后退出码 `0`，但没有 turn 终态 | 外部取消后退出 `143`，但没有 final result | 识别“缺少可靠终态”，避免按退出码硬映射 | 无法确认工作结果；与失败、受阻和成功平级保留 |
| 请求停止 | 可终止本地进程组；没有事务性取消证明 | 可终止本地进程组；没有结构化取消终态 | 使用产品或进程级停止手段并报告真实观察 | 是否接受停止请求、是否仍观察到本地执行；不承诺成本、副作用或远端工作撤销 |
| 权限与工具 | sandbox 可限制 workspace 写入，但 read-only 不等于读取隔离 | tools、permission mode、safe-mode / restricted 可形成部分边界 | 翻译适用配置并验证实际生效范围 | 披露已验证的能力、保证来源、条件与未覆盖范围；不提供虚假的统一“安全等级” |
| 资源观察 | turn usage 提供 token 统计 | usage / cost 元数据；预算阈值不构成首次调用前硬上限 | 保留产品原始单位、来源和完整性说明 | 提供带来源和覆盖范围的观察量；没有数据时明确未知，不自动形成硬预算 |
| 并发与隔离 | 独立进程、workspace、thread 最小并发成立 | 独立进程、workspace、session 最小并发成立 | 建立产品适用的独立上下文与运行资源 | 是否已建立独立逻辑执行上下文；不外推容量、吞吐、同 workspace 安全性或同 session 多输入并发 |

该矩阵表明，产品差异不只存在于命令字符串和字段名。特别是 Codex 与 Claude Code 的输入生命周期、环境基线、事件组合和取消退出事实不同，静态模板无法自行决定这些事实应怎样被解释。

与此同时，Harness 真正需要的大多数判断并不要求它理解这些差异。例如，“缺少可靠终态，所以结果未知”可以由两个专用 Adapter 分别从完全不同的退出事实得出，但对 Harness 具有相同含义。

### Probe 4.2：从 Harness 行为反向检查共同边界

用上述矩阵反向推演五种核心行为：

1. **启动角色工作。** Harness 提交角色输入后，需要区分 Adapter 接受请求、底层观察到实际开始、明确未送达和送达未知；Git 前提、provider 环境、命令参数和安全基线属于 Adapter 责任。现有证据不支持 delivery ack、at-least-once 或 exactly-once 保证。
2. **保持角色连续性。** Harness 需要保存“这个角色下一次仍应继续原上下文”的关联，但无需知道底层是 Codex thread、Claude session、长驻进程还是未来由接入层携带历史。连续性引用必须限定在产生它的 Adapter 内，不能跨 Adapter 解释。
3. **等待和取得结果。** Harness 可以共同面对观察到开始、观察到终态、尚无终态、已取得 Agent 结果、已确认调用故障和结果未知。进程存活或尚无终态不能单独证明 Agent 正在处理；Agent 自述的 completed / blocked 是结果内容中的工作语义，不能取代调用边界状态。
4. **请求停止。** Harness 可以发出停止请求并接收 Adapter 已确认的停止事实；现有证据不支持共同承诺远端工作、成本、文件或外部副作用已经撤销。
5. **调度前理解能力。** Harness 可以查询 Adapter 声明并证明过的能力与条件，但不能只使用布尔值表达权限、预算或取消保证，更不能从 Agent 产品名称推断当前配置一定可用。

这五种行为都可以在不读取 Codex / Claude 原始事件的前提下成立。因而共同边界对 Harness 有实际价值，不只是对两个 CLI 参数求出的形式交集。

### Probe 4.3：最小共同边界候选

当前证据支持把以下内容作为未来设计阶段的候选语义，而不是现在确定字段或接口：

1. **关联事实**：本次执行属于哪个 thread 角色、哪个专用 Adapter 和哪次具体执行；
2. **连续性事实**：是否建立或继续了同一逻辑角色上下文，以及 Adapter 自己可以解释的不透明引用；
3. **执行事实**：Adapter 是否接受请求、底层是否观察到开始或终态、输入是否明确未送达或送达未知，以及已经观察到的必要进展；
4. **结果分层**：Agent 输出、Agent 声明的完成或受阻、调用故障与结果未知彼此分开；
5. **停止事实**：停止请求是否受支持、是否已经发出，以及 Adapter 能确认停止到哪一层；
6. **能力与条件**：哪些能力已验证可用、在哪个版本和运行前提下成立、保证强度与未覆盖范围是什么；
7. **观察量**：token、cost、耗时等可获得数据的来源、单位和完整性，而不是假定所有 Adapter 都能提供同一统计。

这些语义中，关联、连续交互、可靠取得结果以及区分故障与未知属于可参与 Agent 的核心资格；进展流、流式输入、结构化 schema、细粒度工具事件、权限控制、成本字段和停止强度应作为差异能力显式披露，不宜强制成为所有 Agent 的最低公分母。

“请求停止”可以保留为共同动作语义，但 Adapter 必须能够回答“不支持”或“只能停止本地等待，远端结果未知”。共同动作存在不等于每个 Agent 都提供同样的停止保证。

### Probe 4.4：专用 Adapter 假设的证据强度

现有证据支持的是：**每种 Agent 必须存在专属适配责任**。某个明确负责者必须理解其启动条件、连续性、原始事件组合、非致命诊断、权限和取消边界；这些责任不能泄漏给 Harness 主流程。

但本项不能据此证明：每种 Agent 永远必须使用完全独立的代码包、类或进程，也不能证明专用 Adapter 之间不得共享进程管理、JSONL 读取、日志脱敏、事件持久化或统计等基础设施。未来某些 Agent 也可能由声明配置加共享 driver 完整覆盖。

因此，“一个 Agent 一个专用 Adapter”可以作为后续设计的强候选原则；技术可行性结论应保持在“专属适配行为不可缺失”，不把实现形态提前固化。

### Probe 4.5：未来接入对象的最低证明要求

根据当前两个样本，一个未来 Adapter 至少需要用实际证据证明：

1. 能够在无人操作其原生 UI / 终端的情况下启动一次 Agent 工作；
2. 能把输入和结果与明确的 thread 角色及具体执行相关联；
3. 能让同一角色接收后续输入并保持所需逻辑连续性，不强制要求原生 session id；
4. 能取得机器可处理的 Agent 结果，或明确报告无法取得；
5. 能把 Agent 正常受阻、已确认调用故障和结果未知分开，不靠 Harness 猜测自然语言或产品退出码；
6. 能说明运行目录、环境、权限、工具、停止与资源数据的真实边界，没有覆盖的能力明确标为未知；
7. 能在版本或关键运行条件改变后识别需要复验的能力；
8. 能为归一化事实保留可追溯的产品原始事件、诊断或进程证据；Harness 可以不解释这些证据，但不能因归一化而令错误解析无法审计。

只提供一次文本请求与文本回复、却没有持续 Agent 工作、逻辑连续性和边界事实的裸模型接口，仍不因包装成 Adapter 而满足这些要求。

## 分析推断

1. 共同边界应当是**语义稳定、证据异构**：Harness 依赖共同事实，专用 Adapter 保留产生这些事实的原始证据、诊断引用和解释规则。
2. 共同边界不是把所有 Agent 压成能力最弱者。差异能力应当可以被查询和调度使用，否则身份卡中的实际能力差异无法落到可靠执行上。
3. `结果未知`必须是一等共同语义。Codex 与 Claude Code 在取消后的退出码相反，却都缺少可靠 Agent 终态，这正是不能直接统一退出码的最强反例。
4. 连续性引用必须是不透明且有 Adapter 归属的。Harness 可以持久化它，但不能自行构造、跨 Agent 复用或推断底层继承规则。
5. 能力声明不能脱离证据条件。至少需要保留 Agent / Adapter 版本、验证过的启动上下文、当前调用参数或有效运行表面，以及保证强度；具体数据结构留待设计阶段。
6. 重试安全性没有形成共同保证。Adapter 即使知道故障原因，也可能无法判断前一次输入是否被消费或副作用是否发生；结果未知或送达未知时默认不能自动重试。

## 未覆盖与限制

1. 本项只有 Codex CLI 与 Claude Code CLI 两个真实样本，不能证明边界已经覆盖远程 Agent 服务、桌面产品的程序化入口或未来未知 Agent；
2. 没有编写候选接口或模拟实现，因此只证明共同语义可描述且足以支撑当前 Harness 反向推演，没有证明某个具体 API 易用或稳定；
3. 没有验证 Adapter 热更新、版本协商、跨机器迁移、远端历史携带、认证续期或生产级容量；
4. 能力声明由谁生成、如何复验、是否允许用户覆盖，以及专用 Adapter 如何安装和扩展，仍属于后续设计；
5. 共同边界无法提升 Agent 输出质量，也不会把 Agent 语义声明转化为程序化验收；
6. Stargazing 5 的公共协作能力是否必须经由相同技术通道，不能从本项推出；
7. 没有验证消息送达确认、at-least-once、exactly-once、同一 session 多输入并发或乱序结果关联；这些不能从顺序双消息实验外推。

## 当前结论

`有条件可行`。

Codex CLI 与 Claude Code CLI 的实证差异足以支持用户当前倾向：两者需要各自承担产品专属适配责任。它们的命令、连续输入机制、事件组合、运行上下文、权限控制、诊断和取消退出事实不能被一套简单静态模板可靠抹平。

在这些专用 Adapter 之上，仍然存在对 Harness 有用的最小共同边界：执行尝试关联、逻辑连续性、输入与可观察执行事实、Agent 结果、调用故障、送达或结果未知、停止事实、能力条件和带来源的观察量。共同边界成立的关键不是底层机制相同，而是 Adapter 能够从不同原始证据中产生不失真的共同事实，并把不能统一的能力与保证原样暴露。

它只能判定为`有条件可行`，因为当前证据来自两个本地 CLI；共同边界尚未经过第三种接入形态或具体接口原型检验；每种 Agent 仍需要专属逻辑；能力差异、运行条件和未知状态不得被隐藏。

当前建议把“专用 Adapter + 最小共同语义”带入后续设计候选，但不在 Stargazing 阶段决定一个 Agent 对应哪个类、进程或包，也不排除多个 Adapter 共享基础 driver。下一项 Stargazing 5 可以分别为 Codex 与 Claude Code 验证 Harness 公共协作能力通道，不要求二者使用同一种底层通道，只要求最终调用身份和结果可以被 Harness 确定性归因。
