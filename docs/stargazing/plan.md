# Stargazing 核心技术可行性探索计划

日期：2026-09-01

最后调整：2026-09-02

状态：用户已确认；Stargazing 1 已完成；Stargazing 2 已完成，结论为有条件可行；Stargazing 3 尚未开始

性质：技术调研计划，不是产品实现计划、版本范围或架构决策

## 调研目标

Stargazing 要判断：以当前可获得的成熟 Agent 产品和程序化能力，是否能够建立一个可靠的 Harness 核心，使多个 thread 角色在共同事实、明确约束和持续上下文中协作，并在无需真人逐轮转发时连续推进。

调研优先回答五个阻断性问题：

1. Codex CLI 和 Claude Code CLI 是否能够被可靠启动、持续交互、区分正常结果与调用故障，并在多个角色间保持隔离；
2. Agent 是否能够通过机器可解析的边界读取或改变 Harness 公共协作事实，而不依赖 Harness 猜测自然语言意图；
3. 主持与其他 Agent 角色是否能够完成一次不需要真人中转消息的连续协作闭环；
4. Harness 进程中断、Agent 返回不确定或调用取消时，是否存在足够的事实用于安全恢复和避免伪造确定结论；
5. 权限、审批、预算、工作目录、取消和资源计量等限制，在目标 Agent 与当前运行环境下分别能提供什么真实保证。

## 不在本阶段解决

- 不确定 `v0.0.1` 的功能范围、发布标准或 UI 形态；
- 不设计完整领域模型、数据库 schema、生产状态机或长期扩展接口；
- 不实现身份卡管理、项目组合管理、完整知识库、定时任务、飞书或 Telegram 接入；
- 不为所有 Agent 厂商建立通用适配生态；首轮以 Codex CLI 和 Claude Code CLI 两种真实异构能力为主要对象；
- 不评判 Agent 业务结果质量是否达到特定领域要求，只研究调用、协作和可恢复边界；
- 不把一次跑通的实验代码直接升级为正式产品代码。

## 调研方式选择

可以采用三种常见方式：

1. **资料清单式调研**：逐项阅读 CLI、MCP、存储和并发资料。成本较低，但容易把“文档声称支持”误当成端到端可用。
2. **孤立技术探针**：分别编写调用、恢复和协议实验。证据具体，但如果缺少共同主线，可能形成许多局部成功却无法组成产品闭环。
3. **门槛驱动调研**：先验证 Agent 边界，再验证公共能力通道，随后组成最小连续协作，最后补充恢复与保证强度。每一层都以前一层证据为前提。

本计划采用第三种。它最早暴露会阻断 Harness 核心价值的问题，同时仍允许 Codex 与 Claude Code 的独立调研并行进行。用户已经确认这条推进主线，但它仍是可调整的调研安排，不是架构决定。

## 证据标准

每项调研按以下优先级收集证据：

1. 目标产品当前版本的官方文档、内置帮助和协议说明；
2. 本轮最小兼容性坐标与可复现命令输出；
3. 只覆盖当前问题的最小实验，以及成功与失败路径；
4. 必要时使用官方 issue、发布说明或源代码解释边缘行为；
5. 第三方文章和经验只作补充，不能单独支撑关键结论。

涉及快速变化的 CLI、SDK、MCP 或 API 时，记录必须注明验证日期和精确版本。用户自行负责完成 Agent 登录配置；涉及凭证或私有仓库时，只保留脱敏事实，不读取或保存敏感值。

## 调研主线与顺序

### Stargazing 1：评估协议与最小兼容性基线

**目的：** 建立后续所有结论共同使用的评估协议、证据格式与最小兼容性坐标，避免把调研变成对某台电脑的全面环境审计。

**需要回答：**

- 本轮证据所对应的 macOS 版本、芯片架构、Codex CLI 与 Claude Code CLI 精确版本是什么；
- 在“用户已经自行完成 Agent 安装、登录和必要配置”的前提下，后续如何一致检查启动、输入、输出、会话连续性、退出、超时、取消、并发、工作目录和资源统计；
- 后续实验应怎样记录实际调用参数、工作目录、相关输出、退出事实、副作用、观察、推断与结论；
- 怎样使用隔离临时目录并避免 push、发布、部署、外部消息、凭证泄露等无关副作用；
- 环境变化后，哪些最小坐标需要重新记录，哪些具体能力只在受到影响时局部复验。

**最小兼容性坐标：** 只主动记录 macOS 版本、`arm64` / `x86_64` 架构及两个 CLI 的精确版本。登录状态作为用户负责满足的实验前提，不读取或记录账号、凭证、认证文件、套餐和额度信息。

**默认忽略：** shell、Node.js / Python 等运行时、安装路径、Git 版本、主机资源、网络与代理、安装方式、全局配置、插件、Skill、MCP 和账号套餐等信息不主动盘点。只有实际证据表明某项因素影响结果时，才把它补充为对应结论的成立条件；“默认忽略”不表示已经证明它与结果无关。

**本项不做：** 不检查认证细节，不运行复杂 Agent 能力探针，也不提前验证 session、并发、取消、MCP、故障或恢复；各 CLI 的首次实际程序化调用分别进入 Stargazing 2 和 Stargazing 3。

**计划产物：** `001-evaluation-protocol-and-minimal-compatibility-baseline.md`

**进入下一层的条件：** 最小兼容性坐标、共同检查维度、证据格式、安全实验规则和环境变化后的复验原则已经明确；不要求证明当前机器“全面就绪”，也不要求任何 Agent 能力已经可行。

### Stargazing 2：Codex CLI 程序化协作边界

**目的：** 用当前官方资料与真实调用验证 Codex 是否满足一个 Agent 角色的基本接入需要。

**需要回答：**

- 非交互调用、持续会话、后续输入和结果取得分别有哪些受支持入口；
- 是否能够可靠区分输出内容、结构化事件、诊断信息和进程退出事实；
- 工作目录、权限模式、工具/MCP 配置和角色上下文是否能够在多个 session 间隔离；
- 超时、取消、进程异常和无法确认结果时可以观察到什么；
- 并行运行多个独立 Codex 角色是否存在共享状态或资源冲突；
- token、调用时长或其他成本数据能观察到多少，哪些仍未覆盖。

**计划产物：** `002-codex-cli-programmatic-boundary.md`

**核心门槛：** 至少存在一条无需人工操作终端、能够发起工作、关联后续输入并取得可用或明确受阻结果的可复现路径。

### Stargazing 3：Claude Code CLI 程序化协作边界

**目的：** 用与 Stargazing 2 相同的核心检查维度验证 Claude Code，同时保留它自己的实际语义。

**需要回答：**

- `-p`、session 创建与 resume 等当前入口的真实行为和限制；
- session id、流式或结构化输出、stderr、退出码与最终结果能否可靠取得；
- 权限、工具、MCP、工作目录和多个角色 session 怎样隔离；
- 超时、取消、网络故障、resume 失败和不确定结果时能够取得哪些事实；
- 多个独立 Claude Code 角色并行时是否可靠；
- 能够观察和限制哪些资源消耗。

**计划产物：** `003-claude-code-cli-programmatic-boundary.md`

**核心门槛：** 与 Stargazing 2 相同，但不要求两种 Agent 使用相同命令、输出或会话机制。

Stargazing 2 与 Stargazing 3 在 Stargazing 1 完成后可以并行推进。

### Stargazing 4：异构 Agent 的共同接入边界

**目的：** 根据 Stargazing 2 与 Stargazing 3 的真实差异，判断 Harness 是否能建立足够小的共同调用边界，同时允许 Agent 特有行为存在。

**需要回答：**

- 创建逻辑角色执行上下文、发送后续输入、取得结果、请求停止和报告能力分别需要哪些共同语义；
- 哪些差异可以由声明信息表达，哪些必须由 Agent 专属逻辑处理；
- session 连续性由 Agent 原生维护和由接入层携带历史时，Harness 可以共同依赖的事实是什么；
- 调用成功、正常受阻、调用故障和结果未知能否保持产品层区分；
- 一个未来自定义接入点最低必须证明哪些能力，而不把裸模型补造成 Agent。

**计划产物：** `004-heterogeneous-agent-common-boundary.md`

**核心门槛：** 能描述一个不抹平真实差异、也不依赖特定产品名的最小共同边界。此项只形成可行性结论和候选方向，不设计最终接口。

### Stargazing 5：Harness 公共协作能力通道

**目的：** 验证 Agent 能否以确定性、可归因的方式使用发消息、发布委托和查询 thread 等 Harness 公共能力。

**需要比较：**

- 本地 MCP server 与 MCP tools；
- 独立 CLI/子命令调用；
- 本地 HTTP 或其他受控进程间接口；
- Agent 返回结构化工具请求、由 Harness 解析后执行的边界。

**评估维度：** 两种目标 Agent 的支持程度、调用者角色身份绑定、参数和结果结构、错误语义、并发、连接生命周期、权限校验位置、可测试性以及是否需要自然语言意图判断。

**最小实验能力：** `send_message`、`publish_delegation`、`query_thread`。实验只需操作隔离的临时事实，不建立完整产品模型。

**计划产物：** `005-harness-public-capability-channel.md`

**核心门槛：** Codex 与 Claude Code 各自至少存在一条机器可解析、能够绑定调用角色并取得明确成功或失败结果的公共能力调用路径。两者不强制使用同一种通道。

### Stargazing 6：最小免人工中转连续闭环

**目的：** 将前述证据组合起来，验证产品最核心的技术假设，而不是验证完整产品功能。

**建议实验链路：**

1. 为一个主持角色和一个普通 Agent 角色建立彼此隔离的逻辑上下文；
2. 主持通过 Harness 实验边界发布一项最小委托；
3. Harness 把工作交给目标角色；
4. 目标角色返回结果并通过公共能力回报发布者；
5. 主持接收结果并自主形成下一步或结束本次实验；
6. 全过程不由真人复制、改写或转发角色消息。

这条链路可以使用无副作用的小任务和临时事实存储，不要求引入完整目标模型、知识层、审批、UI 或正式数据库。

**计划产物：** `006-minimal-continuous-collaboration-loop.md`

**核心门槛：** 至少一次使用两个真实 Agent 角色的完整闭环可以复现；若只能依赖真人转发，或只能把固定脚本冒充主持判断，则当前技术方向不能证明核心价值。

### Stargazing 7：持久化、进程重启与不确定结果

**目的：** 判断 Harness 自己重启或 Agent 调用中断后，是否能够恢复协作事实并诚实表达无法确认的部分。

**需要验证的中断点：** 调用前、调用已启动但未返回、结果已产生但未持久化、公共能力请求执行中、结果已记录但尚未送达目标角色。

**需要回答：**

- 哪些最小事实必须先持久化，才能重建角色、消息、调用和委托关系；
- Agent session 能否在 Harness 重启后恢复，失效时能够取得什么证据；
- 重试何时可能重复成本或外部副作用；
- 何时只能报告结果未知，而不能声称失败或成功；
- 实验用存储和恢复机制证明了什么，又没有证明什么。

**计划产物：** `007-persistence-restart-and-unknown-outcome.md`

**核心门槛：** 至少能恢复已确认的 thread 事实，并对无法确认的 Agent 执行保持诚实；不要求本阶段完成生产级高可用或通用幂等方案。

### Stargazing 8：并发、取消、停用与保证强度

**目的：** 验证 Harness 对正在运行的真实 Agent 能观察和控制到什么程度，并把强制、外部强制、弱约束和未覆盖范围分开。

**需要回答：**

- 不同角色能否并行运行，同一角色多个主动执行会发生什么；
- 超时、普通取消、强制停止进程和角色停用分别能阻止哪些后续行为；
- 工作目录、文件、网络、MCP、原生工具和外部服务访问分别由谁控制；
- Harness 能够计量和阻止哪些调用成本，Agent 内部成本或外部成本有哪些盲区；
- 强制边界不可用时能否被检测，哪些情况只能依赖配置说明或提示词。

**计划产物：** `008-concurrency-cancellation-and-guarantees.md`

**核心门槛：** 形成基于实际证据的保证矩阵；不要求所有能力都能被 Harness 强制控制，但不允许把未覆盖能力描述为已经受控。

### Stargazing 9：阶段综合结论

**目的：** 汇总各项证据，判断当前技术条件是否足以进入具体产品设计或版本规划。

**计划产物：** `009-feasibility-synthesis.md`

综合结论至少包含：

- 每项核心门槛的`可行`、`有条件可行`、`不可行`或`未决`判断；
- 已验证的能力、适用版本和环境；
- 会阻断核心闭环的问题及可能替代方向；
- 可以带入设计阶段的候选边界，而不是未经验证的完整架构；
- 必须向用户公开的弱约束和未覆盖范围；
- 仍需在后续阶段研究的非核心问题；
- 对“继续、调整方向、补充证据或停止当前路径”的建议及依据。

## 依赖关系与推进方式

```text
Stargazing 1 评估协议与最小兼容性基线
 ├─ Stargazing 2 Codex CLI 边界 ─┐
 └─ Stargazing 3 Claude Code 边界 ├─ Stargazing 4 共同接入边界
                                       └─ Stargazing 5 公共能力通道
                                  ↓
                         Stargazing 6 最小连续协作闭环
                           ├─ Stargazing 7 重启与恢复
                           └─ Stargazing 8 并发、取消与保证
                                  ↓
                             Stargazing 9 综合结论
```

Stargazing 2 与 Stargazing 3 可以并行；Stargazing 7 和 Stargazing 8 可以在 Stargazing 6 的稳定实验基线上部分并行。其他事项按依赖顺序推进，避免在基础调用边界尚未成立时提前设计完整运行系统。

## 每项调研的完成检查

- 原问题、当前假设和反证条件已经写明；
- 官方资料与本机实际能力已经区分；
- 环境、日期、版本和可复现步骤齐全；
- 成功路径和至少一个相关失败路径得到验证，或明确解释为何无法安全验证；
- 观察事实与分析推断分开；
- 结论使用统一的四类表达，并说明适用条件；
- 新发现的风险、后续问题和对其他调研项的影响已更新；
- `logbook.md` 已同步当前状态和下一步；
- 没有凭证、敏感环境值或不应提交的私有输出。

## 阶段完成条件

本阶段在以下条件同时满足时才可以提议完成：

1. Stargazing 1 至 Stargazing 9 均有结论，或某项因前置不可行而有明确停止理由；
2. Codex CLI 与 Claude Code CLI 的实际程序化边界均有当前版本证据；
3. Harness 公共能力通道至少对两种 Agent 各验证一条可行路径；
4. 至少完成一次由两个真实 Agent 角色参与、无需真人转发消息的连续闭环；
5. 重启恢复、不确定结果、并发取消和约束保证均形成边界结论；
6. 阶段综合记录明确建议继续、调整、补证或停止，并由用户审阅决定下一步。

阶段完成不要求生产级代码、完整功能、性能优化或发布 tag。调研结论即使全部可行，也不能自动替用户决定 `v0.0.1` 范围。
