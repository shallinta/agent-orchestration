# Dreaming 10：委托是独立跟踪的工作责任

日期：2026-08-20

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论 thread 内什么是委托、委托与普通消息有什么不同、谁对委托负责、谁能发布和验收，以及委托需要被怎样持续跟踪。当前暂定使用“委托”作为这一产品概念的术语。

本次不决定精确的数据结构、协议、工具、数据库表、状态枚举或转换规则，也不讨论具体的委托关系与子委托机制。

## 普通消息与委托是两种不同事物

普通消息用于角色之间沟通。发送请求、建议、提醒或讨论内容，不会天然产生一项必须被持续跟踪的工作责任。

委托则是发布角色要求一个唯一目标角色完成一项工作并交付结果的、独立持续跟踪的工作责任。委托一旦合法发布，就不只是一段对话内容；在它走到结束状态之前，Harness 都需要持续保留和呈现这项责任及其进展。

因此，不能仅凭一条自然语言消息看起来像在“派任务”，就把它自动视为委托。普通消息可以辅助说明、讨论或调整委托，但两者仍是不同的产品概念。

## 委托必须能够被 Harness 明确认出

Harness 通常是固定代码程序，不依赖 LLM 理解自然语言来判断一条消息是否构成委托。角色必须以明确、机器可识别的结构化形式发布委托。

结构化委托消息本身仍是 thread 会话的一部分，需要和其他会话消息一样持久化。同时，委托还需要作为一项独立记录持续持久化，并与对应的结构化消息建立关联。用户讨论中曾把这种独立产品记录称为“委托表”；这里确认的是委托必须有独立于消息的可跟踪记录，不是在决定数据库表或其他存储实现。

结构化委托消息与独立记录具体谁先产生、如何相互关联，属于后续设计问题，不在本次 Dreaming 中决定。

## 合法发布后立即形成责任

委托合法发布后立即生效，不要求目标角色先接受，才产生工作责任。

目标角色可以拒绝委托，也可以请求发布者调整委托；发布者可以取消已经发布的委托。这些行为会改变委托的进展，但准确的状态名称、完整状态集合和转换条件留到以后讨论。

## 是否需要发布者验收是委托自身的属性

每项委托带有“是否需要发布者验收”的产品属性。目标角色完成工作并交付结果后，可以标记完成：

- 不需要验收时，目标角色标记完成后，这项委托直接进入终态。
- 需要验收时，目标角色标记完成只代表结果已经交付；发布者验收后，委托才进入结束终态。

这里不确定具体状态名称，也不决定哪些委托应当要求验收。验收要求的默认值、判断条件和配置方式留待后续讨论。

## 一项委托恰好只有一个负责角色

一项委托只有一个目标角色，这个目标角色独立承担完成并交付结果的责任。委托不设置共同负责角色或协作角色。

如果同一项工作需要多个角色各自独立完成，发布者应分别向每个角色发布一项内容相同、状态彼此独立的委托，再由发布者比较各自结果。这不是一项委托被多人共同负责。

普通消息仍然可以有多个接收角色或发给全员。消息能有多个收件人，不代表委托也能有多个负责角色。

## 发布委托是一项角色权限

发布委托属于角色权限，主持默认拥有这项权限。其他角色是否拥有发布权限，以及允许向哪些角色发布，由具备相应操作权的平台用户配置。

一个正在承接委托的目标角色，如果拥有发布权限，也可以继续向其他角色发布新的委托。但新委托不会转移、拆分或免除它对原委托承担的责任；原委托仍由原目标角色负责。

## 发布者固定拥有验收权

一项委托的发布者固定拥有该委托的验收权。Dreaming 9 所说的“回报角色”只表示结果消息应当送达谁，不会因此获得委托验收权。

如果需要第三方评审，应当另行向评审角色发布一项独立的评审委托。评审角色完成评审后，把评审结果回报给原委托发布者；原委托是否验收，仍由它的发布者判断。

这一结论细化并覆盖 Dreaming 9 中可能把多目标任务消息理解为委托的部分：消息可以同时发给多个角色，回报消息也可以指定不同接收者；但一项委托始终只有一个目标角色，验收权始终属于发布者。Dreaming 9 原文作为当时的消息路由认识保留，不回写。

## 与 Spark 1 的“委托”不是同一概念

Spark 1 描述的是 Harness 之外的 Agent 猎人公会式任务委托板，其中一项委托可以允许多个 Agent 重复承接并各自完整完成。那是 Spark 1 旁支系统设想中的委托板语义，不属于本 Dreaming 所定义的 Harness thread 内委托。

Harness 中同一工作如果交给多个角色独立完成，必须分别产生多项独立委托；不能把 Spark 1 的多人重复承接规则带入这里。

## 这项共识暂时不意味着什么

- 不意味着自然语言中的请求、提醒或“请你做某事”会自动成为委托。
- 不意味着已经决定结构化委托消息的精确 schema、字段、协议或发布工具。
- 不意味着“委托表”已经被确定为某种数据库表，也不意味着已经决定任何存储实现。
- 不意味着已经决定全部状态名称、状态枚举、转换规则或异常恢复方式。
- 不意味着已经决定哪些委托需要验收，以及验收要求如何形成默认值。
- 不意味着一项委托可以有多个共同负责或协作角色。
- 不意味着受托角色发布新委托后，可以把原委托责任转移给新目标角色。
- 不意味着回报角色、第三方评审者或主管理员会自动取得原委托验收权。
- 不意味着已经决定委托之间如何建立关系，或是否存在子委托。
- 不意味着 Spark 1 的多人重复承接语义适用于 Harness 委托。

结构化委托的具体表达、独立记录与消息的创建顺序、精确状态模型、验收规则，以及委托之间是否需要关系，留给后续 Dreaming 或设计阶段继续讨论。
