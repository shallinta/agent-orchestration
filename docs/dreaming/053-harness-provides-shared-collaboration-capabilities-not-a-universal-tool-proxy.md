# Dreaming 53：Harness 提供公共协作能力，不代理 Agent 的全部工具

日期：2026-08-31

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 11 已经确认 Harness 负责确定性协作执行，Dreaming 26 和 Dreaming 51 又确认成熟 Agent 保有自己的执行循环与内部工具能力。用户最初同时希望 Harness 能够解析外部调用、发送通知并把 Agent 产生的内容交给其他入口。

本次只讨论：Agent 在 thread 中行动时，哪些能力必须由 Harness 提供和承载，哪些仍属于 Agent 自身，以及 Harness 是否应该成为所有 Agent 工具与外部动作的统一代理层。

本次确认，Harness 是 thread 公共协作能力的提供者。发消息、发布委托、查询 thread、申请审批、使用定时能力以及其他改变或读取 Harness 所承载协作事实的行为，需要通过 Harness 明确提供的能力发生。Agent 自身的推理、工具循环、文件与环境操作仍由 Agent 产品承担；Harness 不因此接管、拦截或代理其全部工具和外部动作。

本次不决定 MCP、API、CLI、协议、工具清单、参数结构、进程关系、鉴权方式、权限实现、错误返回、幂等、审计格式、外部连接器或其他技术设计。

## Thread 公共协作行为必须进入 Harness

按照 Dreaming 50，消息、角色、目标、委托、治理关系、配置和事件等 thread 协作事实由 Harness 统一承载。因此，角色不能仅在自己的内部会话中声称“已经发出消息”“已经发布委托”或“已经获得审批”，就让这些行为自动成为 thread 事实。

角色需要通过 Harness 提供的公共协作能力执行相应行为。Harness 根据明确输入校验行为主体、结构、权限与适用规则，产生或读取相应事实，持久化必要记录，并把确定结果返回给调用角色或路由给目标对象。

这类能力至少可以涵盖已经确认的消息、委托、thread 查询和审批等协作行为。定时任务、心跳检测、角色状态、知识检索、进展快照和其他既有概念未来也可能通过相应能力供角色使用，但本轮不穷举公共能力清单，也不预先决定它们都以同一种交互方式出现。

公共协作能力之所以归 Harness 承载，不是为了集中所有工具，而是因为这些行为会读取或改变 Harness 自己负责的 thread 协作现实。多个角色和访问入口只有依赖同一事实来源，才能获得一致、可追溯的消息、责任和治理关系。

## Agent 保有自身执行循环与原生工具

可参与 Agent 已经能够独立承担 Agent 级工作。它可以在自己的执行环境中分析问题、使用原生工具、读写获准的工作空间、调用自身插件或服务，并根据内部循环完成工作。Harness 不需要把这些内部动作逐项转换为 Harness 工具，也不需要成为每次命令、文件操作或外部请求的数据通道。

这延续 Dreaming 26 的责任边界：Agent 自己处理内部工具使用、临时失败、恢复和工作判断，Harness 只处理自己可以客观确定的调用与协作边界。它也延续 Dreaming 47 的最低成果痕迹原则：Agent 的全部工具过程和工作空间变化不会因为参与 thread 就自动进入完整记录。

角色权限、审批策略和资源预算仍然有效。Agent 使用原生能力不表示可以绕过已有约束；但 Harness 怎样在不代理每次工具调用的情况下限制 Agent 环境、哪些能力能够被可靠约束，以及无法约束时怎样向平台用户表达边界，属于后续产品与设计问题，本轮不假装已经解决。

## Harness 自己提供的外部连接能力仍由 Harness 执行

有些公共能力最终会连接 thread 外部。例如，向用户角色发送消息可能需要经过飞书、Telegram 或其他 Channel；一个明确提供给角色使用的外部通知或服务能力，也可能由 Harness 负责连接。

当角色调用的是 Harness 明确提供的能力时，Harness 仍按照自己的身份、权限、审批、预算、路由和记录规则处理，并对自己实际承载的外部调用留下相应事实。角色不能因为提出了自然语言请求就绕过这些规则，Harness 也不会因为提供连接能力而替角色判断是否值得执行。

但这不意味着 Agent 访问的所有外部系统都必须经过 Harness。Agent 可能通过自己的插件、技能或执行环境直接使用 GitHub、云服务、搜索、文件系统或其他能力。此时 Harness 不自动成为该操作的代理者，也不会假装拥有完整过程事实；它只保留按照 Dreaming 47 实际收到的最终交付、必要消息，以及角色主动同步的重要影响。

## 公共能力是产品责任，MCP 只是候选承载方式

用户提出，Harness 可以在本地提供一个 MCP server，向 Agent 暴露发消息、发布委托、查询 thread 等 Harness 相关 MCP tools。这与本轮公共协作能力边界相容：Agent 可以用明确工具而非自然语言暗示来请求 Harness 行为，Harness 也可以确定性地校验和执行。

但本轮只确认 Agent 需要能够使用 Harness 公共协作能力，不确认这些能力必须由 MCP、必须在本地、必须全部来自同一个 server，或所有 Agent 都具备相同 MCP 支持。MCP server 作为延后设计线索另行保存，进入设计阶段后再与其他承载方式、Agent 兼容性和安全边界比较。

## Harness 不是通用工具网关

如果所有 Agent 文件操作、命令、插件和外部请求都必须通过 Harness，Harness 将承担一个通用 Agent Runtime、沙箱、工具代理和外部集成平台的范围。这会重复成熟 Agent 已有能力，增加接入限制，并偏离本项目聚焦多角色协作空隙的核心问题。

反过来，如果 Harness 只做无状态消息转发，又不为角色提供委托、查询、审批和其他 thread 公共行为，Agent 就无法可靠操作同一协作现实，用户仍可能被迫在不同 Agent 之间人工维护责任和上下文。

因此当前边界不是“Harness 管所有工具”与“Harness 只是聊天转发器”二选一，而是按事实归属区分：Harness 明确承载 thread 公共协作能力；Agent 保有完成自身专业工作的内部能力。

## 与既有共识的关系

Dreaming 9 和 Dreaming 50 已经确认 Harness 承载完整 thread 记录与权威协作事实。本轮进一步确认，改变这些事实的角色行为必须通过 Harness 公共能力发生，不能只存在于某个 Agent 私有上下文中。

Dreaming 10 的委托与普通消息相互独立。无论未来使用何种交互方式，发布委托都需要进入 Harness 的委托能力和独立记录，而不是把一段看似委托的内部文本自动当成合法委托。

Dreaming 11 的确定性边界继续有效。Harness 公共能力接收明确行为并执行规则，不通过自然语言猜测角色是否想发消息、发布委托或获得审批。

Dreaming 26 和 Dreaming 51 已经把成熟 Agent 内部执行与 Harness 调用边界分开。本轮避免以公共能力为由反向接管 Agent 内部工具循环，也避免 Harness 重新变成通用 Agent 框架。

Dreaming 47 已经排除对工作空间变化的全量观察。本轮进一步确认，Agent 原生工具和外部操作不会仅因发生在 thread 工作中就自动被 Harness 代理或完整记录；只有 Harness 自己承载的调用以及角色实际提交的成果痕迹进入相应记录范围。

## 这项共识暂时不意味着什么

- 不意味着 Harness 只是消息总线，或只提供发消息能力。
- 不意味着 Agent 可以在自己的私有会话中自行创造委托、审批、消息送达或其他 Harness 事实。
- 不意味着所有 Agent 文件操作、命令、工具调用、插件和外部请求都必须经过 Harness。
- 不意味着 Harness 自动掌握 Agent 通过原生能力执行的全部外部动作和中间过程。
- 不意味着 Agent 原生能力可以绕过角色权限、审批策略或资源预算；具体约束方式仍待后续讨论。
- 不意味着 Harness 提供的外部连接能力可以绕过既有权限、审批、预算、路由和记录规则。
- 不意味着已决定完整的 Harness 公共能力清单，或每个角色能够使用相同范围。
- 不意味着必须使用 MCP、本地 server 或单一工具协议实现公共能力。
- 不意味着已经决定 MCP tools、API、CLI、参数、鉴权、身份映射、连接器、错误处理、审计或技术架构。

公共协作能力最小需要覆盖哪些角色行为，以及 Agent 原生能力与角色权限之间怎样形成可信边界，留给后续 Dreaming 或设计阶段讨论；不作为当前主线的自动下一问题。
