# Dreaming 6：Thread 是一项有界协作

日期：2026-08-13

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论 thread 在产品中的含义、用户从哪里开始一次协作，以及本 Harness 是否负责跨 thread 管理。不讨论 thread 的存储、状态模型、创建界面或运行机制。

## 共同确认的核心定义

Thread 代表一项具有共同目标和预期成果，并且有开始、有进展、有结束的有界协作。

它不是：

- 一个聊天会话；
- 一整个长期项目；
- 按天、周或其他固定时间段划分的活动容器。

聊天可以是参与 thread 的一种方式，但聊天窗口或会话边界不定义 thread。一个项目可以包含多个 thread；同一个 thread 持续多久也由其协作目标决定，而不是由固定时间决定。

## 用户从创建 Thread 开始使用 Harness

用户使用本 Harness 时，从创建一个 thread 开始。用户可以在创建时或生命周期中按需让角色加入；目标和预期成果可以在协作中逐渐确定。Harness 聚焦这一个 thread 生命周期内发生的协作。

这里不要求所有目标在创建时已经完全清晰，也不表示 thread 创建后不能调整方向；“有共同目标和预期成果”用于说明这段协作为什么被放在一起，而不是要求一份不可修改的任务合同。

## Thread 的切分权属于用户

什么应该放在同一个 thread、什么应该拆成多个 thread，由用户根据自己的工作方式和判断决定。

Harness 不强制用户采用某种颗粒度，也不替用户管理工作分解方法。它可以在创建 thread 时提供文本式启发建议，帮助用户考虑目标是否过大、是否包含多个相对独立的成果，但建议不构成限制，最终选择属于用户。

这种边界接受两类取舍都由用户承担：

- thread 较大时，协作可能更连续，但包含的阶段和子目标也更多；
- thread 较小时，目标可能更聚焦，但用户需要自行处理不同 thread 之间的背景复用。

本项目不试图替所有场景制定唯一正确的切分标准。

## 本 Harness 的职责边界

本 Harness 聚焦解决一个 thread 生命周期内的问题。

Thread 结束时，协作中形成的经验、知识、进展总结或业务资料，可以知识库、文档或其他产物的形式提交给用户自行使用。Harness 可以负责形成和交付这些 thread 内产物，但不负责：

- 同一项目中不同 thread 之间的信息传递、沉淀和汇总汇报；
- 跨项目的知识、经验沉淀或总结；
- 跨项目、跨 thread 的身份卡资产治理与集中管理；
- 多项目、多 thread 的实时进度看板。

这些能力不是因为没有价值而排除，而是属于另一个更上层的产品职责。明确边界可以避免本 Harness 从“单次协作运行环境”膨胀成完整项目管理平台。

Harness 仍需要让用户为当前 thread 选择和使用可复用的身份卡；否则无法按照 Dreaming 4 和 Dreaming 5 创建角色。这里排除的是跨项目、跨 thread 的身份卡目录、治理和资产管理，而不是当前协作对身份卡的使用。独立使用 Harness 时，身份卡从哪里取得、最低限度需要怎样管理，尚未讨论。

## 已记录的远期相邻产品

未来可能开发一个独立的 Agent 项目管理工具，用于管理多个项目及其多个 thread，并承担跨 thread、跨项目的信息沉淀、汇总汇报、身份卡管理和实时进度看板等职责。

这个相邻产品可以消费 Harness 交付的 thread 产物，但它不是本 Harness 当前需要解决的问题。两者未来如何连接，留到真正讨论该产品时再决定。

## 这项共识暂时不意味着什么

- 不意味着 thread 创建时完全没有最低治理条件；这些要求后来由 Dreaming 8 补充。
- 不意味着 thread 的目标和预期成果在生命周期中不可变化。
- 不意味着 Harness 要判断用户的 thread 切分是否正确。
- 不意味着 Harness 不能生成 thread 内的知识、文档、总结或其他产物。
- 不意味着所有协作只能存在一个目标或一个成果，只要用户认为它们属于同一项有界协作即可。
- 不意味着 Harness 与未来上层工具的连接关系已经确定。

Thread 内部如何判断结束、角色如何在权威目标下共同协作，留给后续 Dreaming 继续讨论。
