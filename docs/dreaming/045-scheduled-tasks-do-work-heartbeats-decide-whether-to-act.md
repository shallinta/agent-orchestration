# Dreaming 45：定时任务到时做事，心跳检测到时判断是否行动

日期：2026-08-27

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 44 暂时保留了定时任务与心跳检测是否需要在用户使用上明确区分的问题。本次只确认两者的产品语义边界，以及它们分别可以面向哪类角色；不讨论调度机制、数据结构、工具形式或其他技术实现。

上一轮由 Agent 根据用户关于 CronJob 与 HeartBeat 的构想提出以下推导：定时任务表达“到时要做什么”，心跳检测表达“到时检查一下，再判断是否需要行动”；心跳检测只面向具备语义检查和判断能力的 Agent 角色，向用户角色周期发送内容仍属于定时提醒。用户已经明确认同这组推导，因此本轮将其记录为当前阶段共识。

这里的区分依据是每次触发承载的用户意图和预期结果，不是一次性或周期性、Cron 或 interval、固定时刻或相对时间等实现形式。

## 定时任务承载已经安排好的工作

定时任务表示：创建者在安排时已经知道触发后希望发生什么。时间条件到达后，Harness 按既有安排向目标角色送达对应内容。

目标是 Agent 角色时，定时任务唤起该 Agent 去处理一项已经明确安排的工作，例如每周五整理一份周报、明日上午继续分析某份资料，或每月更新一次知识文档。Agent 仍可能因权限、审批、预算、可用状态或客观条件而无法完成，但每次触发的预期都是尝试完成这项已知工作，而不是先判断本次是否存在工作。

目标是用户角色时，定时任务发送普通提醒或消息，例如在约定时间提醒主管理员检查成果。它不会把用户角色当作 Agent，也不会产生 Agent 调用或委托责任。

定时任务既可以只触发一次，也可以重复触发。重复执行不使它自动成为心跳检测；例如“每周五生成周报”仍然是在每次到时执行一项预先安排好的工作。

## 心跳检测承载周期检查与条件性行动

心跳检测表示：创建者预先安排的是一次周期性检查，而不是假定每次检查时一定存在需要推进的实质工作。触发后，目标 Agent 根据约定关注点和当前 thread 状态，判断是否出现需要关注、报告或处理的事项。

“当前没有需要行动的事项”是一次心跳检测的正常结果，而不是失败或漏执行。发现事项后，Agent 可以在已有授权范围内处理、发送普通消息、请求审批或按照既有规则发布委托；Harness 不从检查内容中自行判断该采取什么行动。

例如，周期性查看是否出现逾期委托、是否有新风险需要提醒主管理员、是否达到需要维护知识的条件，都可以使用心跳检测。它们共同的产品语义是“定期醒来检查是否有事”，而不是“每次醒来都必须完成一项固定产物”。

## 心跳检测只面向 Agent 角色

心跳检测需要读取允许范围内的现状、理解关注点并作出“是否需要行动”的语义判断。Harness 是确定性程序，不承担这种意图理解和判断；用户角色也不是由 Harness 唤起执行 prompt 的主体。因此，心跳检测的直接目标只可以是 Agent 角色。

周期性向用户角色发送固定消息，仍然是定时任务中的用户提醒。需要先检查现状再决定是否通知用户时，心跳检测先唤起 Agent；Agent 判断需要通知后，再通过普通消息把结果送达用户角色。

这不表示心跳检测必须以主持为目标。任何具备相应能力和权限的 Agent 角色都可能承担具体检查，目标角色怎样选择、谁有权创建心跳检测，留待后续讨论。

## 两者的边界不由时间表达决定

定时任务和心跳检测都可能周期发生，也都可能依赖相同的时间触发能力。是否使用固定时刻、间隔周期或其他时间条件，不能决定它属于哪一种产品语义。

判断边界时，应关注创建者安排的责任：

- 如果每次触发都预期目标完成一项已经说明的工作，即使工作中包含查询或分析，它仍是定时任务。
- 如果每次触发的主要责任是检查当前状态，再决定本次是否需要产生进一步行动，它是心跳检测。

例如，“每天检查数据并无论结果如何生成报告”是定时任务；“每十分钟检查数据，仅在异常时报警或处理”是心跳检测。两者都包含检查，也都可以周期运行，但用户对一次正常触发结果的预期不同。

实践中仍可能出现难以立即分类的安排。此时应由创建者或负责理解需求的 Agent 明确希望表达的责任，而不是由 Harness 分析自然语言后自动分类。

## 对 Dreaming 44 的细化

Dreaming 44 中“定时任务与心跳检测是否需要在用户使用上明确区分”的开放问题，本轮得到肯定回答：它们是两种不同的用户意图和产品语义，即“到时做”与“到时检查是否要做”。未来技术实现可以共享调度基础，但不能用底层复用消除这层用户语义差异。

Dreaming 44 中面向用户角色的定时提醒继续有效；本轮进一步限定，心跳检测不以用户角色为直接目标。需要检查后通知用户的路径仍然是先唤起 Agent，再发送普通用户消息。

`定时任务`和`心跳检测`仍是当前暂称。本轮确认的是两类能力的语义区别，不要求最终产品继续使用这两个名称。

## 这项共识暂时不意味着什么

- 不意味着定时任务与心跳检测必须采用两套独立的技术实现。
- 不意味着周期任务都属于心跳检测，或一次性任务都属于定时任务。
- 不意味着定时任务一定成功完成已安排工作。
- 不意味着心跳检测每次都必须发现问题、产生消息或启动新工作。
- 不意味着心跳检测只能由主持承担。
- 不意味着心跳检测可以绕过角色权限、审批策略、资源预算、可用状态或其他治理边界。
- 不意味着 Harness 需要理解自然语言并自动判断一项安排属于哪种能力。
- 不意味着已经决定创建者、创建权限、最低信息、时间表达、检查范围、结果形式、工具、UI、协议、数据结构、状态或实现。

定时任务与心跳检测分别需要向创建者表达哪些最少信息，留给后续 Dreaming 讨论。
