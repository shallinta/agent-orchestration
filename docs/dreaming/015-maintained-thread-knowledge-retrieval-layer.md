# Dreaming 15：每个 Thread 都有持续维护的知识检索层

日期：2026-08-25

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论 thread 为什么需要持续维护的知识检索层、角色如何使用它、谁负责语义维护，以及当前有效知识与历史演变之间的关系。

本次不决定知识 schema、索引技术、存储方式、检索算法、提示词内容、默认触发规则、权限细目或没有变化时的处理方式。

## 每个 Thread 都必须建立知识检索层

每个 thread 都必须建立并持续维护自己的知识检索层。它帮助角色从长期累积的协作信息中查询当前有用的业务知识、经验、规则、结论和其他可复用认识。

“持续维护”表示这项责任贯穿 thread 生命周期，不表示每产生一条消息或事件，Harness 就实时自动总结。维护频率、新鲜度要求和允许的延迟都尚未决定。

Thread 可以长期存在、跨越多个权威目标，并不断加入新的消息、事件、委托、快照和角色。仅依赖角色逐条翻阅完整历史，难以持续有效地找到当前仍适用的知识；知识检索层为此提供一个面向查询的工作入口。

这里确认的是每个 thread 都具有这项产品能力。“层”表示产品中的派生视图与查询能力，不代表已经决定技术分层、模块、索引、数据库、文件或检索技术。

## 完整记录仍是事实来源

Dreaming 9 确认的完整 thread 记录，以及后续确认的独立委托记录，仍然是事实来源。知识检索层基于这些记录进行语义整理，是派生的检索辅助。

完整记录作为事实来源，能够证明某条消息、事件、委托或治理行为发生过；它不保证消息中的每个主张都真实正确。知识维护需要区分客观事实、已经确认的决定、角色分析判断、假设和等待验证的内容，不能仅因某个主张被记录或被整理进知识层，就把它升级为事实或权威结论。

知识被纳入检索层，不会因此自动成为事实、权威目标、已确认决定或审批结论；知识没有被纳入当前有效视图，也不表示对应事实从完整记录中消失。

知识检索层可能包含归纳、判断，也可能因为维护滞后而保留尚未标记的过时认识。角色在需要时应能追溯到完整记录中的依据，不能把知识层当作对事实来源的覆盖或替代。

## 所有角色都具有知识查询能力

知识查询入口和查询动作对每个角色可用，不需要由主持代替角色完成每一次知识查找。

查询能力对所有角色可用，不等于所有角色能够检索相同内容。每个角色实际可检索的知识范围受其角色权限控制；某项知识对一个角色可见，也不会自动使它对其他角色可见。

角色能否沿知识结果查看底层消息、事件或委托依据，也受相应角色权限控制。角色没有可见知识范围时，查询表现为没有结果、受限提示还是其他行为，目前尚未决定。

角色权限限制的是可检索范围，不改变完整记录是事实来源，也不改变知识检索层作为 thread 公共协作能力的存在。

## 知识维护可以被明确触发

知识维护可以来自两类触发：

- 具备相应权限的角色主动请求进行知识维护。
- Thread 配置中的确定性触发，例如按时间触发、累计到一定信息数量时触发，或者与进展快照更新同步触发。

时间、数量以及与快照同步目前只是候选例子，不代表默认规则已经确定。哪些角色能够主动触发、默认是否启用确定性触发、具体条件和范围是什么，都尚未决定。

检查点或其他触发发生后，如果没有知识变化，是否仍需要形成一次维护结果，也尚未决定。

## 主持负责语义维护，Harness 只负责确定性请求

触发知识维护后，Harness 通过专门用于知识维护的明确提示，请求主持进行本次知识维护。提示词的具体内容尚未决定。

主持负责理解新增事实和既有知识的含义，并判断应当新增什么、修正什么、合并哪些重复内容、把哪些知识标记为过时，以及哪些旧知识已经被新知识取代。主持可以亲自完成，也可以像生成进展快照一样，发布一项普通委托，由具备合适能力和权限的角色代为维护。

委托代办仍遵循普通委托的责任与验收规则，不因此产生额外的知识维护审批机制；代办时是否需要验收，不在本次决定。

Harness 不理解知识内容，不自行判断应当新增、修正、合并、标记过时或取代什么。它只根据明确触发和权限规则发出维护请求，并保存、展示由主持或受托角色形成的维护结果。

## 知识查询面向当前有效视图

知识检索层面向角色提供当前有效的知识视图。知识随着 thread 发展，可以被修正、合并、标记为过时，或被新的知识取代，使后续查询优先获得当前仍适用的认识。

“当前有效”是一项语义判断，由主持或受托维护角色基于事实依据作出，不由 Harness 根据文本或时间自行推断。知识层展示某项内容为当前有效，也不会让它越过原有治理关系自动成为权威结论。

维护当前有效视图不表示旧知识及其变化过程可以消失。旧版本、修正与取代过程，以及形成这些变化的依据，都需要保留，并能够追溯到完整消息、事件、委托和其他相关事实记录。

这里确认的是当前视图与历史可追溯并存的产品行为，不是在决定版本表、变更链、物理覆盖或其他存储结构。

## 与进展快照的历史行为不同

知识维护的时机可以与 Dreaming 13 的进展快照检查点相似，也可以在 Thread 配置明确时与快照更新同步，但两者不是同一种派生视图。

进展快照记录某个检查点当时的协作认识，历史快照不回写，新的认识通过新快照表达。知识检索层则需要持续维护当前有效内容，让角色查询时优先获得现阶段适用的知识。

知识层维护当前有效内容，不表示可以丢弃历史。快照强调保留每个时点的工作视图；知识层强调当前有效查询，同时保留旧知识的演变和事实依据。是否与快照同步维护，仍取决于明确配置，而不是两者天然绑定。

## 与既有边界保持一致

本轮进一步确认了 Dreaming 9 中尚未展开的知识库持续维护与查询能力，但不改变完整记录、直接送达和主动查询之间的区别。

它也与 Dreaming 11 一致：Harness 可以识别明确触发、校验权限、发送维护请求、持久化并展示结果，但不能理解知识或作出语义维护决定。

按照 Dreaming 14，知识关键字和知识检索层可以成为新角色入场上下文的一部分，但主持的推荐仍只是相关性建议，不会临时扩大或缩窄角色的知识查询权限。

## 这项共识暂时不意味着什么

- 不意味着已经决定知识的 schema、分类、字段或关系结构。
- 不意味着已经决定使用全文索引、向量检索、图结构或其他索引技术。
- 不意味着已经决定知识的文件、数据库或其他存储方式。
- 不意味着已经决定检索算法、排序方式、召回策略或查询交互。
- 不意味着已经决定知识维护提示词的具体内容。
- 不意味着持续维护要求实时更新、逐条消息触发，或已经确定新鲜度标准。
- 不意味着已经决定维护触发的默认值、权限、条件或事实范围。
- 不意味着已经决定没有知识变化时是否仍形成维护结果。
- 不意味着已经决定角色权限的具体细目、默认范围或授权流程。
- 不意味着 Harness 会理解知识内容，或自动决定新增、修正、合并、过时和取代关系。
- 不意味着知识检索结果自动成为事实、权威目标、已确认决定或审批结论。
- 不意味着已经决定旧知识版本、演变关系和事实依据采用何种结构保存。

知识的表达与组织、索引与存储、检索体验、维护提示、触发默认值、权限细节、无变化时的行为，以及历史演变的具体呈现，留给后续 Dreaming 或设计阶段继续讨论。
