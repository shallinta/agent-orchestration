# Dreaming 17：资源预算是 Thread 自治的强制边界

日期：2026-08-25

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论 thread 中的资源预算解决什么问题、由谁设定、Harness 如何执行，以及预算边界内的主持自治。

本次不决定预算 schema、计费适配器、计量算法、接口、协议或其他实现方式，也不确定具体预算维度及其默认值。

## 预算不是事后统计

Thread 资源预算不是协作结束后才查看的一份消耗统计，而是平台用户事先或在协作过程中明确设定、由 Harness 确定性计量并强制执行的自治边界。

统计回答“已经消耗了什么”，预算还要约束“接下来是否仍允许产生新的资源消耗”。已经发生的消耗事实可以同时服务于统计和预算判断，但事后展示统计不能代替预算约束。

预算的目的不是让 Harness 评价工作价值，而是在主持和其他角色获得一定自治能力时，为平台用户提供可以预先控制的资源边界。

## 预算可以覆盖多种可计量资源

当前考虑的候选预算维度包括：

- token 消耗；
- 远程 API 费用；
- Agent 或外部服务的调用次数；
- 运行时间。

这些只是候选范围，不表示每个 thread 必须同时配置全部维度，也不表示已经确定每个维度怎样定义、计量或组合。运行时间具体指向什么范围、不同供应方费用如何取得、不同资源之间能否换算，本轮均不决定。

“资源预算”因此不只表示货币金额。凡是平台用户希望用明确阈值约束、并且 Harness 能够确定性计量和比较的资源，都可能成为预算维度；最终纳入哪些维度仍需后续确认。

## 平台用户设定边界，主持在边界内自治

具备相应 Thread 配置权的平台用户负责设置和修改预算及其执行策略。这延续 Dreaming 9 的权限边界：预算属于平台层的 Thread 配置，不属于主管理员、主持或其他 thread 内角色的配置权。

主持可以在预算和其他既有权限、配置允许的范围内，自主选择合适的协作方式，例如决定安排哪些角色参与、安排多少次调用或是否组织多角色讨论。预算不会替主持选择业务上最合适的方案，只限制允许消耗的资源边界。

角色不能通过普通消息、委托、讨论结论或其他 thread 内行为自行提高、关闭或绕过平台预算。即使某个真人既拥有用户角色又是平台用户，也必须通过其平台用户身份和相应 Thread 权限修改预算，不能从角色身份自动推出这项能力。

预算限制的是自治可消耗的范围，不会自动授予原本没有的角色权限、工具权限或行为能力。某项动作只有在既有能力与权限允许、并且预算边界也允许时，才能继续产生新的资源消耗。

## Harness 只计量和比较明确阈值

Harness 依据平台用户已经设置的预算规则，对可计量消耗进行记录，并把当前消耗与明确阈值进行比较。它可以识别阈值是否到达，但不理解一次调用的业务意义，也不判断这次调用“是否值得”。

是否值得继续调用、应当改用更快或更便宜的 Agent、应当缩小讨论范围还是申请追加预算，都是主持或真人结合目标与协作情况作出的语义判断。Harness 不能因为认为某项工作重要，就自行突破预算；也不能因为认为收益不足，就在阈值以内额外阻止调用。

预算消耗、阈值到达、提醒与阻止等能够由明确规则识别的事实，继续按照 Dreaming 11 的确定性事件边界执行，并进入完整 thread 记录。具体事件分类和表达方式不在本轮决定。

## 软阈值用于提醒调整

预算策略可以包含软阈值。到达软阈值时，Harness 不自行评价协作方案，而是按明确规则提醒主持和相关用户角色，使他们能够调整后续协作方式、减少消耗，或者由具备相应 Thread 配置权的平台用户考虑调整预算。

软阈值提醒不会自动修改预算、停止 thread、撤销委托或替主持选择替代 Agent。哪些用户角色属于“相关”、提醒发送几次、通过什么渠道送达，以及提醒后是否采取行动，尚未决定。

## 硬上限阻止新的成本型调用

到达硬上限后，Harness 必须阻止新的成本型调用，直到具备相应 Thread 配置权的平台用户追加预算，或者按照已经配置的规则获得明确授权。

硬上限是强制边界，不是给主持参考的建议。主持、主管理员、管理员或其他角色都不能仅通过 thread 内自然语言要求 Harness 忽略它；明确授权也必须来自平台用户预先设置或执行的预算规则，而不是 Harness 根据内容重要性自行推断。

本轮只确认对“新的成本型调用”的阻止。到达硬上限时已经开始但尚未结束的调用如何处理，预算追加或一次性授权怎样恢复调用，以及授权适用于一次调用、一个范围还是其他边界，都尚未决定。

硬上限也不表示 thread 自动结束、权威目标自动失败或已经发生的记录被撤销。预算受限后的业务下一步仍由主持或真人判断。

## 通用预算可以与具体能力开关组合

预算与具体能力是否开放是两个不同问题。平台用户可以用能力开关控制主持或其他角色能否采取某类行为，也可以用通用预算控制多类已允许行为共同能够消耗多少资源。

例如，Dreaming 16 中“主持能否自行发起多角色讨论”仍可以由具体 Thread 配置控制；即使该能力被允许，相关调用也必须服从通用预算。反过来，仍有预算余额也不会自动开放一个被禁止的能力。

通用预算的价值在于为多种成本型行为提供共同的自治边界，避免平台用户为了控制总体消耗而必须给每一种具体行为分别设置预算。这不排除未来对特定能力增加更细的限制，但是否需要、如何组合均未决定。

## 尚未解决的计量与恢复边界

以下问题会影响预算能否准确执行，但本轮保留为未决事项：

- 已经开始的调用在触及硬上限后如何处理；
- 调用前估算与实际消耗之间存在误差时如何判断和记录；
- 软阈值与硬上限的默认值，以及是否必须同时存在；
- 追加预算、恢复调用和一次性授权的产品行为；
- 是否按预算维度、角色、Agent 或其他范围分别限制；
- 供应方未提供成本数据、数据延迟或无法准确计量时如何处理。

这些未决问题不改变当前边界：只要某项预算规则已经被平台用户明确配置，Harness 就按能够确定取得的计量事实与明确阈值执行，不用语义判断替代缺失的计量规则。

## 与既有边界保持一致

本轮进一步展开 Dreaming 8 中曾列为配置候选的“统计与预算”，并按照 Dreaming 9 的后续修正确认预算设置权属于具备相应 Thread 配置权的平台用户，而不是主管理员角色。

它也延续 Dreaming 11：Harness 只处理可明确计量的事实、阈值和已经配置的动作，不判断调用价值或选择业务方案。阈值之外需要如何调整协作，由主持或真人决定。

与 Dreaming 16 一致，主持能否自行采取某类成本型行为仍可由具体能力配置控制；通用预算提供跨行为的资源上限，不把每种协作场景都变成独立预算模式。

## 这项共识暂时不意味着什么

- 不意味着预算只是协作结束后的统计报告。
- 不意味着已经确定 token、费用、调用次数和运行时间都会成为正式预算维度。
- 不意味着已经决定任何维度的定义、单位、计量范围、换算方式或组合关系。
- 不意味着 Harness 会判断一次调用是否值得、是否必要或业务优先级多高。
- 不意味着主持或其他角色可以修改、关闭或绕过平台用户设置的预算。
- 不意味着有预算余额就自动授予某项角色权限、工具权限或具体能力。
- 不意味着软阈值会自动停止协作、修改预算或选择替代方案。
- 不意味着硬上限可以被 thread 内自然语言请求绕过，也不意味着到达硬上限会自动结束 thread。
- 不意味着已经决定在途调用、估算误差、阈值默认值、恢复、一次性授权、细分范围或成本数据缺失时的行为。
- 不意味着每一种成本型行为都需要单独配置预算。
- 不意味着已经决定预算 schema、计费适配器、计量算法、接口、协议、事件结构或调用流程。

正式预算维度、阈值与提醒默认值、在途调用和估算误差处理、授权与恢复边界、细分范围以及数据不可得时的行为，留给后续 Dreaming 或设计阶段继续讨论。
