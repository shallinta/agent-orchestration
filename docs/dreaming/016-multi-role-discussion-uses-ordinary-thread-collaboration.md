# Dreaming 16：多角色讨论沿用普通 Thread 协作能力

日期：2026-08-25

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论多个角色共同分析、质疑、评审或交换意见时，Harness 是否需要把这种过程特殊化，以及发起讨论的成本治理与 thread 内治理边界。

本次不决定讨论 schema、状态、协议、算法、固定模板或其他实现方式。

## 多角色讨论不是独立领域概念

多角色讨论是 thread 内普通协作的一种使用场景，不特殊化为独立的领域实体、协作活动、运行模式或生命周期。

因此，thread 不需要为了开始一场讨论而进入某种特殊模式，也不需要由 Harness 识别一段协作何时成为讨论、讨论处于什么阶段或何时语义上已经结束。一次讨论结束也不表示委托完成、目标达到或 thread 结束。

“多角色讨论”在本轮只是对一类自然发生的协作过程的描述，不引入需要维护的额外领域对象。

## 讨论规则由角色用自然语言表达

讨论的目的、参与范围、互动方式、结束条件、进展如何记录、结果交给谁接收等要求，都通过 thread 内的自然语言规则说明。

主持负责理解这些规则，并使用已有的普通协作能力推进讨论，例如发送普通消息、向单个角色分别发布需要持续跟踪的委托、按照已有路由或广播安排消息送达，以及在明确的 Thread 配置边界内组织参与。

普通消息与委托的区别继续遵循 Dreaming 10：沟通和意见交换不天然产生需要跟踪的责任；只有确实要求某个唯一目标角色完成工作并交付结果时，才发布普通委托。多个角色分别承担同类工作时，仍是多项各自独立的委托，不产生“共同负责”的讨论委托。

这些自然语言规则指导角色协作，但不会因为被写在消息中就自动变成 Harness 需要理解的特殊讨论配置。规则是否已经满足、讨论是否获得足够结论以及语义上的下一步，仍由主持或相关真人角色判断。

## Harness 只执行通用的确定性能力

Harness 对讨论中的消息、委托和 Agent 调用，继续使用通用的权限校验、消息与事件路由、调用、并发控制和持久化逻辑。已有的定向路由、单条消息多收件人、全员广播以及 Thread 配置可以组合支持不同互动方式。

Harness 不识别“头脑风暴”“轮流发言”“两两讨论”“主持评审”等特殊讨论模式，也不理解讨论内容、评价观点质量、判断是否形成共识或决定谁的意见更重要。

如果角色希望采用轮流、广播、两两交流或其他互动方式，应由主持理解自然语言规则，并通过已有能力组织。Harness 只执行其中机器可识别且权限允许的明确动作，不从讨论文字中自行推导调用顺序、参与者或结束条件。

## 讨论记录进入完整记录，结论进入既有派生视图

讨论过程中产生的角色消息、委托和事件，继续按照 Dreaming 9 进入完整 thread 记录。定向送达不会使讨论内容脱离完整记录。

讨论形成的进展、风险、待决策事项或建议下一步，可以按照 Dreaming 13 进入后续进展快照；具有持续复用价值的有效认识，可以按照 Dreaming 15 进入知识检索层。是否重要、是否已形成结论以及应如何概括，仍由 Agent 或真人作出语义判断，Harness 不自行提炼。

讨论中的观点或总结被持久化、写入快照或纳入知识层，不会自动成为权威目标、已确认决定或审批结论。既有的事实来源、派生视图和治理边界保持不变。

## 主持能否自行发起由 Thread 配置控制

主管理员不必参与或亲自发起每一次多角色讨论。是否允许主持自行发起多角色讨论，是由具备相应 Thread 权限的平台用户控制的一项 Thread 配置，因为一次讨论可能带来额外的 token 消耗和 Agent 调用成本。

配置允许时，主持可以根据协作需要自行发起多角色讨论，并向主管理员同步讨论结论。允许主持发起不表示主管理员必须参与讨论，也不把讨论结论自动升级为主管理员确认的治理决定。

这项配置的默认值、成本阈值、是否需要按不同参与规模区分，以及向主管理员同步结论的时机与格式，都尚未决定。其他角色在什么权限下可以发起多角色讨论，本轮也不决定。

这里控制的是主持是否可以产生相应调用与成本，不把多角色讨论本身变成特殊领域实体。Thread 配置仍由具备相应 Thread 权限的平台用户设置和修改，主管理员的 thread 内治理权不因此变成平台配置权。

## 重大治理事项仍遵循既有权力边界

讨论可以形成建议、分歧、风险识别或候选结论，但不能仅凭讨论过程自行完成重大治理决定。

涉及重要风险的处置和其他重大治理事项，应由主管理员决定，或者由管理员在主管理员已经明确授予的范围内决定。管理员只能在明确授权的事项与范围内行动，不能从“参与了讨论”或“负责某个领域”自动获得治理权。

权威目标的设置、修改、替换和完成确认仍然是主管理员的唯一权力，不属于可以从管理员一般授权中自动推出的范围。即使讨论涉及目标变化，也只能提出、质疑或完善候选内容，最终仍由主管理员确认。

Harness 不根据讨论内容判断某项结论是否属于重要风险或重大治理事项。主持或相关角色负责识别并提交给拥有相应治理权的角色；Harness 只按照明确权限与路由执行。

## 与既有边界保持一致

本轮保留 Dreaming 9 的定向路由、广播与完整记录边界，不为多角色讨论创建独立消息体系。

它也保留 Dreaming 10 的单一委托责任，以及 Dreaming 11 的语义判断与确定性执行分工。讨论只是主持通过普通消息、委托、路由和配置组织协作的场景，不会让 Harness 获得自然语言理解或业务判断能力。

讨论结果进入进展快照或知识检索层时，分别继续遵守 Dreaming 13 与 Dreaming 15 的派生属性、语义维护和可追溯边界。

## 这项共识暂时不意味着什么

- 不意味着已经存在“讨论”“会议”或“脑暴”领域实体。
- 不意味着已经定义独立的讨论活动、模式、生命周期、状态或结束事件。
- 不意味着 Harness 会识别讨论目的、参与关系、互动方式、结论或结束条件。
- 不意味着自然语言规则会成为 Harness 自动解析的讨论协议或配置。
- 不意味着所有多角色讨论都必须广播，也不意味着所有讨论消息都直接送达每个角色。
- 不意味着讨论必须创建委托；是否创建取决于是否需要形成可独立跟踪的工作责任。
- 不意味着主管理员必须发起或参与每次讨论，也不意味着主持可以绕过 Thread 配置自行产生讨论成本。
- 不意味着主持发起讨论后获得新的治理权，或讨论结论自动成为主管理员确认的决定。
- 不意味着管理员的一般授权包含权威目标设置、修改、替换或完成确认权。
- 不意味着已经决定主持自行发起权限的默认值、成本阈值、参与规模规则或结论同步格式。
- 不意味着已经决定讨论 schema、状态机、协议、算法、固定模板、提示词或调用流程。

不同互动方式如何用自然语言表达、主持自行发起权限的默认边界、成本治理细节、主管理员同步要求以及其他角色的发起权限，留给后续 Dreaming 或设计阶段继续讨论。
