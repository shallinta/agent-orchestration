# Dreaming 39：推进语义属于 Thread 内角色，Harness 不预设阶段模型

日期：2026-08-27

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 33 曾使用“阶段推进安排”描述主持面向近期工作的组织方式，Dreaming 38 的结尾也继续沿用了“当前阶段”和“下一阶段”。本次重新讨论：阶段是否是平台或 Harness 的通用产品语义，以及协作进程应由谁命名和切分。

本次确认，平台与 Harness 都不存在统一的“阶段”语义，也不预设 Step、轮次、里程碑或其他推进模型。协作进程怎样命名和切分，属于 thread 内角色的场景化语义；主持只需根据现状持续决定怎样继续推进。

本次不决定角色在具体场景中使用的计划方法、进程词汇、文档模板、展示方式、通知、UI、接口、协议、数据结构、状态机、模块或实现。

## 平台与 Harness 不拥有阶段语义

平台与 Harness 不建立统一的阶段列表、当前阶段、阶段状态、阶段转换或阶段完成事件，也不要求所有 thread 采用同一种推进粒度。

因此，Harness 不通过委托完成数量、消息内容、时间经过、进展快照或其他事实自动判断“一个阶段已经结束”或“应当进入下一阶段”。平台也不要求用户先创建阶段、选择阶段模板或更新阶段状态，才能继续协作。

平台与 Harness 可以保存和展示角色写出的“阶段”“Step”等文字，也可以让角色查询相关消息和文档，但这只是在处理 thread 内容，不表示系统理解或执行了这些语义。

## 推进表达由 Thread 内角色自行选择

Thread 内角色可以根据实际场景，使用“阶段”“Step”“轮次”“里程碑”“章节”“回合”或其他概念组织协作。不同 thread 可以采用完全不同的词汇与切分方式，同一个 thread 也可以在认识变化后调整表达。

角色也可以完全不为推进过程命名，只讨论当前问题、发布委托、吸收结果并决定下一步。缺少阶段或 Step 表达不表示 thread 缺少秩序，也不会阻止 Harness 执行普通消息、委托、审批、预算和其他通用规则。

这些场景化推进语义可以出现在角色消息、普通文档、委托说明、进展快照或知识内容中，但只在该 thread 的协作语境内具有含义，不会因为被反复使用就自动升级为平台或 Harness 的系统概念。

## 主持持续决定下一步，不执行系统阶段转换

主持结合当前权威目标、已有事实、角色判断、委托责任、评审结果、风险、权限、审批和预算，持续判断接下来最值得做什么。

这种推进可以表现为形成一项新委托、继续沟通、等待已有角色、调整安排、请求决定、处理风险或其他普通协作行为。主持不需要先声明“当前阶段完成”或“进入下一阶段”，这些动作才能合法发生。

如果 thread 内角色已经采用某种阶段、Step 或里程碑语义，主持可以遵照它组织工作，并在语义上说明转换；但这仍是主持和其他角色理解的协作内容，不是 Harness 识别和驱动的状态变化。

## 委托状态不构成推进阶段门禁

未终结委托是 Harness 可以明确记录和展示的客观工作责任，但它们不会自动构成“阶段尚未结束”的系统结论。

主持可以根据具体语义决定让某项委托继续、调整、取消、延后、与其他工作并行，或采取其他当前允许的行动。它不能把未终结委托静默伪装成已经完成，但也不需要为了进入一个不存在于 Harness 中的“下一阶段”而机械等待全部委托进入终态。

如果某项权威目标、委托条件、审批要求或其他明确治理规则规定某个行动必须等待特定结果，Harness 继续执行这项明确边界。约束力来自相应目标、责任或治理规则，不来自通用阶段模型。

## 进展快照不创造阶段模型

进展快照可以使用当前 thread 选择的推进词汇，描述角色当时怎样理解工作进展。它也可以完全不采用阶段划分，只呈现目标、结果、风险、待决事项和其他有用信息。

快照中写明“进入第二阶段”只是一项可追溯的角色判断，不会让平台或 Harness 产生系统阶段状态。后续角色可以继续沿用、质疑或调整这种表达，而完整记录仍保留当时发生了什么。

知识检索层同样可以整理 thread 内采用的推进语义，但不能把某种场景化说法自动变成跨 thread 通用模型或权威治理结论。

## 对 Dreaming 33 的修正

Dreaming 33 的真正核心仍然有效：主持不必一开始制定覆盖完整生命周期的详细计划，也不能脱离权威目标随机反应；它需要形成足以继续推进的近期认识与安排，并随新事实调整。

本轮修正其中“阶段推进安排”“当前阶段”“下一阶段”等词语可能造成的通用产品含义。它们只是在 Dreaming 33 当时用于解释近期安排的描述性语言，不表示所有 thread 都有阶段，也不表示平台或 Harness 应支持阶段实体、状态或转换。

从本记录开始，应把 Dreaming 33 理解为“主持形成足以继续推进的近期安排”。角色可以用阶段、Step 或其他语义表达这项安排，也可以不为它命名。Dreaming 33 原文继续保留，涉及阶段系统语义时以本记录为准。

Dreaming 38 结尾关于“判断当前阶段已经足够、进入下一阶段”的提问也只保留为当时的讨论线索，不再作为后续问题前提。真正需要讨论的是主持如何持续判断下一步，以及何时需要主管理员治理决定。

## Harness 只提供事实并执行明确行为

Harness 继续负责消息和委托路由、完整记录、权限、审批、预算、客观角色状态、定时触发以及其他已经明确的确定性职责。

Harness 不理解当前协作处于什么阶段，不判断某种推进表达是否合理，也不替主持决定下一步。即使 thread 内角色采用严格的阶段计划，Harness 也只执行其中已经转化为明确消息、委托、审批、预算或其他通用行为的部分。

## 这项共识暂时不意味着什么

- 不意味着 thread 内角色不能使用阶段、Step、里程碑或其他推进概念。
- 不意味着主持不需要理解整体目标、组织近期工作或持续决定下一步。
- 不意味着未终结委托可以被静默当成已经完成。
- 不意味着所有委托都必须终结后，主持才能继续安排其他工作。
- 不意味着进展快照和知识检索层不能记录 thread 内使用的推进语义。
- 不意味着角色写出的“阶段完成”会自动成为平台状态、Harness 事件或权威结论。
- 不意味着平台需要提供阶段模板、阶段配置或通用进程模型。
- 不意味着 Harness 会理解、评价或转换 thread 内角色使用的推进语义。
- 不意味着已经决定角色怎样规划、命名、切分或展示推进过程，也不意味着已经决定 UI、接口、协议、数据结构、状态机、模块或实现。

主持持续推进过程中，什么时候应当把“目标可能已经达到”的判断提交给主管理员确认，留给后续 Dreaming 继续讨论。
