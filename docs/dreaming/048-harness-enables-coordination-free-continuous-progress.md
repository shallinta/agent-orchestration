# Dreaming 48：Harness 必须支持无需真人持续协调的连续推进

日期：2026-08-31

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 1 确认项目最初的问题是人被迫填补多个 Agent 之间的协作空隙，Dreaming 2 确认人应从持续协调者转变为关键判断者。本次只进一步讨论：什么样的用户体验才能表明 Harness 确实具备解决这一核心问题的能力。

本次确认，在角色权限、审批策略和资源预算允许时，Harness 必须支持一段无需真人持续承担消息转发、上下文搬运和逐轮推动的连续协作。用户可以暂时离开，主持与其他 Agent 角色仍能在既有边界内分派工作、吸收结果、安排评审或修复、判断下一步并继续推进。

这是一项产品必须提供的核心能力，不是每个 thread 必须实际出现的运行规则，也不是由程序计算和验收的成功指标。本次不决定任何状态、计时、轮数、指标、埋点、验收算法、UI、协议或实现。

## 核心价值需要在连续协作中成立

如果用户仍需在每一轮理解一个 Agent 的输出、改写给另一个 Agent 的提示、转交结果、安排评审、传递修复意见并催促下一步，那么即使 Harness 已经能够调用 Agent、记录消息和创建委托，它也没有真正消除最初的人工协调负担。

因此，Harness 的核心价值不能只体现在“能够连接多个 Agent”或“能够把单次消息从一端发到另一端”。它需要让若干相关协作动作在没有真人逐轮接力的情况下连续发生，使人可以把注意力放回其他工作，并在确实需要判断时再回来。

这里强调的是协调责任的转移，不是单纯减少用户点击次数。即使界面操作很少，只要用户仍必须持续观察并决定每一次常规交接，原问题依然存在；反过来，用户收到若干不要求回复的重要同步，也不代表其重新承担了持续协调责任。

## 用户可以暂时离开，协作仍然推进

当权威目标、当前限制以及必要授权已经足以支持工作时，用户应当能够暂时不参与日常协调。主持继续理解整体进展，在角色权限、审批策略与资源预算范围内选择角色、发布委托、吸收重要结果、组织必要评审或修复，并判断接下来可以采取的行动。

Harness 继续承担确定性的调用、路由、记录和约束执行。语义判断仍由主持及其他 Agent 角色完成，不因为用户暂时离开就转移给 Harness 固定程序。

用户暂时离开不表示 thread 与用户断开，也不表示所有消息都被屏蔽。按照 Dreaming 46，主持或其他相关角色仍可向用户角色同步不要求回复的重要信息；这类送达不会自动打断协作，也不会产生用户必须回应的义务。

## 需要人的时刻仍然可以中断连续推进

当协作遇到超出当前权限或审批自治的行动、需要主管理员作出的权威目标决定、需要真人承担的价值判断或风险接受，以及其他确实无法在既有边界内继续的事项时，相关角色可以明确请求用户介入。

这种介入不是产品失败，而是 Dreaming 2 所说“关键节点判断者”的正常位置。用户完成必要判断后，协作可以在新的明确事实和约束下继续，重新形成无需真人逐轮协调的连续推进。

反之，主持和其他角色不能把本可在既有边界内完成的日常交接全部上抛给用户，也不能因为担心出错就让用户重新承担消息中转与每一步选择。哪些事项确实需要人由相关角色结合语义和既有治理判断，Harness 不自行理解内容。

## 这是产品能力，不是每个 Thread 的强制运行规则

不同 thread 可以拥有不同的角色权限、审批策略、资源预算、风险特征和用户偏好。平台用户可能主动选择较严格的审批边界，某些高风险或高度不确定的工作也可能自然需要更频繁的人类判断。

因此，不能要求每个 thread 都必须产生一段无人介入的连续过程，也不能因为某个 thread 中用户频繁参与，就由 Harness 自动判断产品价值没有成立。实际协作能连续推进多远，是目标、人才、约束与用户选择共同作用的结果。

产品层面的要求是：当这些条件允许时，Harness 不能因为自身缺少协作承接能力，迫使用户继续充当消息中转者。是否在某个 thread 中采用更高自治，以及用户是否愿意暂时离开，继续由平台配置、thread 内治理和用户选择决定。

## 不进行程序化验收

Harness 不需要计算一次协作是否已经形成“合格的免协调区间”，也不需要依据持续时间、消息数量、委托数量、参与 Agent 数量、人工点击次数或其他统一阈值给出通过与失败结论。

这些数字即使未来可用于观察和改进，也不能代替用户对实际体验的判断。一个很短的自动交接可能已经显著减少干扰，一段很长的自动运行也可能只是低价值空转；Harness 无法仅凭数量判断是否真正释放了用户注意力或产生了有用结果。

因此，是否解决了持续协调负担，最终由用户结合实际工作体验判断。它不是目标完成、委托验收、治理确认、系统健康检查或版本准出的程序化条件。

## 不引入“免协调阶段”或运行状态

本轮使用“无需真人持续协调的连续推进”描述一种核心用户能力和理想体验，不把它建立为 thread、角色、委托或 Harness 的新状态，也不形成阶段、模式或特殊协作活动。

协作仍然使用既有目标、消息、委托、评审、角色权限、审批策略、资源预算和用户 Channel 等普通能力。用户何时离开、何时回来、哪些动作在这期间发生，都不需要先开始或结束一个名为“免协调”的系统过程。

这与 Dreaming 39 不预设通用阶段模型保持一致，也避免为了证明产品价值而增加与实际协作无关的仪式和状态维护。

## 与既有共识的关系

本轮把 Dreaming 1 和 Dreaming 2 的价值方向进一步变成可感知的用户体验边界：人不再充当持续协调者，必须表现为协作能够在一段连续过程中不依赖人的逐轮转发和推动，而不只是一句愿景。

Dreaming 18 继续决定实际自治边界。免协调连续推进不能绕过角色权限、审批策略或资源预算，也不会创造第四套授权；严格约束下频繁需要用户介入是允许的结果。

Dreaming 29 至 Dreaming 40 已经描述主持从初始意图、目标确认、近期安排、角色选择、结果吸收到目标完成提议的语义责任。本轮不增加新的职责类型，而是明确这些职责应当能够在条件允许时连续承担，不要求用户逐步驱动。

Dreaming 46 继续允许重要信息送达用户而不要求回复。用户收到消息不等于连续推进已经停止；只有确实需要回应的事项才表达用户介入期待，沉默不会产生治理效力。

## 这项共识暂时不意味着什么

- 不意味着每个 thread 都必须出现无人介入的连续协作。
- 不意味着连续推进必须达到统一时长、轮数、委托数量或 Agent 数量。
- 不意味着用户在此期间不能查看 thread、主动发言或收到重要信息同步。
- 不意味着任何用户消息都会打断连续推进，或必须把用户标记为离席状态。
- 不意味着主持和其他角色可以绕过角色权限、审批策略、资源预算或治理权威。
- 不意味着需要人的关键决策是产品失败。
- 不意味着自动运行时间越长、用户操作越少，产品价值就一定越高。
- 不意味着 Harness 会理解语义、判断下一步或评价协作是否有价值。
- 不意味着需要新增免协调阶段、模式、状态、活动、开关或生命周期。
- 不意味着已经决定统计指标、埋点、用户问卷、验收算法、测试方法、UI、接口、协议或实现。

用户怎样直观了解协作仍在健康推进、哪些体验会破坏“可以放心暂时离开”的信任，以及未来是否需要非验收性的效果观察，可以在出现实际需要时继续讨论；不作为当前主线的自动下一问题。
