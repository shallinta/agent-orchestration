# Dreaming 41：委托只发生在 Agent 角色之间

日期：2026-08-27

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 10 形成委托概念时使用了泛化的“发布角色”和“目标角色”，后续记录也多次沿用了这种说法。本次重新讨论委托究竟服务于哪类角色，以及用户角色是否应当进入委托的发布、承接和验收生命周期。

本次确认，委托系统专为 Agent 角色之间的工作责任协作而存在。一项委托的发布者和唯一目标角色都必须是 Agent 角色；用户角色既不能发布委托，也不能成为委托目标，因此不存在由用户角色验收委托的场景。

用户角色继续通过普通消息和目标确认、审批等治理行为参与 thread。用户提出的工作要求可以由 Agent 角色理解并转化为委托，但不会因为自然语言看起来像任务就自动成为委托。本次不决定角色类型校验、权限配置表达、委托工具、消息格式、UI、接口、协议、数据结构、状态机、模块或实现。

## 委托解决的是 Agent 之间的持续工作责任

Agent 角色可以持续执行工作、接收机器可识别的责任、交付结果，并围绕拒绝、调整、完成和验收等行为推进委托生命周期。委托把一个 Agent 角色要求另一个 Agent 角色完成的工作，从普通对话中独立出来，使 Harness 能够确定性地跟踪责任与状态。

真人参与 thread 的方式不同。用户角色主要表达意图、提供信息、提出要求、参与讨论，并执行目标确认、审批和重要决策等治理行为。把这些互动强行装进委托生命周期，会要求真人额外处理承接、拒绝、完成、超时和验收等机制，也会混淆真人治理责任与 Agent 工作执行责任。

因此，“所有角色通过同一种消息抽象参与协作”不等于所有角色都拥有相同的工作机制。普通消息继续覆盖 Agent 与用户角色之间、多个用户角色之间以及多个 Agent 角色之间的沟通；委托则是仅适用于 Agent 角色的专用能力。

## 发布者必须是具备相应权限的 Agent 角色

用户角色不存在发布委托的产品功能，也不能由平台用户通过角色权限配置把这种能力授予用户角色。这是角色类型对应的能力边界，不是用户角色默认关闭、以后可以打开的一项普通权限。

主持当前默认拥有委托发布权限，因为主持附加在 Agent 角色上并承担组织推进责任。其他 Agent 角色是否能够发布委托、允许在什么范围内发布，继续由既有角色权限与 Thread 约束决定；Agent 类型只表示具备使用委托系统的资格，不表示每个 Agent 角色都自动获得无限发布权限。

用户角色可以通过普通消息向主持或其他 Agent 角色提出工作要求、建议分工或要求调查。是否需要把这项输入转化为一个可持续跟踪的委托，由收到输入且具备发布权限的 Agent 角色根据语义和治理要求决定，并由该 Agent 角色执行明确的委托发布行为。Harness 不从用户自然语言中自动生成委托。

## 目标角色也必须是 Agent 角色

一项委托恰好只有一个目标角色，这个目标角色必须是 Agent 角色。用户角色不能成为委托目标，也不进入拒绝、请求调整、标记完成、等待验收或其他委托生命周期行为。

当协作需要真人提供资料、回答问题、查看成果、作出决定或执行审批时，Agent 角色通过普通消息或对应治理行为请求用户角色参与。等待真人回应可以受到既有消息等待、超时、角色可用状态或审批规则约束，但不会因此把真人变成受托角色。

一条发给用户角色的消息即使包含“请提供资料”“请确认风险”或“请查看结果”等明确行动请求，仍然是普通消息或治理请求，而不是委托。Harness 不能仅凭请求具有工作意味，就给用户角色创建委托责任。

## 用户要求由 Agent 角色转化并承担发布责任

主管理员或其他用户角色可以明确要求开展某项 Agent 工作，但它们是在通过普通消息或治理权影响协作，不是在亲自发布委托。

主持或其他具备权限的 Agent 角色吸收这项要求后，可以形成委托，并承担委托发布者已有的责任：提供起步上下文、接收和吸收结果、决定是否需要验收、在需要时执行验收，以及把重要影响同步主持。用户要求的来源不会把这些发布者责任转移给用户角色。

如果用户角色指定了希望由哪个 Agent 角色执行，主持仍需遵守适用的治理要求、角色权限、审批和预算。用户的明确决定可能对主持具有治理约束力，但真正进入委托系统的发布行为及发布者身份仍属于 Agent 角色；两层语义不能混成“用户角色直接发布委托”。

## 委托验收只发生在 Agent 发布者一侧

Dreaming 10 已经确认，是否需要发布者验收是每项委托的属性，验收权固定属于发布者。按照本轮边界，发布者一定是 Agent 角色，因此委托验收也只由 Agent 角色执行。

用户角色不存在需要验收委托的产品需求。主管理员查看成果、确认目标完成、批准高风险行动或对结果提出反馈，分别属于普通沟通或 thread 内治理行为，不会因此取得某项委托的验收权，也不应与委托验收合并。

如果 Agent 发布者需要参考用户反馈再决定是否验收，可以先通过普通消息请求用户查看或判断，再由 Agent 发布者吸收反馈并执行自己的委托验收责任。用户提供意见不会让用户成为委托发布者、目标角色或验收者。

## 用户角色仍可收到委托相关信息

用户角色不能发布、承接或验收委托，不表示委托及其结果对用户不可见，也不表示 Agent 角色不能向用户同步相关信息。

具备相应权限和消息路由条件时，用户角色可以收到关于委托进展、结果、风险或决策请求的普通消息，也可以在平台权限允许时通过 UI 查看完整 thread 记录。被通知、被抄送结果、参与讨论或查看记录，都不会把用户角色纳入委托生命周期。

平台用户对完整 thread 和角色权限的管理，继续属于平台账号与 Thread 权限体系；用户角色在 thread 内收到哪些消息和执行哪些治理行为，继续属于角色体系。委托的 Agent 类型边界不会把这两层重新混合。

## 对既有 Dreaming 的限定

本轮不改变 Dreaming 10 已确认的委托独立记录、合法发布后生效、单一负责角色、可拒绝或调整、可选发布者验收和终态等核心语义，但限定其中角色范围：

- “发布角色”或“发布者”应理解为具备相应发布权限的 Agent 角色；
- “目标角色”应理解为唯一的 Agent 角色；
- 平台用户可以在 Agent 角色具备类型资格的前提下配置发布权限，不能把用户角色配置成委托发布者或目标角色；
- 发布者验收权始终属于 Agent 发布者，不存在用户角色验收委托。

Dreaming 35 中“任何拥有相应委托权限的角色”从本记录开始也只指 Agent 角色。Dreaming 36、37、38 中的发布者、目标角色和评审角色同样都受本轮资格边界限制。

Dreaming 38 曾写到是否发布新委托可由“Agent 或真人角色”决定，其中真人角色直接发布委托的含义被本轮明确修正。真人可以通过普通消息提出形成新责任的需要，由具备权限的 Agent 角色理解并决定怎样明确发布；Harness 不替双方识别或转换自然语言意图。

旧记录继续保留当时的泛化表述，不回写；凡涉及委托发布者、目标角色和验收者的角色类型，以本记录为准。

## Harness 的边界保持确定

Harness 在委托系统中只接受符合当前产品边界的明确发布行为，持续记录和执行合法委托的状态与规则。用户角色发送普通消息不会被 Harness 自动转成委托，也不会因为消息中包含任务措辞而获得委托能力。

Harness 不负责理解用户请求是否值得形成委托，也不替 Agent 角色重组工作内容、选择目标角色或决定是否需要验收。意图理解与委托组织继续由 Agent 角色承担，Harness 只执行明确且合法的行为。

本轮确认的是产品资格与用户使用边界，不决定怎样在具体协议中表达角色类型、怎样拒绝非法发布、怎样呈现入口或怎样实现权限校验。

## 这项共识暂时不意味着什么

- 不意味着用户角色不能向 Agent 角色提出工作要求或建议分工。
- 不意味着用户发出的工作请求会自动成为委托。
- 不意味着主持必须把用户的每项普通请求都转化为委托。
- 不意味着 Agent 角色只要具有 Agent 类型就自动拥有委托发布权限。
- 不意味着平台用户可以把用户角色配置成委托发布者或目标角色。
- 不意味着用户角色会进入委托拒绝、调整、完成、超时或验收生命周期。
- 不意味着用户角色不能收到委托相关消息、结果、风险或决策请求。
- 不意味着用户查看成果、确认目标完成或执行审批等同于委托验收。
- 不意味着 Agent 发布者不能参考用户反馈形成自己的验收判断。
- 不意味着所有 Agent 与用户之间的等待行为都需要委托系统跟踪。
- 不意味着已经决定角色类型校验、权限表达、非法发布处理、工具、交互、UI、接口、协议、数据结构、状态机、模块或实现。
