# Dreaming 27：角色停用可逆，唯一标签必须先转交

日期：2026-08-26

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论 thread 角色被停用和重新启用时的产品含义、停用期间的行为、既有责任怎样保持，以及承载主持或主管理员唯一标签的角色为什么不能被直接停用。

本次不决定底层 session 的保留、释放或恢复，停用时在途调用怎样处理，启用后怎样补齐上下文，也不决定通知、权限粒度、UI、协议、状态机或其他实现方式。

## 停用和重新启用是平台层操作

只有具备相应 Thread 权限的平台用户，才可以停用或重新启用一个 thread 角色。这项操作属于平台账号与 Thread 权限层，不属于 thread 内角色治理行为。

主持标签负责整体协作推进，主管理员标签负责权威目标确认与最高审批，但这些职责不会使承载标签的角色取得停用或重新启用其他角色的平台操作权。普通用户角色、管理员角色或其他角色也不能仅凭 thread 内身份推出这项权力。

同一个真人可能同时使用平台用户账号并在 thread 中拥有用户角色，但其停用操作的权威来自平台用户所具备的 Thread 权限，不来自主管理员、主持或其他系统标签。

哪些平台用户具体拥有这项权限、是否可以只操作部分角色以及怎样调整权限，本轮不决定。

## 停用不是退出或删除

角色停用是一项可逆的运行限制，不表示角色退出 thread，也不表示角色被删除或由身份卡重新创建。

停用后，角色仍然属于原 thread，其身份、已经发生的消息、事件、委托与行为记录全部保留。角色曾经参与过什么、承担过什么责任以及产生过什么结果，不会因为停用而从完整记录中消失或被改写。

停用操作本身、停用期间发生的联系尝试和 Harness 的反馈也继续按照 Dreaming 9 进入完整 thread 记录。停用只改变角色从此刻起能否接收新的工作与产生新的调用资源，不改变历史事实来源的完整性。

本轮不讨论永久退出、删除、清除数据或匿名化等其他可能行为，也不能从停用规则推导这些行为存在。

## 停用期间不接收新的消息和委托

角色停用期间不接收新的普通消息或委托。无论是定向发送还是其他会把新内容交给该角色的方式，都不能绕过停用状态让它取得新的普通消息或形成新的委托责任。

其他角色尝试联系或向停用角色发布委托时，Harness 依据可客观确定的停用事实直接反馈目标角色已经停用，不调用该角色，也不依靠自然语言判断它是否愿意、是否暂时有空或是否适合当前工作。

Harness 的反馈不自动替发信者选择其他角色、转移已有委托或决定等待。联系尝试是否需要改发、另建委托或采取其他行动，由相关角色根据业务语义明确决定。

停用期间，Harness 不为该角色产生新的 Agent 调用资源。这里确认的是停用生效后不再开始新调用；停用发生时已经在途的调用怎样完成、中止或记录，本轮保持未决。

## 已有责任和等待事项不会自动处置

角色停用前已经存在但尚未结束的委托、等待事项和其他关系继续保留。停用不会自动取消、转移、拒绝、完成或结束这些事项，也不会让已有委托从完整记录中消失。

停用可能使某些工作暂时无法继续，但这只是相关角色需要处理的新事实，不是委托业务状态或责任变化。委托发布者、主持、目标角色或其他具备相应权力的角色，需要根据具体事项明确决定后续处理；Harness 不自行改派角色、取消委托或宣告失败。

如果停用角色仍是某项未结束委托的唯一目标角色，该责任关系不会仅因停用自动转移。未来应使用何种明确行为处理无法继续的责任，继续遵守 Dreaming 10 的未决边界，本轮不新增转移机制。

审批等待、明确等待选择或其他等待事项在角色停用后怎样继续、解除或通知，也不由停用动作自动决定。

## 重新启用恢复同一个逻辑角色

具备相应 Thread 权限的平台用户可以重新启用停用角色。重新启用恢复的是原来的同一个逻辑角色，不会重新读取身份卡并创建一个新角色，也不会产生一个与旧角色并列的副本。

重新启用后的角色继续拥有自身身份、历史记录及未被其他明确行为改变的既有关系。停用期间保留的未结束委托与等待事项仍与这个同一角色相关，不需要因为启用而复制或重新创建。

重新启用后，角色可以在当前适用的角色权限、审批策略、资源预算和其他 Thread 配置范围内重新接收新的普通消息、委托与调用。重新启用本身不会自动处理积压事项、重投停用期间未送达的内容或改变待处理顺序。

停用期间新增了哪些 thread 上下文、重新启用后怎样获得必要信息、底层 session 是否延续，以及需要什么通知或确认，本轮不决定。

## 主持和主管理员标签必须先转交

主持与主管理员都是每个 thread 任意时刻必须各有一个承载角色的唯一系统标签。因此，当前承载主持或主管理员标签的角色不能被直接停用。

发起停用的平台用户必须先确保相应唯一标签职责已经通过当前有效治理方式明确转交给另一个符合标签资格且当前启用的角色，再停用原角色。主持标签仍只交给合格的 Agent 角色，主管理员标签仍只交给合格的用户角色；转交不能通过停用动作被隐式推断。

如果当前没有另一个合格且启用的角色，就不能完成原承载角色的停用。需要先使一个合格角色进入可承载状态并完成明确转交，Harness 不会自动创建角色、选择接任者或替平台用户完成交接。

Harness 只校验停用前置条件：原角色不再承载必须保持唯一且持续存在的主持或主管理员标签后，停用才可以生效。这里不决定交接内容、接任角色怎样获得上下文或标签转交本身如何实现。

这项结论只确立“停用承载唯一标签的角色之前必须先转交”的前置条件，不重新决定其他场景下由谁发起或批准标签转交，也不扩张平台用户在其他标签治理中的权力。

原角色重新启用后，不会因为过去承载过主持或主管理员标签就自动取回该标签。唯一标签当前归属继续保持，除非以后再次发生独立、明确且有效的转交。

## 其他系统标签的停用行为仍未决定

普通管理员标签不是唯一标签，未来还可能出现其他系统标签。它们在角色停用前是否必须移除、转交、保留或采取其他处理，本轮不决定。

不能把主持和主管理员的唯一性前置条件自动推广到所有标签，也不能因为普通管理员标签非唯一就推导其在停用期间一定保留或失效。每类标签的资格、唯一性与持续性要求需要以后分别讨论。

## 停用不同于其他不可用事实

角色停用是平台用户明确执行的可逆操作，不是 Harness 根据繁忙、审批等待或调用故障自行推导的状态。

Dreaming 19 的审批等待、Dreaming 20 的繁忙和 Dreaming 26 的调用能力受阻都有各自的客观原因与影响范围；它们不会自动触发角色停用。反过来，停用也不会被解释为角色拒绝委托、能力不足或 Agent 调用故障。

Harness 只依据已经生效的平台操作反馈角色停用事实，不理解平台用户为什么停用，也不评价该决定在业务上是否合适。

## 这项共识暂时不意味着什么

- 不意味着主持、主管理员、管理员或其他角色可以凭 thread 内身份停用或重新启用角色。
- 不意味着停用等于角色退出 thread、被删除或由身份卡重新创建。
- 不意味着停用会删除、改写或降低历史消息、事件、委托与行为记录的完整性。
- 不意味着停用角色可以继续接收新的普通消息、委托或产生新的调用资源。
- 不意味着停用会自动取消、转移、拒绝、完成或结束已有委托与等待事项。
- 不意味着重新启用会创建新角色、复制责任、重投未送达内容或自动处理积压事项。
- 不意味着承载主持或主管理员标签的角色可以在未完成标签转交时直接停用。
- 不意味着 Harness 会自动选择接任者、创建合格角色或转交唯一标签。
- 不意味着本轮重新决定了其他场景下标签转交的发起权、批准权或完整流程。
- 不意味着普通管理员标签或其他未来系统标签已经有明确的停用处理规则。
- 不意味着已经决定底层 session 的保留、释放或恢复，以及停用时在途调用的行为。
- 不意味着已经决定启用后的上下文补齐、通知、权限粒度、UI、接口、协议、状态机、算法、模块或实现方式。
