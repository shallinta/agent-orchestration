# Dreaming 44：定时与心跳能力承载重复行为，不新增持续活动概念

日期：2026-08-27

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 43 确认定时提醒、监控、复盘和知识维护等既有行为在主持主动静默期间仍可继续。后续讨论中曾提出是否需要把这些行为统一抽象为一种新的“持续活动”。本次只讨论是否需要这个上位概念，以及定时触发面向 Agent 角色和用户角色时分别应表现为什么。

本次确认，不新增独立的“持续活动”领域概念。重复、延迟或周期性行为由定时任务、心跳检测等具有具体特点的能力承载；这些名称目前只是暂称，最终术语和相互边界留待后续根据实际特点决定。

定时目标为 Agent 角色时，到时触发 Agent 接收执行输入；目标为用户角色时，只发送普通消息或提醒通知，不生成 Agent prompt、不调用 Agent，也不创建委托。需要 Agent 先处理再通知用户时，先以 Agent 为目标，处理结果再通过普通消息送达用户。本次不决定创建权限、字段、工具、Cron 表达式、心跳周期、提示词、服务、消息渠道、UI、接口、协议、数据结构、状态机、模块或实现。

## 不为重复行为增加统一上位实体

定期复盘、持续监控、报警、知识维护和提醒，在业务目的、触发方式、目标角色、输出和停止条件上可能完全不同。仅因它们会重复发生，就建立一套统一的“持续活动”概念，可能把具体能力重新包装成一个缺乏清晰用户价值的抽象层。

用户真正需要的是：能够明确安排何时再次唤起一个 Agent、何时向真人发送提醒、何时周期性检查 thread 状态，以及怎样查看、修改或停止已经安排的行为。定时任务和心跳检测等具体能力已经可以承载这些需求，不需要再让用户理解一层额外术语。

因此，本轮否定把所有长期或重复后续行为统一建模为“持续活动”的建议。将来如果实践证明存在多个具体能力都无法表达的共同用户问题，可以重新讨论；当前不因为追求概念对称而提前增加它。

## 定时任务与心跳检测是具体能力的暂称

`定时任务`可以暂时用来描述：在明确时间、周期或其他确定性时间条件到达时，把预先安排的信息发送给指定目标，以触发一次 Agent 行为或用户提醒。

`心跳检测`可以暂时用来描述：按一定节奏唤起指定 Agent，检查 thread 中是否出现需要关注、判断或推进的变化。它强调周期性检查，而不预设每次检查一定产生外部动作。

这两种描述只帮助保存当前产品想法，不表示已经决定它们必须是两个独立产品实体、共享或不共享同一机制、采用什么字段，或者最终继续使用 CronJob、Heartbeat、定时任务、心跳检测等名称。

进展快照检查点、知识维护触发、委托截止提醒、监控报警和普通定时提醒，未来可能使用相同的底层定时或事件能力，也可能具有不同的专用行为。本轮不把底层复用可能性反向推导成统一产品概念。

## Agent 目标接收执行输入

当定时任务或心跳检测以 Agent 角色为目标时，到达触发条件后，Harness 向该 Agent 角色发送本次预先安排的执行输入，并清楚说明这次输入来自定时任务或心跳检测，使 Agent 能够结合对应目的和当前上下文作出响应。

定时输入可以用于提醒 Agent 生成复盘、检查指标、维护知识、查看待办、判断是否需要报警，或执行其他已经获得授权的工作。Agent 的实际行动继续受角色权限、审批策略、资源预算、可用状态和当前有效治理要求约束；定时到达不会绕过这些边界。

定时触发本身不是委托。它不会自动产生委托发布者、唯一目标角色责任、验收属性或委托状态。被唤起的 Agent 如果判断需要把工作交给另一个 Agent 持续跟踪，仍需按照 Dreaming 41 由具备权限的 Agent 角色明确发布委托；Harness 不从定时内容自动推导委托。

定时输入也不会因为送达 Agent 就自动成为新权威目标。它只执行此前已经安排的触发行为；目标形成和确认继续遵守现有治理规则。

## 用户目标只接收普通消息或提醒

当定时任务的目标是用户角色时，到达时间后向该角色发送普通消息或提醒通知。用户角色不需要接收 prompt，也不会因此产生 Agent 调用、委托责任、拒绝或完成动作以及委托验收。

例如，“明天下午提醒主管理员查看最终文档”可以直接以主管理员用户角色为消息目标，不必先唤起主持再让主持机械转发。这减少不必要的 Agent 调用和成本，也保持提醒行为与 Dreaming 41 的 Agent-only 委托边界一致。

定时提醒送达用户角色时，仍遵守 Dreaming 9 的消息路由与通道边界：thread 完整记录保留触发和消息事实，用户角色的外部消息通道只收到定向给它的内容，不因此获得完整 thread 历史。

用户收到提醒后可以回复、作出治理决定或提出新要求。这些后续行为继续按照普通消息、目标确认、审批和其他既有规则处理，不会因为起点是一条定时消息就产生特殊权力或生命周期。

## 需要处理后再通知时先触发 Agent

有些提醒不是转发一段固定文字，而是需要先查询最新数据、分析 thread 状态、形成摘要、判断是否异常或生成个性化内容。此时定时任务应先以合适的 Agent 角色为目标，让 Agent 完成所需处理，再通过普通消息把结果或通知发送给用户角色。

这条路径中的 Agent 处理和用户通知是两个角色适配不同的行为：前者触发 Agent 理解与执行，后者向真人送达普通消息。不能为了界面上看起来只有一个“定时提醒”，就把用户角色伪装成 Agent prompt 的接收者。

Agent 是否必须通知用户、通知哪些内容和对象，可以来自已经明确安排的输入、当前治理要求或 Agent 对上下文的语义判断。Harness 负责执行明确路由，不自行理解分析结果后决定应通知谁。

## 定时行为独立于目标完成和主动静默

已经创建并仍然有效的定时任务或心跳检测，不会因为当前权威目标完成、暂无新目标或主持进入主动静默而自动停止。

主动静默只限制主持自行扩张新方向。定时触发到达后，Harness 继续按既有安排唤起 Agent 或向用户发送提醒；Agent 只处理触发所要求的工作，事件结束后如果没有主管理员新输入，主持继续遵守 Dreaming 43 的主动静默边界。

如果定时行为已经失去意义，需要按照其自身能力提供的明确方式修改、暂停、关闭或删除。主管理员一句泛化的“不需要后续动作”不会让 Harness 猜测哪些定时行为应该停止；具体用户操作和权限留待以后讨论。

定时行为也不自动绑定某一权威目标。它可以服务于一个目标、跨越多个目标或只承担独立提醒；是否仍然有价值由角色和用户判断，不由 Harness 从目标状态推导。

## 触发与结果都进入完整记录

定时任务或心跳检测的创建、修改、停止、触发、目标送达以及可确认的执行结果或提醒结果，都属于 thread 生命周期中应当保留的事件与信息。

完整记录使角色和平台用户能够追溯为什么某次 Agent 被唤起、为什么用户收到了提醒，以及此前安排后来怎样变化。记录发生过什么不等于证明定时内容正确、执行结果可靠或提醒有价值；这些仍可能需要角色判断和事实核实。

如果一次触发因为目标角色停用、不可用、调用故障、消息通道失败、权限或预算限制而无法按预期完成，Harness 应保留可确认的失败或受阻事实。具体重试、补发、错过时间后的处理和恢复规则留到后续讨论。

## 延后设计线索

讨论中提出了一条可供设计阶段参考、但尚未成为实现决定的思路：Harness 运行 CronJob 类服务；具备相应能力的角色通过工具写入定时任务记录；记录包含时间安排、目标和需要在触发时传递的信息；时间到达后，服务把记录交回 Harness；Harness 根据目标角色类型发送输入，并在 Agent 目标场景附加定时任务或心跳特定的提示内容。

OpenClaw 以及其他 Agent 产品中的定时任务和心跳能力可以作为后续调研参考。当前未核验其具体架构，也不把任何外部产品的现有实现自动视为本项目方案。

本线索只保存“未来可从哪里开始试验”的想法，不决定是否运行独立服务、由谁创建记录、记录字段、工具契约、调度方式、错过执行处理、提示词拼接、会话恢复或其他技术实现。

## 对既有共识的细化

本轮继续保留 Dreaming 13 和 Dreaming 15 的确定性触发边界：Harness 可以在明确时间、事件或数量条件到达时发出请求，但不替 Agent 生成语义快照或维护知识。定时与心跳能力可以成为触发来源，不会改变快照和知识检索层各自的产品语义。

本轮也细化 Dreaming 43 对长期监控、复盘、知识维护和提醒的讨论：这些行为不需要统一升级为新的“持续活动”概念，可以由具体定时或心跳能力承载。Dreaming 43 结尾提出的“持续责任怎样被暂停、调整和结束”应理解为具体定时任务、心跳、委托或其他既有能力分别怎样管理，而不是设计一个新的通用持续活动生命周期。

Dreaming 41 继续有效。定时触发面向用户角色只产生普通消息或提醒；面向 Agent 角色产生一次 Agent 执行输入，但两者都不会自动成为委托。

## 这项共识暂时不意味着什么

- 不意味着需要新增名为“持续活动”的领域概念或统一生命周期。
- 不意味着 CronJob、Heartbeat、定时任务和心跳检测已经成为最终术语。
- 不意味着定时任务与心跳检测已经确定为两个独立实体或必须共享同一机制。
- 不意味着所有重复行为都必须使用同一种触发能力。
- 不意味着定时触发面向 Agent 时会自动创建委托或新权威目标。
- 不意味着定时触发面向用户时会调用 Agent、生成 prompt 或产生委托责任。
- 不意味着所有用户提醒都必须经过主持转发。
- 不意味着需要处理数据的提醒可以绕过 Agent 直接让 Harness 理解业务内容。
- 不意味着主动静默、目标完成或暂无目标会自动停止已有定时行为。
- 不意味着定时任务天然绑定单一权威目标。
- 不意味着角色或平台用户已经获得任何尚未讨论的创建、修改或停止权限。
- 不意味着已经决定字段、工具、Cron 表达式、心跳周期、提示词、调度服务、错过执行、重试、补发、通道、交互、UI、接口、协议、数据结构、状态机、模块或实现。

定时任务与心跳检测在用户使用上是否需要明确区分，以及各自最小需要表达哪些信息，留给后续 Dreaming 继续讨论。
