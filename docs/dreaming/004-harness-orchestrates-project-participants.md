# Dreaming 4：Harness 调度的是项目参与者

日期：2026-08-12

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论身份资料卡所代表的对象，以及 Harness 在协作中实际面对和调度的基本单位。不讨论资料卡字段、权限模型、调度算法或具体协作流程。

## 对前一轮理解的扩展

身份资料卡不是 Agent 产品描述，也不只描述一个带有具体模型、插件、记忆和环境的数字 Agent。

它描述的是一个参与项目协作的身份。这个身份可以被理解为项目协作者、参与者、员工、伙伴、顾问、专员或其他符合具体场景的角色。

身份背后的实际主体可以是：

- 数字人：Agent 加上具体模型、配置、插件、记忆、环境和调用方式；
- 真实用户：真人加上其在项目中的身份，例如老板、产品经理、编辑或审批人；
- 未来可能接入的系统平台：例如以“仓管员”身份参与、负责保存和提供产物的 GitHub。

系统平台也可能由 Agent 通过 skill 或 plugin 间接操作，因此这种参与者形态目前只是远期启发，不代表已经确定独立的系统参与者类型。

## 共同确认的关键抽象

项目协作与底层 Agent、真人用户或外部系统之间，需要增加一层统一的“项目参与者”抽象，并以身份资料卡表示。

Harness 在一个 thread 中实际调度和协调的是项目参与者，而不是直接调度抽象的 Agent 产品或用户账号。谁可以参与、适合做什么、应当如何与其协作等判断，都以该参与者的身份资料卡为依据。

可以把关系暂时表达为：

```text
底层主体（数字 Agent / 真人 / 未来可能的系统）
                    ↓
          身份资料卡所表示的项目参与者
                    ↓
           参与 thread 中的协作与调度
```

这层抽象是同一 thread 中多 Agent 与真人共同参与的关键基础。对 Harness 而言，真人不是临时插入流程的例外；只要以身份资料卡进入协作，真人和数字 Agent 都是项目参与者。

## 由此产生、尚未单独确认的理解

同一个底层主体在不同项目中可能具有不同身份。例如同一个真人在一个 thread 中是老板，在另一个 thread 中是编辑；同一个 Agent 配置也可能在不同协作中承担不同角色。

反过来，名称相同的身份也不一定对应同一个主体。两个项目都可以有“代码评审员”，但它们背后可能是不同的 Agent 或真人。

这提示身份与主体可能不能简单混为一谈。身份资料卡或许需要首先表达“这个参与者在当前协作中是谁、如何参与”，而不只是回答“底层调用的是哪个 Agent 或账号”。身份、主体以及两者之间是否一一对应，尚未形成共识，需后续继续讨论。

## 这一抽象带来的远期可能性

统一参与者抽象使项目未来不只能够支持单用户与多 Agent，还可能支持：

- 多个真实用户与多个 Agent 同时参与一个项目；
- 编辑部中多级真人编辑与多个 Agent 共同完成一本书的审查、校对和修订；
- 跑团、游戏或狼人杀等场景中，真人与多个数字 NPC 一起交互或协作；
- 外部系统以具有职责的项目身份参与并提供能力。

这些例子用于检验抽象的延展性和保存长期灵感，不构成近期功能范围。

## 关于项目名称的旁注

如果 Harness 最终编排的是广义项目参与者，`agent-orchestration` 这个名称可能无法覆盖全部长期方向。目前不因此改名，也不让命名问题干扰核心 Harness 能力的讨论；待项目本质更加清晰后再重新审视。

## 这项共识暂时不意味着什么

- 不意味着数字 Agent、真人和系统拥有完全相同的能力、在线状态或调用方式。
- 不意味着三者必须共用完全相同的权限和执行协议。
- 不意味着身份资料卡中的所有描述都是客观、完整或永久有效的。
- 不意味着身份资料卡已经是具体的数据结构或配置文件。
- 不意味着 Harness 只凭资料卡就能做出正确调度；资料卡提供决策依据，但如何判断仍未讨论。
- 不意味着上述远期场景会进入近期版本。

“项目参与者与底层主体如何关联”“一个参与者在 thread 中如何存在”“身份资料卡为协作提供哪些信息”，都留给后续 Dreaming 分别讨论。
