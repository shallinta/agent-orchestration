# Dreaming 34：主持自主选择已有角色并显式报告能力阻塞

日期：2026-08-26

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 33 已经确认主持需要形成足以推进当前阶段的安排。本次继续讨论：主持怎样在 thread 已有角色中选择委托对象，以及没有合适角色时怎样继续推进。

本次确认，在适用的权限、审批和预算边界内，选择哪个已有角色承担具体工作，默认属于主持的语义协调职责，不需要 Harness 计算统一的“最佳角色”。当现有人才范围确实无法推进时，主持必须区分暂时不可用与能力缺口，并采用当前配置允许的处理方式。

本次不决定角色评价字段、选择算法、排序模型、人才推荐、申请格式、等待机制、阻塞状态机、通知、UI、接口、协议、数据结构、模块或实现。

## 主持默认在已有角色中自主选择

主持根据当前阶段的工作需要，在 thread 已有角色中判断谁适合承担具体工作。判断可以综合身份卡所表达的专长、特征、成本、速度和质量倾向，以及该角色进入 thread 后已经形成的上下文、历史表现、当前工作关系与其他相关信息。

主持还需要考虑 Harness 能够提供的客观运行事实，例如角色是否启用、是否正等待审批、当前并发能力是否已被占用，以及适用的角色权限、审批策略和资源预算。

这些信息共同帮助主持作出选择，但不会产生一个脱离场景、永久有效的角色排名。同一角色可能适合某项工作而不适合另一项工作；同一张身份卡在不同 thread 中产生的角色，也可能因为上下文和已有成果不同而得到不同选择。

## Harness 提供事实和边界，不判断谁最合适

Harness 可以向主持提供已有角色、身份卡资料、客观可用状态和当前约束，并确定性执行消息路由、委托、权限、审批与预算规则。

理解工作需要、比较角色能力、权衡质量速度成本、判断一个角色是否足够合适，以及决定主持能否亲自承担，都是主持的语义判断。Harness 不读取这些内容后自动打分、推荐或改派角色，也不把“当前空闲”等同于“业务上合适”。

主管理员可以在 thread 协作中提出分工要求、排除某种选择或纠正主持判断；具备相应 Thread 权限的平台用户也可以通过角色权限和其他配置形成确定性约束。但在没有额外审批要求时，主持对已有角色的日常委托选择不默认逐次等待主管理员确认。

## 没有合适角色时先区分两种情况

“当前不能立即交给某个角色”可能来自两类不同原因：

1. 已有合适角色，只是正在执行其他工作、等待审批或因其他客观运行事实暂时不能开始相关工作。
2. 当前已有角色中没有适合承担这项工作的角色，形成了真正的人才能力缺口。

前一种情况不等于 thread 缺少这种能力。主持可以选择其他合适角色，也可以等待原角色恢复到能够承担或开始相关工作的状态；既有规则允许某些繁忙角色先接收待处理委托时，本轮不改变该行为。

后一种情况不能靠无限等待已有角色自然解决，也不应为了表面继续推进而明知不合适地强行分派。

## 引入新角色申请由 Thread 配置控制

如果 Thread 配置允许主持提出引入新角色申请，主持发现人才能力缺口时，可以按照既有治理规则向主管理员说明需要怎样的新角色以及原因。

提出申请只是一项 thread 内治理请求，不会自动批准申请、选择身份卡、创建角色或赋予权限。后续是否引入以及怎样完成平台层操作，继续遵守既有治理和平台权限边界。

这修正了 Dreaming 8 中“主持发现缺少合适角色时默认向主管理员申请引入”可能形成的无条件理解：主持是否拥有提出这类申请的能力，由具备相应 Thread 配置权的平台用户设置，不是主持标签天然附带的无限权力。Dreaming 8 原文保留，相关理解以本记录为准。

## 不允许申请时的推进顺序

如果当前配置不允许主持提出引入新角色申请，主持仍应先利用现有人才范围：

- 已有合适角色只是暂时不可承担或开始工作时，可以等待其恢复，或选择另一名合适角色。
- 主持自身具备相应能力，并且行动满足角色权限、审批策略和资源预算时，可以亲自执行这项工作。
- 没有合适的已有角色，且主持也不能负责任地亲自执行时，主持必须向主管理员明确报告能力阻塞，并等待主管理员决定。

能力阻塞报告不是变相的新角色申请，也不会绕过“不允许主持提出引入申请”的配置。它只是如实说明：依靠主持当前被允许使用的人才范围和自身能力，无法可靠推进这部分工作。

主管理员可以据此决定是否接受等待、调整推进方式、修改目标，或推动具备相应平台权限的用户改变配置或引入角色；这些后续选择不在本次统一规定。主持不能用静默等待掩盖能力缺口，也不应在明知自己无法胜任时强行执行。

## 能力阻塞是语义结论，不是 Harness 可自动推导的状态

Harness 可以知道角色停用、审批等待、并发占用、权限不足或预算受限等客观事实，但它不能仅凭这些事实判断“现有角色都不合适”或“主持能够胜任”。

因此，能力阻塞是主持结合工作内容、角色资料、已有上下文和客观约束作出的语义结论，并通过 thread 消息明确报告。Harness 负责记录和传递这项报告，不自行生成、否定或解除它。

如果后来有角色恢复、配置变化、目标调整或新角色加入，主持可以基于新事实重新判断并继续推进；这不需要把此前如实作出的能力阻塞报告视为错误。

## 这项共识暂时不意味着什么

- 不意味着 Harness 会为角色建立通用能力排名、评分或推荐算法。
- 不意味着空闲角色天然比繁忙角色更适合，也不意味着角色繁忙就构成人才缺口。
- 不意味着主持选择每一个已有角色前都要取得主管理员批准；是否审批由既有策略决定。
- 不意味着主持可以绕过角色权限、审批策略或资源预算进行委托或亲自执行。
- 不意味着允许提出新角色申请就等于允许主持自主创建或引入角色。
- 不意味着能力阻塞报告本身会修改配置、增加角色、改变目标或产生批准。
- 不意味着禁止申请新角色时，主持只能无限等待或必须勉强自行执行。
- 不意味着已经决定角色资料字段、评价方式、选择与推荐算法、申请内容、等待条件、阻塞状态、提醒、UI、接口、协议、数据结构、状态机、模块或实现。

主持选定角色后，一项委托需要向目标角色提供多少背景和工作上下文，才能让它可靠地开始工作，留给后续 Dreaming 继续讨论。
