# Dreaming 12：Thread 的生命周期可以跨越权威目标

日期：2026-08-20

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论权威目标完成与 thread 正式结束之间的关系、目标如何在 thread 内演进，以及谁能提议目标完成、确认目标完成和正式结束 thread。

本次不设计结束按钮或其他 UI，不讨论状态枚举、保留期资源、会话维持、目标历史结构、重设目标流程，以及 thread 结束后的只读、恢复或归档行为。

## 目标完成与 Thread 结束是不同动作

当前需要明确区分三个动作：

1. 主持可以根据目标和成果，提议当前权威目标已经达到、预期成果已经完成。
2. 主管理员在 thread 内作出语义治理判断，确认当前权威目标已经达到、成果可以接受。
3. 具备相应 Thread 权限的平台用户，可以通过平台操作正式结束 thread。

三者不等同。主持提出完成建议，不会自动完成目标或结束 thread；主管理员确认目标和成果，不会自动结束 thread；平台用户正式结束 thread，也不是在替主管理员判断成果质量。

正式结束是低频且简单的平台操作，当前只需要由具备相应 Thread 权限的平台用户手动执行。暂不考虑通过配置自动结束 thread；平台用户也可以选择一直不执行正式结束。

## 当前目标完成不会自动结束 Thread

当前权威目标完成后，thread 可以继续保留。用户可以继续查询既有历史信息，长期跟踪相关工作的未来发展，或者继承 thread 已有上下文，继续讨论并确认新的权威目标。

保留期间不强制要求 thread 必须没有活跃目标或活跃工作。角色既可以只查询历史，也可以继续发送消息或发布、处理委托；这些活动是否必须先形成一个新的权威目标，目前不作强制要求。

因此，目标生命周期与 thread 生命周期相互分离。一个 thread 可以先后经历多个权威目标，也可以在某个目标完成后进入一段保留期或没有活跃工作的阶段；这些阶段的准确状态名称和边界尚未决定。

## 权威目标演进属于 Thread 内语义治理

权威目标的提出、讨论、设置、更新、替换和完成确认，都是 thread 内的语义治理活动。所有角色都可以参与提出、质疑和完善目标；主持负责组织讨论、提示需要确认的时刻；主管理员最终确认当前权威目标及其变化，并确认目标是否已经达到、成果是否可以接受。

这些行为不是平台用户修改 Thread 配置。它们由 thread 内角色按照治理关系完成，与 Dreaming 9 已确认的平台配置权边界保持分离。平台用户拥有相应 Thread 权限，也不会因此自动取得主管理员在 thread 内的目标确认权。

## 新旧目标关联性不由 Harness 强制判断

Harness 不限制新目标必须与旧目标具有怎样的关联。新旧目标关系是否过弱、继续复用当前 thread 是否会带来问题，都是语义判断，不能由确定性 Harness 判定。

如果主持判断新目标与既有协作关联较弱，可以在 thread 内提醒用户考虑新建 thread。这种提醒来自主持角色的语义判断，不由 Harness 本身或平台入口依据固定规则自动产生，也不构成强制切分要求。主管理员决定是否仍在当前 thread 内确认新目标；如果选择新建 thread，则由具备相应权限的平台用户执行创建操作。

上下文污染、既有角色职责与新目标错位，是复用 thread 可能带来的风险。主持可以根据实际语义提醒这些风险，但不能把它们固化成一条由 Harness 自动执行的切分规则。

## Thread 的切分权仍属于用户

用户继续决定哪些工作放在同一个 thread、哪些工作拆成新的 thread。主持可以给出建议，Harness 可以承载和呈现这些建议，但不能强制用户采用某种切分方式。

这里所说的 Harness 提供建议，是指主持通过 Harness 给出语义建议，不表示 Harness 固定程序会自行判断目标关联性。这个细化与 Dreaming 11 的确定性职责边界一致。

## 对 Dreaming 6 的修正

Dreaming 6 把 thread 严格描述为一项围绕共同目标和预期成果、有开始也有结束的有界协作。当前更准确的定义是：thread 是由用户划定边界的持续协作上下文，可以跨越多个连续的权威目标，也可以包含目标完成后的保留期。

Thread 仍然不等同于一个聊天会话，也不按天、周或其他固定时间段自动划分；它也不必然等同于整个项目。边界仍由用户决定，但不再由单一目标的完成自动决定。

这一结论明确修正并覆盖 Dreaming 6 中将 thread 边界严格绑定于一项有开始、有结束的有界协作及其目标的理解。Dreaming 6 原文作为当时认识保留，不回写；从本记录开始，以持续协作上下文和独立生命周期的定义为准。

## 与 Dreaming 11 的语义边界一致

Harness 不判断权威目标是否完成，也不判断新旧目标是否足够相关，更不会因为目标完成、没有活跃委托或其他客观事实而自动结束 thread。

主持和主管理员分别承担完成提议与完成确认的语义责任；具备相应 Thread 权限的平台用户只在获得明确意愿后执行正式结束或新建 thread 等平台操作。Harness 负责执行明确操作，不替任何一方推导意图。

## 这项共识暂时不意味着什么

- 不意味着已经设计 thread 的关闭按钮、页面交互或 API。
- 不意味着存在或需要配置任何自动结束能力。
- 不意味着已经决定 thread、目标、保留期或无活跃工作的状态枚举与转换。
- 不意味着已经决定保留期是否继续占用 Agent 会话、运行资源或其他能力。
- 不意味着已经决定多个权威目标的历史如何记录、关联或展示。
- 不意味着已经决定新目标如何重设、确认或形成具体流程。
- 不意味着已经决定 thread 正式结束后是只读、可恢复、可重开、可归档，还是具有其他行为。
- 不意味着 thread 保留期间必须没有活跃目标、消息或委托。
- 不意味着角色必须先确认新目标，才能继续查询、发送消息或处理委托。
- 不意味着主持关于上下文污染、角色错位或新建 thread 的建议会成为 Harness 固定规则。
- 不意味着一个 thread 必须等同于整个项目，或必须与整个项目分开。

正式结束的具体操作、目标与 thread 的状态表达、保留期间的资源行为、目标历史、目标重设流程，以及结束后的行为，留给后续 Dreaming 或设计阶段继续讨论。
