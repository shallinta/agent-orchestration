# Dreaming 50：Harness 承载 Thread 协作事实，客户端只是能力不等的访问入口

日期：2026-08-31

状态：当前阶段共识，可继续修正

## 这次只讨论什么

用户最初希望先跑通不依赖前端 UI 的 Harness 核心，之后可以接入 Electrobun、网页、飞书、Telegram 或其他入口。本次只讨论：thread 的协作事实与行为归属于谁，以及不同 UI、API 和消息 Channel 是否必须提供相同能力。

本次确认，thread 的消息、角色、目标、委托、治理关系、配置、事件和其他协作事实由 Harness 统一承载，不归属于某个具体客户端。UI、API 和消息 Channel 是访问同一 thread 的不同入口，可以根据用途只提供部分能力，不要求功能对等。

本次不决定进程划分、通信协议、同步方式、缓存、离线行为、鉴权方案、客户端框架、API 形态、消息平台接入方式或其他技术实现。

## Thread 不属于某个 UI

Electrobun 配套 UI、未来可能存在的网页 UI、命令行入口或其他客户端，都不拥有一份独立的 thread。客户端关闭、更换或同时使用多个入口，不应改变 thread 身份，也不应重建角色、目标、委托和既有责任关系。

Harness 承载同一份持续协作事实。客户端可以读取获准看到的信息、提交获准执行的操作并展示结果，但不能因为自身界面、缓存或本地交互而产生一份与 Harness 并列的权威 thread 现实。

这使 Harness 可以在没有特定第一方 UI 持续运行的情况下维持协作。用户仍然需要通过某种获准入口创建、查看或操作 thread，但产品核心不以 Electrobun 或任何单一界面的存在作为 thread 成立与继续推进的前提。

## 不同访问入口可以提供不同能力

“可以更换或接入其他前端”不表示每个入口都必须复制配套 UI 的全部功能。

配套 UI 可以面向具备相应 Thread 权限的平台用户，展示完整记录、角色状态、委托、进展快照、知识视图和 Thread 配置。某个网页或其他客户端可以只覆盖其中一部分。飞书、Telegram 等用户角色 Channel 则可以主要承担定向消息送达、角色回复和少量明确交互，而不向该角色或真人开放完整 thread 历史与平台管理能力。

一个入口提供哪些能力，取决于它的产品用途以及使用者已经拥有的权限和身份关系。入口能力较少，不表示它访问的是一个缩水的新 thread；入口能力较多，也不表示它因此成为 thread 的事实来源或获得额外治理权。

## 同一 Thread 可以同时被多个入口访问

平台用户可以在配套 UI 查看完整记录，同时让主管理员用户角色通过飞书接收定向消息；其他平台入口或用户 Channel 也可以在符合权限与路由规则时并存。

这些入口处理的是同一 thread 中的事实与行为。某个入口提交的有效操作进入 Harness 后，其他有权入口随后看到的是同一协作现实中的变化，而不是在各自客户端内维持互不相关的副本。

本轮只确认多入口共享同一 thread 的产品行为，不决定实时同步、一致性、冲突、重复提交、离线编辑或客户端缓存怎样处理。

## 入口不会改变行为主体和权力来源

访问入口回答“通过哪里进行操作”，平台用户、用户角色和 Agent 角色回答“谁在以什么身份行动”，Thread 权限、角色权限和系统标签回答“它能够做什么”。这些问题不能因使用同一个界面或消息平台而合并。

同一个真人可能在配套 UI 中以平台用户身份修改 Thread 配置，也可能通过飞书以主管理员用户角色确认权威目标。即使背后是同一个人，两项行为的主体、权力来源和产品语义仍然不同。

客户端不能因为能够展示一个按钮、发送一条消息或调用一个入口，就创造平台用户权限、角色权限或 thread 内治理权。Harness 仍按照已经确认的身份和权限边界处理有效行为；具体怎样证明入口背后的主体身份，留待后续设计。

## Channel 是部分访问入口，不是完整客户端的默认替代品

按照 Dreaming 9 和 Dreaming 46，飞书等 Channel 只把明确发给用户角色的消息送达该角色背后的真人，并接受该角色通过相应入口产生的回复或其他获准行为。消息是否送达、是否要求回复和平台用户能否查看完整记录仍是不同问题。

因此，把飞书或 Telegram 称为可接入入口，不会推翻既有的定向消息边界。用户角色通过 Channel 参与 thread，不会自动获得配套 UI 中完整记录、Thread 配置或平台管理能力；反过来，Channel 功能有限也不会让该用户角色变成 thread 外的临时访客。

未来某种第三方客户端也可能在满足相应身份与权限条件时提供更完整能力，但这不是所有消息 Channel 的默认要求，本轮也不决定这种扩展方式。

## 第一方 UI 是重要产品体验，但不是核心事实归属

配套 UI 可以成为平台用户理解和管理 thread 的主要体验，完整展示协作记录、进展、责任和配置。将 Harness 与具体 UI 解耦，不表示第一方 UI 不重要，也不表示所有用户都应通过底层接口或消息软件完成工作。

边界在于：第一方 UI 展示和操作 Harness 承载的 thread，而不是由 UI 自己拥有 thread；UI 的发布节奏、运行状态或技术框架也不应改变这一产品关系。

早期先验证纯 Harness 核心、之后再建设 Electrobun UI 是用户提出的推进方向，但本轮不把它收敛为版本范围或实现顺序，只确认产品核心不依赖某一个前端形态。

## 与既有共识的关系

Dreaming 9 已经区分完整持久化、定向送达、平台用户 Thread 权限和角色权限。本轮进一步确认，完整 thread 记录属于 Harness 承载的协作事实；配套 UI 是完整记录的一个展示和操作入口，外部消息 Channel 是定向消息入口。

Dreaming 11 的确定性边界继续有效。不同入口可以提交明确行为，但不会替 Harness 或角色作出语义判断；Harness 仍校验结构、身份与权限并执行确定性行为。

Dreaming 46 已经确认发给用户角色的消息沿其 Channel 分发，发送不等于要求回应。本轮不改变该规则，只把 Channel 放回多入口产品关系中：它连接同一 thread，但不因此拥有完整平台能力。

Dreaming 49 的领域无关核心同样适用于访问入口。软件开发或其他领域可以拥有专门客户端体验，但这些体验不会各自创造不同的 Harness 核心和 thread 事实。

## 这项共识暂时不意味着什么

- 不意味着所有 UI、API、命令行入口和消息 Channel 必须提供相同功能。
- 不意味着飞书、Telegram 等 Channel 默认可以查看完整 thread 历史或修改 Thread 配置。
- 不意味着配套 UI 不重要，或所有用户都应直接使用 API 与 Harness 交互。
- 不意味着客户端可以凭自身界面能力创造平台权限、角色权限或治理权。
- 不意味着同一真人通过不同入口采取的行为拥有相同主体语义。
- 不意味着 Harness 已经决定单进程、服务化、客户端—服务端或其他技术架构。
- 不意味着已经决定固定输入输出协议、API、事件流、同步、一致性、离线、缓存、冲突、重复提交或鉴权实现。
- 不意味着第三方客户端必须由本项目开发、托管或保证功能完整。
- 不意味着已经确定 Electrobun、网页或任何消息平台的版本范围和建设顺序。

不同入口最低需要提供哪些能力、用户怎样在入口之间连续操作，以及身份与权限如何安全映射，留给后续 Dreaming 或设计阶段讨论；不作为当前主线的自动下一问题。
