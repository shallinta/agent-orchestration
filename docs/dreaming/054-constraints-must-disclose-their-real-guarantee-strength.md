# Dreaming 54：约束必须公开其真实保证强度

日期：2026-08-31

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 18 把角色权限、审批策略和资源预算定义为自治程度的三项正交约束，Dreaming 53 又确认 Harness 不代理成熟 Agent 的全部原生工具。阶段性主线审计据此发现一个产品信任问题：如果 Harness 无法观察或阻止某项 Agent 原生行为，却仍把相关限制表达成确定有效的权限、审批或硬预算，会提高用户预期并制造虚假安全感。

本次只讨论：平台用户应当从一个约束表达中获得什么保证，Harness 是否需要把所有约束都建设成由自己强制执行，以及只能依赖 Agent 遵守的限制应当怎样被理解。

本次确认，约束的产品表达必须与实际保证能力一致。能够由 Harness 或明确的外部机制实际阻止的限制，可以作为强制约束；只能通过提示词、角色说明或协作规则要求 Agent 遵守的限制，必须明确表达为弱约束；Harness 无法覆盖的能力范围也要如实披露。产品不为了表面统一而强行接管所有 Agent 能力，也不能把弱约束包装成强制保证。

本次不决定沙箱、操作系统权限、Agent 配置、进程隔离、代理、凭证、计量、验证方式、约束 schema、保证等级名称、UI、协议、接口或其他技术实现。

## 实事求是比形式上的统一强制更重要

不同 Agent、调用边界和执行环境能够被 Harness 控制的程度不同。Harness 明确承载的消息、委托、审批、Channel 分发或其他公共协作能力，可以在行为真正发生前校验规则并阻止不允许的调用；Agent 自带的插件、文件操作、网络访问或外部服务能力，则可能完全由 Agent 或其运行环境掌握。

本项目不要求为了让所有限制看起来一致，就把全部 Agent 原生动作改造成 Harness 代理调用。这样做会推翻 Dreaming 53，重复成熟 Agent 的执行基础，并显著缩小可参与 Agent 范围。

但保留原生能力也不能成为模糊产品承诺的理由。当前能够强制多少就承诺多少，只能提示多少就明确说明只能提示；无法确定时不假装已经受控。用户预期应由真实保证形成，而不是由“权限”“审批”“硬限制”等看似安全的词语形成。

## 强制约束需要存在实际阻止能力

一项限制只有在不满足条件时能够被某个明确边界实际阻止，才具有强制保证。

Harness 直接提供和控制的公共协作能力，可以由 Harness 自己承担强制责任。例如角色无权发布委托时，Harness 可以拒绝创建委托；某项 Harness 外部连接能力需要审批时，在批准前可以不执行该连接；Harness 能够确定计量并控制的新调用到达硬预算时，可以拒绝继续发起。

强制能力也可能来自 Harness 之外，例如 Agent Runtime、操作系统、沙箱、远程服务端权限或其他能够实际阻止行为的边界。此时产品可以说明这项限制受到外部机制强制，但不应把保证来源冒充为 Harness 自身，也不应在没有可靠依据时宣称外部机制已经生效。

本轮只确认“能实际阻止”这一产品含义，不决定 Harness 怎样验证外部边界、什么证据足够可靠，或哪些机制可以被接受为强制保证来源。

## 提示词与角色说明形成弱约束

有些限制只能被写入主持职责、角色提示词、委托要求或其他自然语言规则，要求 Agent 自觉遵守。例如，Harness 无法限制某个 Agent 原生网络工具时，可以明确要求它不要访问某类服务，但提示本身不能保证 Agent 不会误解、忽略或违反要求。

这类限制仍有实际价值。成熟 Agent 通常会遵循清晰指令，弱约束也可以减少误操作并表达用户期望；本项目无需因为无法做到绝对阻止就放弃所有行为规则。

边界在于，弱约束必须被明确告知用户，不能与能够实际拒绝行为的强制约束使用相同保证措辞。提示词约束说明“Agent 被要求怎样做”，不证明“系统保证它只能这样做”。

弱约束被违反也不自动等于 Harness 的强制权限系统失效，因为它原本没有承诺实际阻止；但产品仍应如实保留已经知道的相关事实。是否以及怎样检测、提醒和处理违反行为，留待后续讨论。

## 未覆盖能力不能被默认算作安全

Harness 可能不知道某个 Agent 安装了哪些插件、持有什么外部凭证，或者无法判断其运行环境能否访问某项资源。这种能力不属于已强制约束，也不能仅因没有观察到相关行动就推断为安全。

平台用户需要能够知道某项约束覆盖哪些行为、由谁保证，以及哪些相关能力仍未覆盖。未覆盖不等于禁止、不等于允许，也不等于已经发生风险；它表示产品没有对该范围给出强制保证。

公开未覆盖范围可能降低用户对自动化安全性的预期，但这正是本轮选择的产品价值：宁可让用户看到真实能力边界并自行决定是否接受，也不通过模糊措辞提高信任。

## 保证强度属于具体约束范围，不是角色的一枚总标签

同一个角色可以同时受到不同保证强度的限制。它发布委托和发送 Harness Channel 消息可能受 Harness 强制约束；访问某个目录可能受外部沙箱强制；是否调用 Agent 自带的搜索插件则可能只有提示词弱约束；某些未知插件还可能完全未被覆盖。

因此，不能只把整个角色概括为“受控”或“不受控”，也不能因为角色有若干强制权限，就推断其所有原生能力都被强制管理。保证强度应当跟随具体限制和能力范围被理解。

本轮不决定最终需要几个等级、叫什么名称、以多细的粒度表达，或平台用户怎样查看。`强制约束`、`弱约束`和`未覆盖能力`只是当前用于说明核心区别的产品语言，不是已经确定的数据枚举。

## 强制保证不能静默降级

如果一项限制原本被表达为强制约束，但实际执行时发现必要的 Harness 或外部阻止边界不可用，产品不能静默退化为提示词要求并继续让用户以为原保证仍然成立。

具体应当阻止相关能力、报告保证不可用、要求平台用户重新选择，还是采取其他行为，本轮不决定；但变化必须公开，用户必须有机会根据真实保证重新判断是否继续。透明公开不是一次性的产品说明，而是约束实际保证发生变化时仍然成立的责任。

反过来，一项弱约束以后获得了可靠强制边界，也可以明确提升保证强度，但不能仅凭 Agent 多次遵守提示就推断它已经成为强制约束。

## 对既有自治与预算共识的修正

Dreaming 17 所说的预算强制边界，继续适用于 Harness 能够确定性计量并控制的新资源消耗。Agent 通过 Harness 无法计量或阻止的原生能力产生的成本，不会因为 thread 配置了预算就自动受到同等硬上限保证；产品必须公开预算覆盖范围，而不是把可见预算描述成角色全部真实消耗的总保证。

Dreaming 18 的角色权限、审批策略和资源预算仍然共同形成自治程度，但本轮进一步限定：三项约束只有在各自明确覆盖的行为范围内，才产生相应保证。一个角色在 Harness 公共协作能力上受到强制审批，不表示其所有原生外部动作也自动被审批门禁覆盖。

因此，“角色不能绕过约束”的当前准确含义是：任何受某项强制约束明确覆盖的行为都不能绕过该约束；对于只存在弱约束或尚未覆盖的原生能力，产品不能声称 Harness 已经提供同等强制保证。这一认识细化并覆盖 Dreaming 17、18 和 53 中可能形成的全局强制理解，旧记录保持原文。

## 与既有共识的关系

Dreaming 11 要求 Harness 只执行确定性规则。本轮进一步确认，无法被确定执行的提示词要求不能伪装成 Harness 强制规则。

Dreaming 17 已经把预算限定在 Harness 能够确定性计量和比较的资源范围，本轮补足对用户的保证表达：无法计量或控制的 Agent 原生成本属于未覆盖范围。

Dreaming 18 的三项正交约束继续有效，但自治程度不能掩盖每项真实约束的覆盖范围与保证强度，正如自治预设不能掩盖底层真实配置。

Dreaming 53 确认 Harness 不代理 Agent 全部工具。本轮使这条边界与治理约束能够共存：不要求全部代理，但必须公开哪些约束是强制、哪些是弱约束、哪些能力尚未覆盖。

## 这项共识暂时不意味着什么

- 不意味着 Harness 必须强制控制 Agent 的全部文件、网络、插件、工具和外部服务能力。
- 不意味着只能通过提示词表达的行为要求没有价值，或不应提供。
- 不意味着弱约束可以使用与强制权限、审批或硬预算相同的保证措辞。
- 不意味着配置了一项角色权限、审批策略或资源预算，就自动覆盖该角色全部原生能力。
- 不意味着未覆盖能力已经被禁止、已经被允许、已经发生风险或已经安全。
- 不意味着外部强制机制不能提供可靠保证，只是必须如实说明保证来源和覆盖范围。
- 不意味着整个角色只能拥有一种统一的保证等级。
- 不意味着已经确定保证等级名称、数量、粒度、默认值、展示方式或验证方法。
- 不意味着强制约束失去必要边界时可以静默降级为提示词约束。
- 不意味着已经决定沙箱、操作系统权限、Agent 配置、代理、凭证、计量、检测、UI、接口、协议或实现。

平台用户在创建或调整角色时最低需要看到哪些保证信息，弱约束被违反后如何处理，以及哪些高风险能力应当只允许强制约束，留给后续根据真实需要讨论；不作为当前主线的自动下一问题。
