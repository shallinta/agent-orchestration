# Dreaming 5：身份卡是模板，角色是 thread 内实例

日期：2026-08-12

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论身份卡、角色与 thread 之间的领域关系，以及角色之间为什么需要相互独立。不讨论这些概念未来以什么数据、模块或程序结构实现。

## 共同确认的领域关系

身份卡是长期保存、可以反复选用的角色模板，类似“人才市场”中的一份简历。它描述项目可能需要的一种身份，但自身不是正在参与项目的协作者。

当身份卡被加入一个 thread 时，才基于它产生一个属于该 thread 的角色。这个角色代表“该身份正在参与这一次协作”。

可以把这一关系概括为：

> 身份卡是可复用的角色模板；角色是该模板在一次 thread 中产生的独立实例。

## 每次加入都产生独立角色

同一张身份卡可以：

- 被不同 thread 分别使用；
- 在同一个 thread 中被使用多次。

每次加入都产生一个新的角色。即使它们来自同一张身份卡、使用相同名称，或背后使用同一种 Agent，它们仍是彼此独立的协作角色。

因此，两个公司的项目都可以有一个来自“资深架构师小明”身份卡的角色；同一个项目也可以同时加入两个来自这张身份卡的角色。如何在实际协作中区分同名角色，留到未来讨论。

## 底层主体不定义角色身份

项目当前不需要追踪或区分“底层实际是不是同一个主体”。对协作而言，一个身份实例就是一个角色。

同一种 Agent 可以被不同 Agent 身份卡使用，并在同一 thread 中产生不同角色。例如同一个 Agent 产品可以分别支持“程序员”和“绘图师”两个身份。它们在项目中承担不同职责，并维持彼此隔离、各自连续的工作上下文。

这种隔离避免把不相关工作混进同一角色的上下文。连续的代码工作不应因为中间穿插绘图任务而变得断裂；绘图工作也不应被无关代码信息持续占据注意力。它还可能减少不必要的上下文膨胀、压缩和消耗。

## 角色的生命属于 thread

角色从加入 thread 开始，在该 thread 中保持逻辑上的身份与工作连续性，并在 thread 结束时结束这次角色生命。

同一张身份卡以后再次被使用，产生的是新角色，而不是让旧角色跨 thread 继续存在。Thread 结束时可以把值得保留的记忆、经验或项目知识以知识库、文档或其他产物形式交给用户；如何在不同 thread 之间使用和管理这些内容，不属于本 Harness 的职责，也不能默认等同于延续整个旧角色。

这里确认的是角色在逻辑上的连续性，不要求底层连接或会话永远不发生变化。少见的运行中更换模型、调用端或会话异常，可以在未来根据实际需要降级处理，不在当前需求讨论中展开。

## 当前聚焦的身份卡与角色类型

近期需求思考只聚焦两类身份卡及其产生的角色：

- Agent 身份卡与 Agent 角色；
- 用户身份卡与用户角色。

系统平台作为角色是更远期的启发，当前不继续展开。

数字 Agent 与真人的交互方式不同，但都通过相应身份卡进入 thread，并成为其中的角色。如何消化它们在通信、等待、异常和会话方面的差异，属于后续设计问题。

## 这项共识暂时不意味着什么

- 不意味着已经决定身份卡或角色的数据结构。
- 不意味着角色必须是具有行为的程序对象，也不意味着它必须是纯数据。
- 不意味着已经决定谁负责创建、调用、恢复或销毁角色。
- 不意味着同名角色的区分方式已经确定。
- 不意味着用户不能在新的 thread 中主动使用旧有知识，只是跨 thread 管理不属于本 Harness 的职责，也不默认复活旧角色。
- 不意味着所有角色必须在 thread 开始时一次性加入，或必须始终保持活跃。

身份卡包含哪些协作信息、thread 本身代表什么、角色如何加入和离开协作，都留给后续 Dreaming 分别讨论。
