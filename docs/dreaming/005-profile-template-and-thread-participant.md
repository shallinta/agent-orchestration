# Dreaming 5：身份资料卡是模板，参与者是 thread 内实例

日期：2026-08-12

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论身份资料卡、项目参与者与 thread 之间的领域关系，以及参与者之间为什么需要相互独立。不讨论这些概念未来以什么数据、模块或程序结构实现。

## 共同确认的领域关系

身份资料卡是长期保存、可以反复选用的参与者模板，类似“人才市场”中的一份简历。它描述项目可能需要的一种身份，但自身不是正在参与项目的协作者。

当身份资料卡被加入一个 thread 时，才基于它产生一个属于该 thread 的项目参与者。这个参与者代表“该身份正在参与这一次协作”。

可以把这一关系概括为：

> 身份资料卡是可复用的参与者模板；项目参与者是该模板在一次 thread 中产生的独立实例。

## 每次加入都产生独立参与者

同一张身份资料卡可以：

- 被不同 thread 分别使用；
- 在同一个 thread 中被使用多次。

每次加入都产生一个新的项目参与者。即使它们来自同一张资料卡、使用相同名称，或背后使用同一种 Agent，它们仍是彼此独立的参与主体。

因此，两个公司的项目都可以有一名来自“资深架构师小明”资料卡的参与者；同一个项目也可以同时加入两名来自这张资料卡的参与者。如何在实际协作中区分同名参与者，留到未来讨论。

## 底层主体不定义参与者身份

项目当前不需要追踪或区分“底层实际是不是同一个主体”。对协作而言，一个身份实例就是一个参与主体。

同一种 Agent 可以被不同身份资料卡使用，并在同一 thread 中产生不同参与者。例如同一个 Agent 产品可以分别支持“程序员”和“绘图师”两个身份。它们在项目中承担不同职责，并维持彼此隔离、各自连续的工作上下文。

这种隔离避免把不相关工作混进同一参与者的上下文。连续的代码工作不应因为中间穿插绘图任务而变得断裂；绘图工作也不应被无关代码信息持续占据注意力。它还可能减少不必要的上下文膨胀、压缩和消耗。

## 参与者的生命属于 thread

项目参与者从加入 thread 开始，在该 thread 中保持逻辑上的身份与工作连续性，并在 thread 结束时结束这次参与生命。

同一张身份资料卡以后再次被使用，产生的是新参与者，而不是让旧参与者跨 thread 继续存在。跨 thread 值得保留的记忆、经验或项目知识由 Harness 另行管理，不能默认等同于延续整个旧参与者。

这里确认的是逻辑参与者的连续性，不要求底层连接或会话永远不发生变化。少见的运行中更换模型、调用端或会话异常，可以在未来根据实际需要降级处理，不在当前需求讨论中展开。

## 当前聚焦的参与者类型

近期需求思考只聚焦两类身份资料卡及其参与者：

- 数字 Agent；
- 真实用户。

系统平台作为参与者是更远期的启发，当前不继续展开。

数字 Agent 与真人的交互方式不同，但都通过身份资料卡进入 thread，并成为其中的项目参与者。如何消化它们在通信、等待、异常和会话方面的差异，属于后续设计问题。

## 这项共识暂时不意味着什么

- 不意味着已经决定身份资料卡或项目参与者的数据结构。
- 不意味着项目参与者必须是具有行为的程序对象，也不意味着它必须是纯数据。
- 不意味着已经决定谁负责创建、调用、恢复或销毁参与者。
- 不意味着同名参与者的区分方式已经确定。
- 不意味着跨 thread 完全不能复用知识，只是不默认复活旧参与者。
- 不意味着所有参与者必须在 thread 开始时一次性加入，或必须始终保持活跃。

身份资料卡包含哪些协作信息、thread 本身代表什么、参与者如何加入和离开协作，都留给后续 Dreaming 分别讨论。
