# Dreaming 1：人被迫填补 Agent 之间的协作空隙

日期：2026-08-12

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只尝试说清楚项目为何需要存在，不讨论 Harness 应该有哪些功能，也不讨论主 Agent、流程模型、版本范围或技术实现。

## 来自初始想法的事实

- 市面上已经存在能力很强的 Agent；项目的出发点不是重新开发一个通用 Agent。
- 不同 Agent 的能力结构不同。例如，有的 Agent 分析全面、质量高但执行较慢；有的 Agent 在得到充分方案和限制后执行很快，但独立进行方案设计或评审时可能更容易遗漏问题。
- 通过人工组合不同 Agent，已经可以获得不错的结果：让更全面的 Agent 负责方案与评审，让更快的 Agent 负责开发与返修。
- 这种组合没有真正释放人的时间。人仍需在 Agent 之间复制和改写信息、补充背景与限制、组织提示词、传递评审意见、跟踪进度并决定下一步。
- 用户希望从高频的协调劳动中抽身，但仍参与重要节点的判断和签字。

## 共同确认的核心问题

多个各有优势、已经足够有用的 Agent，目前无法自然地共同维持一段连续工作。为了让它们形成合作，人被迫填补它们之间的协作空隙。

这里的“填补空隙”不只是复制粘贴，还包括：

- 理解一个 Agent 的输出对整个需求意味着什么；
- 判断哪些内容需要交给另一个 Agent；
- 根据接收者的特点重新组织背景、目标、限制和期望结果；
- 维持跨多轮工作的上下文与当前进展；
- 判断何时继续、返工、暂停或由人作决定。

因此，项目最初要面对的不是单个 Agent 的智能上限，而是多个 Agent 之间缺乏可以持续承接工作的协作条件。

## 这项共识暂时不意味着什么

- 不意味着 Harness 必须接管上述全部工作。
- 不意味着人的参与越少越好。
- 不意味着协作一定要被建模为固定工作流、任务队列或对话。
- 不意味着减少转发成本就是项目唯一或最终的价值。
- 不意味着已经决定任何产品功能、角色分工、协议或架构边界。

“协作空隙具体由什么组成”“哪些应由 Harness 承担”“多个 Agent 的组合是否还应产生高于单 Agent 的群体能力”，都留给后续 Dreaming 分别讨论。
