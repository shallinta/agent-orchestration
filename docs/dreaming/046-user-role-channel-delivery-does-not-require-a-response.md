# Dreaming 46：用户角色消息发往所连 Channel，发送不等于要求回应

日期：2026-08-28

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 2 确认人应从持续协调者转变为关键判断者，Dreaming 9 确认完整 thread 记录与定向消息送达是不同问题，Dreaming 11 又确认是否需要用户判断属于角色的语义责任。本次只进一步讨论：信息在完整记录中可见、消息主动送达用户角色、以及用户是否被要求回应，三者之间是什么关系。

本次确认，发给用户角色的消息会发往该角色已经连接的通信 Channel，无论该角色是私聊接收者，还是包含在广播接收范围内。Harness 不再对消息是否重要、是否要求回复进行第二次语义筛选。

消息送达不自动产生回应义务。主持或其他相关角色可以向主管理员同步不需要回复的重要信息；主管理员背后的真人可以不回复或晚回复。只有发送者明确提出需要信息、判断、批准、确认或其他回应时，消息才表达回应期待；本轮不决定普通回应请求的结构、追踪与阻塞行为。

## 完整可见、定向送达与回应期待是三件事

完整记录回答“thread 中发生过什么”。Harness 持久化所有消息、事件和信息，具备相应 Thread 权限的平台用户可以通过配套 UI 查看完整记录，不要求每条内容都曾直接发送给自己的用户角色。

定向送达回答“哪条消息现在发给谁”。当一条私聊消息的接收者是主管理员或其他用户角色，或者一条广播消息的接收范围包含该用户角色时，Harness 按既有路由把该消息发送到角色已经连接的通信 Channel，例如飞书或 Telegram。用户角色未被列为接收者时，消息仍进入完整记录，但不会仅因存在于记录中而被额外推送给该角色。

回应期待回答“发送者是否需要接收者作出后续回应”。它不能从消息已经送达、消息看起来重要、接收者拥有主管理员标签或用户长时间没有回复等事实中自动推导。

因此，这三个层次不能互相替代：完整可见不等于已经定向送达，定向送达不等于要求回应，没有回应也不等于产生了任何治理结论。

## 发给用户角色就沿其 Channel 正常分发

用户角色的通信 Channel 是该角色接收 thread 定向消息的入口。Harness 已经明确知道一条消息的接收范围后，只需要按角色的既有连接执行分发，不再判断消息是否达到某种“值得打扰用户”的门槛。

这条规则同时适用于私聊和广播。广播不是只留在配套 UI 中的公共记录；只要主管理员角色属于广播接收范围，该条消息也会发往主管理员角色的 Channel。

这也修正了讨论中可能形成的一个误解：不需要另建一个由 Harness 决定是否启动的“主动打扰”流程。角色把消息明确发给用户角色，本身就已经表达了希望该角色收到这条消息；Harness 的职责是可靠分发，而不是再次理解内容并决定是否值得送达。

本轮只确认已有 Channel 的角色消息送达语义，不决定一个角色能连接几个 Channel、Channel 失效或发送失败时怎样处理、是否支持免打扰、摘要、合并通知或其他通道行为。

## 发送者承担是否占用用户注意力的判断

用户无需持续盯住完整 thread 记录，才能保证自己不会错过角色明确发给自己的消息。与此同时，普通进展和所有新事实也不应仅因发生就被无差别发送给主管理员。

是否把一条消息发给主管理员或其他用户角色，由主持或相关角色结合当前事项作出语义判断。需要人的权威、价值判断、风险接受或责任承担时可以发送；即使不要求用户采取行动，发送者认为某项重要事实值得同步时也可以发送。

用户预先明确订阅或安排的提醒、进展信息及其他消息，也可以按照既有明确规则送达。它们不需要由 Harness 在每次触发时重新判断是否重要。

发送者应避免把“用户可以查看完整记录”误解为必须让用户自行持续监控，也应避免把“消息可以通过 Channel 送达”误解为所有进展都应抄送用户。怎样判断具体信息是否值得同步属于 Agent 或真人角色的语义责任；Harness 不读取内容后替其决定。

## 重要信息可以只同步而不要求回复

向主管理员发送消息不只用于审批、目标确认、风险接受或其他必须回应的事项。主持和相关角色可以主动同步重要进展、风险现状、结果变化或其他值得主管理员知晓的信息，同时不要求主管理员立即回复。

主管理员背后的真人收到这类信息后，可以选择不回复，也可以稍后在认为合适时回应。没有回复不会自动表示主管理员同意、拒绝、确认、批准、接受风险、认可事实或放弃权利。

一条信息同步消息也不会因为用户后来回复，就追溯性地变成审批或目标确认。用户回复表达什么，继续依据该次明确发言或治理行为本身判断。

这使“让用户保持必要知情”与“每次都要求用户作出决定”能够分离。项目追求的是减少低价值协调和不必要回应，而不是禁止角色向用户同步不要求回复的重要信息。

## 需要回应时由发送者明确表达

如果发送者确实需要主管理员或其他用户角色提供信息、判断、批准、确认或其他回应，应当在消息或相应治理行为中明确表达这一期待，不能仅依赖“消息已经发给主管理员”让 Harness 或用户猜测。

普通消息默认不因为送达而产生回复义务。主管理员标签代表既有治理权，但不表示所有发给该角色的消息都自动成为审批请求，也不表示主管理员必须逐条回复。

明确要求回应是否需要独立产品概念、结构化行为或固定状态，本轮不决定。回应尚未到达时是否阻塞发送者、某项工作、相关委托或其他协作，也留待后续根据具体需要讨论；不能从本轮共识自动推出。

现有目标确认、目标完成确认和审批等已经具有治理语义的行为继续遵守各自规则，不能降级为“发过一条消息就视为完成”。主管理员的沉默仍不能替代明确确认或批准。

## Harness 只执行明确路由

Harness 可以确定一条消息的明确接收者、当前广播范围以及用户角色已经连接的 Channel，并按照这些事实执行消息分发和持久化。

Harness 不判断消息内容是否重要，不决定发送者是否应该联系主管理员，不推断接收者是否需要回复，也不从没有回复推导同意、拒绝或其他业务含义。需要语义判断时，由主持或相关 Agent、真人角色承担。

这延续 Dreaming 11 的边界：角色作出“发给谁、为什么发送、是否需要回应”的语义决定，Harness 对已经明确的消息执行确定性路由。

## 对既有共识的细化

本轮细化 Dreaming 2。人不再持续监控 thread，不等于角色不能主动向人同步信息；减少注意力负担的关键，是发送者有选择地联系用户，而不是限制只有需要审批的消息才能送达。

本轮也细化 Dreaming 9。配套 UI 中的完整记录与用户角色的外部 Channel 仍然分离；一条消息只要明确发给用户角色，就会发往其 Channel，而无需 Harness 再执行内容重要性判断。

Dreaming 11 继续有效。是否值得联系用户、是否需要回应，以及回应内容意味着什么都属于角色的语义判断；Harness 只执行明确路由与记录。

Dreaming 31 和 Dreaming 40 等治理边界同样保持不变。消息发送、用户沉默或普通回复，都不能替代权威目标确认、目标完成确认或其他要求明确治理行为的事项。

## 这项共识暂时不意味着什么

- 不意味着所有 thread 消息都会通过主管理员的 Channel 发送。
- 不意味着只有私聊会发往 Channel，或广播只在配套 UI 中可见。
- 不意味着 Harness 会根据重要性、紧急程度或回应期待过滤已经明确发给用户角色的消息。
- 不意味着只有需要回复、审批或确认的内容才能发给主管理员。
- 不意味着消息发给主管理员后，主管理员必须立即回复或一定要回复。
- 不意味着主管理员没有回复就表示同意、拒绝、确认或批准。
- 不意味着普通信息同步会自动变成审批、目标确认或其他治理请求。
- 不意味着已经决定普通回应请求的结构、追踪、等待、超时、催促、取消或阻塞行为。
- 不意味着已经决定多 Channel、发送失败、免打扰、消息摘要、合并通知、优先级、UI、接口、协议、数据结构、状态机、模块或实现。

普通回应请求在什么情况下需要等待或阻塞，以及用户较长时间没有回应时角色应当怎样继续，留待未来出现实际需要时再讨论，不作为当前主线的下一问题。
