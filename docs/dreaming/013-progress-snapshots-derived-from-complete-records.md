# Dreaming 13：进展快照是完整记录的语义派生视图

日期：2026-08-25

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论进展快照与完整 thread 记录的关系、谁负责生成快照、检查点如何请求更新，以及历史快照如何保留和纠正。

本次不决定快照模板、字段、格式、存储方式、版本关系结构、引用形式、触发默认值、UI、API 或文件布局，也不设计任何自动质量评价。

## 完整记录是事实来源，进展快照是派生视图

Dreaming 9 确立的完整记录原则覆盖 thread 生命周期内的消息、事件和信息，其中也包括后续 Dreaming 10 进一步确立的委托记录。这些完整消息、事件和委托记录是 thread 事实的来源。

进展快照则是 Agent 或真人基于这些事实生成的语义派生工作视图。它帮助角色快速理解当前协作进展，但不能覆盖、修改或替代完整记录，也不能成为判断事实是否发生的唯一依据。

因为快照包含语义整理，它可能已经过时、遗漏部分事实，或者包含生成角色的分析与判断。查看者需要能够区分快照中的事实、权威结论与角色判断，并在必要时回到完整记录核对。

## 快照呈现当前协作所需的工作信息

进展快照可以包含：

- 当前权威目标；
- 已完成的工作；
- 正在进行的委托；
- 已形成的重要结论；
- 已识别的风险；
- 等待决策的事项；
- 对下一步的建议。

这些是当前确认的候选内容，不是已经确定的固定模板。不同场景是否使用相同内容、各项如何表达，以及是否还需要其他内容，均未决定。

## 主持对快照可用性负责

主持默认负责确保进展快照更新及时，并且足以支持当前协作。主持可以亲自生成快照，也可以向其他角色发布一项普通委托，由目标角色生成快照。

Harness 只负责在检查点或明确请求到来时触发“生成新快照”的请求，向生成角色提供相对于既定检查点范围的新增事实，持久化已生成的快照，并将其展示给相应使用者。Harness 不自己概括事实，也不判断哪些信息重要、哪些结论正确。

主持的责任是确保快照可用于协作，不表示 Harness 能自动评价快照质量，也不表示主持必须亲自撰写每一份快照。

## 每个检查点形成新的历史快照

一般情况下，每次检查点产生一份新的进展快照。历史快照不回写，thread 同时提供一个稳定的“当前进展”入口，始终指向最新快照。

如果发现旧快照存在错误、遗漏或过时判断，应当在后续新快照中说明修正或取代关系，旧快照仍然保留。这使角色既能看到当前工作视图，也能追溯过去每个检查点当时形成的认识。

这里确认的是产品行为，不意味着已经选择用一个文件、多个文件、数据库版本或其他方式保存快照。“当前进展”入口怎样呈现、历史快照之间怎样表示版本关系，也留到后续设计。

如果自上一个检查点以来没有任何变化，是否仍然生成一份“无变化”快照，目前尚未决定。这是对一般检查点规则保留的明确边界，不影响有新进展时以新快照保留历史的原则。

## 检查点来自明确请求或确定性触发

生成新快照的检查点可以来自两类来源：

- 明确请求：主持提出请求、具备相应权限的其他角色提出请求，或者具备相应 Thread 权限的平台用户执行明确操作。
- 配置好的确定性触发：例如到达指定时间、发生已经明确的事件，或者达到配置的数量阈值。

时间、事件和数量阈值目前只是候选例子，不代表已经决定默认触发方式。哪些角色有权请求、平台用户需要什么权限、默认何时触发、每次请求覆盖哪些事实范围，都尚未决定。

Harness 在检查点到达后只发出“生成新快照”的请求，不自行生成语义摘要，也不根据消息内容是否“重要”而主动决定触发检查点。检查点到达本身是可以由明确请求或配置规则识别的客观事件；快照内容仍由 Agent 或真人作出语义整理。

## 快照不需要逐次治理验收

每份进展快照不需要主管理员逐次验收，也不会因为被持久化或展示就自动成为权威结论。主持对快照是否足以支持协作负责。

其他角色代写快照时，可以使用 Dreaming 10 中已经确认的普通委托及其验收能力，但这不是进展快照额外增加的一层系统审批。代写委托默认是否要求主持验收，目前尚未决定。

为了避免把派生判断伪装成事实，快照应当区分：

- 当前权威目标和已经确认的决定；
- 客观事实；
- 角色作出的分析与判断；
- 风险；
- 等待确认的问题。

只有在快照内容涉及新权威目标、目标变化或其他 thread 内治理事项时，主管理员才按照既有治理职责介入。快照本身不扩大主管理员的逐次审批范围，也不降低主管理员对治理事项的确认权。

快照中写明“目标已完成”“决定已确认”或类似内容，只能反映相应角色此前已经作出的治理行为。快照文字本身不能完成目标、确认决定、通过审批或正式结束 thread。

## 快照可以被质疑，并通过后续快照纠正

任何角色都可以质疑进展快照中的事实选择、判断或遗漏。纠正通过后续新快照表达，不回写旧快照。

快照中的内容应当可以追溯到相关消息、事件、委托或旧快照，使查看者能够核对依据和理解修正关系。具体采用链接、标识、引用片段或其他形式，尚未决定。

历史快照不回写是用户对产品快照行为独立确认的共识，不是从当前仓库 Dreaming 文档的维护规则推导出来的。仓库如何保存 Dreaming 认识快照，与产品如何保留 thread 进展快照，是两个不同层次的问题。

## 与 Dreaming 9 和 Dreaming 11 保持一致

进展快照不会改变 Dreaming 9 的完整记录原则。完整消息、事件和委托记录仍然保留；快照是否被定向展示或送达某些角色，不会把快照变成完整记录的替代品，也不会改变完整记录与定向展示相互分离的边界。

Dreaming 11 已确认 Harness 只能识别和处理确定性事实。检查点到达可以是客观事件，但“哪些内容重要”“当前进展意味着什么”“下一步应该做什么”仍是语义判断。因此 Harness 只触发更新请求、提供事实范围、持久化和展示，不负责总结。

## 这项共识暂时不意味着什么

- 不意味着已经决定统一的快照模板、字段或必填内容。
- 不意味着已经决定快照的文件格式、存储方式、文件数量或数据库版本方案。
- 不意味着已经决定“当前进展”稳定入口在 UI、API 或文件系统中如何表现。
- 不意味着已经决定历史快照之间的版本关系结构或具体引用形式。
- 不意味着已经决定触发检查点的默认值、请求权限、具体条件或事实范围。
- 不意味着已经决定没有任何变化时是否仍生成新快照。
- 不意味着已经决定代写快照的普通委托默认是否需要验收。
- 不意味着已经决定任何 UI、API 或文件布局。
- 不意味着 Harness 会自动生成摘要、判断内容重要性或评价快照质量。
- 不意味着进展快照会自动成为权威目标、已确认决定或其他治理结论。

快照模板与字段、存储和展示、稳定入口、版本与引用关系、触发规则与权限、无变化时的行为、代写验收默认值，以及自动质量评价的边界，留给后续 Dreaming 或设计阶段继续讨论。
