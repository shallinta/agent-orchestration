# Dreaming 26：Agent 内部失败不同于 Harness 调用故障

日期：2026-08-26

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论 Agent 内部失败与 Harness 调用边界故障的责任区分、Agent 正常返回“无法完成或受阻”应被怎样理解，以及调用故障应影响到多大范围。

本次不决定错误分类全集、适配器、退出码、重试默认值、恢复命令、会话机制、部分可用状态枚举、通知、UI、协议、状态机或其他实现方式。

## 成熟 Agent 通常自行管理内部失败

thread 连接的 Agent 角色通常来自成熟的 Agent 产品。这类 Agent 一般已经拥有自己的执行循环、工具使用、内部重试、工具恢复和失败判断能力，能够在一次对外调用内部处理许多临时问题。

因此，Harness 默认不介入 Agent 的内部执行过程，不替 Agent 决定某一步工具是否重试、怎样修复工具环境或何时放弃内部路径。Harness 管理的是对 Agent 发起调用并取得可靠返回的边界，而不是重新实现一套 Agent 内部执行能力。

这是本项目采用成熟 Agent 产品时的产品前提和常态，不保证每个自定义 Agent 都具备同等能力。自定义 Agent 可能缺少内部恢复或失败判断，但 Harness 也不能通过无限重复整个任务来弥补其内部能力不足。怎样表达和验证自定义 Agent 的这些能力，本轮不决定。

## Agent 内部恢复后仍是正常执行

Agent 在内部遇到工具错误、临时失败或其他问题后，如果依靠自身能力恢复并正常返回可靠结果，那么从 Harness 调用边界看，这次调用仍然是正常执行。

内部曾经发生失败，不会仅凭这一事实使 Harness 把调用标记为故障、再次执行完整任务或改变委托。Harness 也不要求 Agent 把每一次内部尝试暴露为由 Harness 接管的恢复步骤。

Agent 是否需要在正常结果中说明内部问题、这些信息怎样展示或统计，本轮不决定。这里确认的只是：已经在 Agent 内部得到恢复的问题，不会自动升级为 Harness 调用故障。

## Harness 只能识别调用边界上的故障

Harness 无法可靠启动或连接 Agent、无法恢复本次调用所需的会话，或者无法取得可作为本次调用结果使用的可靠返回，属于 Harness 可以客观识别的调用故障。

调用故障表示 Harness 与 Agent 之间的这次执行边界没有可靠完成，不代表 Harness 已经理解 Agent 内部发生了什么，也不表示委托的业务目标不可能完成。

Harness 可以按照事先明确、适合当前故障且安全的确定性策略处理调用故障，例如在有界条件内再次尝试或执行明确的边界恢复动作。但本轮不决定哪些故障可重试、具体策略、默认次数、等待方式或恢复动作。

## 正常返回“无法完成或受阻”是工作结果

如果 Agent 已经被可靠调用并正常返回，只是在结果中明确表示“无法完成”“当前受阻”或给出类似业务结论，那么调用和沟通本身是成功的。这是一项需要角色理解的工作结果，不是技术调用故障。

Harness 不理解这段返回代表的具体原因、严重程度或下一步，也不会因为结果不符合成功预期，就把它改判为连接失败或自动重新执行完整任务。

发布者、目标角色、主持或其他有权角色可以根据返回内容判断是否需要补充信息、调整委托、改变计划或采取其他行动。这里不新增任何角色权力，也不决定工作结果怎样改变委托进展；相关行为继续遵守 Dreaming 10。

“Agent 正常返回了结果”也不等于“委托已经完成并被验收”。调用成功、工作结果含义与委托生命周期是三个不同层次，不能互相自动推导。

## 重试只用于明确、有界且适合重试的调用故障

调用故障可以受确定性恢复策略处理，但所有自动重试都必须具有明确条件、有限次数或其他清晰终止边界，并且该类调用在已知边界下适合重试。

重试可能造成重复资源成本，也可能重复触发 Agent 已经开始的外部动作或其他副作用。因此，Harness 不能把“不确定是否成功”简单等同于“可以安全再来一次”，更不能无限重试直到得到看似满意的业务结果。

Agent 正常返回“无法完成或受阻”不是调用故障，默认不触发整个任务自动重跑。反复提交相同任务不能替代成熟 Agent 应承担的内部恢复，也不能成为补偿自定义 Agent 能力不足的通用策略。

哪些调用适合重试、怎样识别可能重复的成本或副作用，以及怎样保证恢复安全，本轮不决定；尤其不设计幂等协议、去重机制或具体恢复流程。

## 故障首先影响最小执行范围

一次调用故障首先只影响当前执行尝试，不会立刻把相关 Agent 角色整体标记为不可用，也不会让该角色的其他健康执行能力停止工作。

如果明确恢复策略仍可继续，Harness 只在策略边界内处理当前尝试。策略成功后，相关执行可以继续；策略耗尽或遇到未覆盖情况后，故障才影响与这次调用相关的执行流或对应执行能力，并形成可记录、可报告的客观事实。

一个 Agent 角色可能拥有不止一种仍可工作的执行能力。某项能力发生故障时，其他已经明确为健康且适用于其他工作的能力可以在其他适用约束内继续使用，Harness 不因为局部故障统一停用整个角色。

只有在一个角色全部已明确适用的执行能力都被阻断时，才把该角色视为在 Agent 调用意义上整体不可用。哪些能力适用于哪些执行、部分可用怎样表达、能力恢复后怎样更新，以及不同限制如何组合，本轮均不决定；Harness 不能通过理解任务内容自行猜测替代能力。

## 调用故障不自动改变委托

无论一次调用尝试失败、恢复策略耗尽、某项执行能力被阻断，还是角色在调用意义上整体不可用，都不会自动使相关委托失败、取消、拒绝、完成或结束，也不会自动转移目标角色的责任。

这些事实可能影响委托接下来是否能够继续执行，但委托状态、责任和验收继续遵守 Dreaming 10。Harness 记录并报告能够确定的故障范围、尝试情况和能力可用事实，不从技术故障推导业务结论。

后续怎样处理，由具备对应权力的角色根据故障事实、委托目标和业务影响明确决定。Harness 不自行取消委托、改派其他角色、降低成果要求或宣告工作失败。

## Harness 只管理调用边界与确定性策略

Harness 负责识别调用是否在明确边界内可靠启动、连接、恢复所需会话并取得可靠返回，依据明确且安全的有界策略处理调用故障，以及持久化和路由相关事实事件。

Harness 不进入 Agent 内部替它恢复工具，不评价 Agent 返回的工作结论是否充分，也不根据结果语义决定是否重跑。内部执行与业务语义分别属于 Agent 产品和 thread 角色，Harness 只处理能够客观确定的边界事实。

所有调用故障、策略尝试、策略耗尽和能力可用事实继续按照 Dreaming 9 进入完整 thread 记录，并遵守 Dreaming 11：策略完成、耗尽或未覆盖时报告事实，由 Agent 或真人判断下一步。

## 这项共识暂时不意味着什么

- 不意味着所有自定义 Agent 都具备成熟 Agent 产品的内部重试、工具恢复或失败判断能力。
- 不意味着 Harness 会进入 Agent 内部接管工具恢复、路径选择或失败判断。
- 不意味着 Harness 可以靠反复执行完整任务弥补 Agent 的内部能力不足。
- 不意味着 Agent 内部发生过失败但已经恢复，会自动成为 Harness 调用故障。
- 不意味着 Agent 正常返回“无法完成或受阻”属于技术调用故障或应自动整体重跑。
- 不意味着调用成功等于工作目标实现、委托完成或结果已被验收。
- 不意味着任何调用故障都适合重试，或可以无限重试。
- 不意味着局部调用故障会立刻使角色整体不可用或阻断其他健康执行能力。
- 不意味着调用故障、策略耗尽或角色不可用会自动使委托失败、取消、结束或转移责任。
- 不意味着已经决定错误分类全集、适配器、退出码、重试默认值、恢复命令或会话机制。
- 不意味着已经决定部分可用状态枚举、通知、UI、接口、协议、状态机、算法、模块或实现方式。
- 不意味着已经设计幂等协议、去重机制或副作用恢复方式。

调用故障的详细分类、适合重试的边界、策略默认值、能力部分可用与恢复、通知和具体交互，留给后续 Dreaming 或设计阶段继续讨论。
