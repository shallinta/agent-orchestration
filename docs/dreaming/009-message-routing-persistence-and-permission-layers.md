# Dreaming 9：消息路由、完整记录与权限分层

日期：2026-08-18

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论 thread 内信息如何被完整保留、消息如何送达角色、角色如何取得相关上下文，以及平台用户、Thread 权限与角色权限之间的产品边界。不讨论数据结构、接口、协议、模块划分或其他实现细节。

## 定向发送不影响完整持久化

Harness 持久化一个 thread 生命周期内发生的所有角色消息、事件和信息，形成完整的 thread 记录。一条消息只定向发送给某个或某些角色，不会让它从完整记录中消失，也不会降低持久化记录的完整性。

因此，“Harness 保存了什么”与“某条消息当时送给了谁”是两个不同问题。定向发送决定消息的直接接收者，完整持久化则服务于 thread 的连续性、审计和后续上下文使用。

## 配套 UI 展示完整记录

Harness 的配套 UI 展示完整的 thread 持久化记录。本地数据保存在创建该 thread 的机器上。

谁能够通过 UI 查看或管理完整记录，取决于平台用户是否能够访问这台机器或其 UI、是否通过相应的远程鉴权，以及是否拥有该 thread 的 Thread 权限；不取决于这个人在 thread 中是否拥有用户角色。

同一个真人可以既是平台用户，也拥有 thread 内的用户角色，但两者不是同一个概念。拥有用户角色不会自动获得 UI 中完整记录的访问权；反过来，拥有 Thread 权限的平台用户也不必先在 thread 中产生一个用户角色，才能查看或管理完整记录。

## 外部消息通道只传递定向消息

飞书等外部消息通道只把定向发送给某个用户角色的具体消息送达该角色背后的真人，不向该真人开放完整 thread 历史。

外部通道是角色接收特定消息的一种外围入口，不等同于配套 UI 的完整记录视图。gateway、飞书接入以及不同外部通道如何建设，属于外围能力，当前不深入讨论。

## 默认采用定向路由，不自动广播

Thread 默认不把每条消息广播给所有角色。主持分派任务时，应当明确：

- 任务发给哪个目标角色，可以是单个角色、多个角色或全员；
- 推荐目标角色查询哪些消息记录，或者使用哪些 thread 上下文、知识库关键字；
- 目标角色在完成任务时允许与哪些对象角色讨论或协作；
- 完成后应当向哪个角色回报结果。

如果主持没有给出回报对象，默认回报给主持。

当现有角色中没有合适人选时，主持先向主管理员申请新增角色，或者请在相应领域有权限的管理员指定合适角色。谁有资格批准或指定，仍受已经确认的 thread 内治理关系约束。

## 主持推荐上下文，但不临时缩窄查询权限

主持为一次任务推荐相关消息、上下文或知识库关键字，是为了帮助目标角色快速找到重要信息，而不是临时规定该角色只能查询这些内容。

一个角色是否能够查询最近 N 条消息、更多 thread 历史、thread 上下文或知识库，取决于它的角色权限。角色在权限允许的范围内主动查询自己需要的信息；主持不为每次任务临时扩大或缩小这项查询范围。

这一区分避免把“主持认为哪些内容与当前任务最相关”误写成“角色被允许看到什么”。前者是协作建议，后者是角色权限。

## 广播是可调整的 Thread 配置

Thread 配置可以切换为全员广播，使消息默认送达全部角色。这适合头脑风暴、会议等需要所有角色共同跟进的场景，并且可以在 thread 生命周期中随时调整。

无论 thread 当前是否采用全员广播，单条消息都可以明确指定多个角色或全员作为接收者。全员广播改变的是默认送达方式，不改变 Harness 对完整 thread 记录的持久化。

## 完整记录支持持续的上下文与知识维护

Harness 保存的完整记录，可以供外围的 thread 上下文查询能力或知识库持续整理和维护，并向角色提供查询能力。角色实际能够查询的范围仍由其角色权限决定。

如何从完整记录形成可查询上下文、如何维护知识库、如何处理信息变化和过时内容，都属于后续设计问题，本次不决定具体实现。

## 平台用户、Thread 权限与角色权限是三个层次

三个概念分别回答不同问题：

- `平台用户` 位于 UI/API 层，是在 thread 外操作 Harness 的账号主体。
- `Thread 权限` 控制某个平台用户能否访问或管理完整 thread，包括其配套 UI 中的完整持久化记录。
- `角色权限` 控制一个角色在 thread 内能够做什么。

角色权限主要包括对本地项目文件、技能、工具或服务、审批、消息记录、thread 上下文和知识库查询等能力的使用范围。角色加入 thread 时，由具备相应操作权的平台用户设置这些权限；具备相应操作权的平台用户之后可以调整。

平台用户的 Thread 权限不会因为它背后的真人在 thread 中拥有主管理员、管理员或其他用户角色而自动产生；角色权限也不会自动转化为平台用户在 UI/API 层的操作权。

## Thread 配置权属于平台用户

所有 Thread 配置的实际设置与修改权都属于具有相应 Thread 权限的平台用户，不属于主管理员角色。

主管理员仍然拥有 thread 内的目标确认、最高审批等治理权，但这些角色治理权不能推出平台层的 Thread 配置权。Thread 的 owner 或 creator 通常会与主管理员背后的真人是同一个人，但这不是强制绑定关系；即使是同一个真人，其平台用户身份与用户角色也必须分别理解。

这一结论明确覆盖 Dreaming 8 中“主管理员拥有 thread 配置权”的旧说法。按照后续 Dreaming 优先规则，从本记录开始，Thread 配置权归平台用户，主管理员只保留 thread 内治理权；Dreaming 8 原文作为当时认识永久保留，不再回写。

## 这项共识暂时不意味着什么

- 不意味着角色会自动收到完整 thread 历史；直接送达和主动查询仍是不同方式。
- 不意味着定向消息不会进入完整记录，也不意味着未被直接发送的角色永远不能在权限允许时查询它。
- 不意味着拥有用户角色就能访问配套 UI 的完整记录。
- 不意味着拥有 Thread 权限的平台用户必须同时在 thread 中拥有用户角色。
- 不意味着外部消息通道可以浏览或同步完整 thread 历史。
- 不意味着主持推荐的上下文关键字构成临时访问限制。
- 不意味着已经决定全员广播如何切换、如何在界面中表现或如何具体配置。
- 不意味着已经决定 gateway、飞书接入、thread 上下文查询能力或知识库如何实现。
- 不意味着已经决定任何消息、事件、权限、配置或查询能力的数据结构、接口、协议与模块实现。

外部通道的具体范围、上下文与知识库的维护方式，以及各类角色权限应如何细分和形成默认值，留给后续 Dreaming 或设计阶段继续讨论。
