# Dreaming 19：审批等待只阻塞发起角色的普通工作并暴露可用状态

日期：2026-08-26

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论一个角色发起审批请求并等待结果时，它对普通后续工作的可用性、其他角色如何得知这一事实，以及发信者可以怎样选择下一步。

本次不建立完整审批模型，也不决定状态枚举、状态机、队列、并发竞态、UI、协议、模块或发布订阅实现。

## 审批等待只影响发起请求的角色

一个角色发起审批请求并进入等待后，该角色在等待期间对普通后续工作不可用。这里的不可用只表示它暂时不能继续接收或执行普通后续工作，不表示角色已经离开 thread、身份失效或永久停止工作。

这项等待只作用于发起审批请求的角色，不阻塞其他角色，也不使整个 thread 进入等待。主持和其他角色仍可继续沟通、处理已有事项、向可用角色分派工作，或推进不依赖该审批结果的其他协作。

角色等待审批也不表示相关委托、权威目标或 thread 自动失败、完成或结束。审批结果在业务上意味着什么，仍由 Agent 或真人根据语义判断。

## Harness 暴露可客观确定的角色可用状态

Harness 可以根据明确发生的审批请求与等待事实，确定发起角色当前是否可接收普通后续工作，并在有消息或工作指向该角色时，不调用目标角色便直接向发信者反馈角色可用状态。

Harness 反馈的是可客观确定的运行事实，例如目标角色当前正在等待审批、暂时不能接收普通后续工作。它不判断目标角色是否愿意处理、是否胜任、是否值得等待，也不根据自然语言猜测角色是不是“忙”“犹豫”或希望稍后处理。

只有明确、机器可识别的运行与等待事实才能改变 Harness 所知的可用状态。角色在普通消息中表达压力、迟疑、优先级或个人意愿，不会仅凭语义被固定程序自动解释为可用状态变化。

角色可用状态回答的是“当前能否接收普通后续工作”，不回答“谁最适合完成这项工作”。后一问题仍由主持、发信者或其他真人角色判断。

## 发信者在得知不可用后选择下一步

Harness 向发信者反馈目标角色暂时不可用后，不自行判断哪种替代方案最合适。发信者可以根据当前目标和工作语义选择：

- 改为联系或委托其他可用角色；
- 暂时处理其他事情；
- 明确选择等待目标角色恢复可用。

“发信者”可以是向目标角色发送消息或安排工作的 Agent 角色，也可以是用户角色。不同发信者可以采取不同选择；Harness 不把某个选择推导为整个 thread 的统一等待策略。

改找其他角色不会让 Harness 自动判断两个角色能力等价，也不会自动转移原有委托责任。是否需要取消、调整或另建委托，继续遵守 Dreaming 10，并由相应角色明确决定。

## 明确选择等待后，在恢复可用时通知

如果发信者明确选择等待，Harness 应在目标角色恢复可接收普通后续工作时通知该发信者。恢复通知只说明目标角色的可用状态已经发生可确定变化，不评价审批结果，也不建议发信者下一步应该做什么。

选择等待必须由发信者明确表达，Harness 不因为发信者没有立即改找其他角色，就推断其已经选择等待。等待的开始与目标角色恢复可用都必须来自 Harness 能够确定识别的事实。

收到恢复通知不等于原消息已经再次发送、目标角色已经接受工作或相关委托已经继续执行。是否自动重投原消息目前保持未决；在规则尚未确定前，不能从“通知恢复”进一步推出自动重投行为。

等待期间发信者是否可以取消等待、修改原意，多个等待者如何处理，以及恢复通知失败后的行为，本轮均不决定。

## 原则上保留审批相关沟通

发起角色对普通后续工作不可用，不应把审批过程本身所需的沟通一并切断。原则上应保留与当前审批直接相关的补充说明、调整、撤回等沟通或行动，使审批等待不成为无法澄清或修正请求的死锁。

但“审批相关沟通”具有较高复杂度。本轮不决定哪些内容属于补充说明、调整或撤回，不决定谁可以发起、发给谁、如何影响审批，也不建立它们的完整行为。

Harness 不能通过理解自由文本语义自行判断某条消息是否属于审批相关沟通。未来如果需要确定性保留这些能力，必须另行讨论可明确识别的分类、权限、路由与行为；本轮只确认不应把它们与普通后续工作一起笼统阻塞的产品原则。

## 与既有边界保持一致

本轮延续 Dreaming 11 的确定性 Harness 边界：Harness 可以识别明确的审批等待、角色不可用和恢复可用等客观事实，但不能理解等待意图、工作价值或替代角色是否合适。

它也延续 Dreaming 18 对审批策略的有限认识。审批等待中的角色可用性只描述执行期间的一项产品行为，不决定哪些行动需要审批、谁能批准、批准条件或审批结果。

所有可用状态变化、不可用反馈、明确等待选择和恢复通知，继续按照 Dreaming 9 进入完整 thread 记录。记录这些事实不表示 Harness 可以从中推导审批的业务含义。

## 这项共识暂时不意味着什么

- 不意味着审批等待会阻塞其他角色或整个 thread。
- 不意味着等待角色已经离开 thread、失去身份或永久不可用。
- 不意味着角色不可接收审批相关的补充说明、调整或撤回。
- 不意味着已经定义哪些沟通属于审批相关沟通，或它们怎样路由和生效。
- 不意味着 Harness 会根据自然语言判断角色意图、繁忙程度、能力或语义上的适合程度。
- 不意味着 Harness 在发现目标不可用后会自动选择替代角色或替发信者决定等待。
- 不意味着恢复通知会自动重投原消息、恢复委托或重新发起调用。
- 不意味着已经决定完整审批模型、审批结果、状态枚举、状态机、队列或并发竞态。
- 不意味着已经决定 UI、接口、协议、模块、状态变化事件、注册响应或发布订阅实现。

审批相关沟通的分类、权限、路由和完整行为，是否自动重投原消息，等待的取消与多发信者行为，以及可用状态变化通知的具体设计，留给后续 Dreaming 或设计阶段继续讨论。
