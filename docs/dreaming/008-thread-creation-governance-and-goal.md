# Dreaming 8：Thread 的创建、治理与权威目标

日期：2026-08-17

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论创建 thread 时必须具备的角色与系统标签、用户是否必须逐项配置、其他角色何时加入，以及目标如何在协作中形成和成为当前权威目标。不讨论这些要求未来采用什么数据结构、模块、接口、协议或其他技术方式实现。

## 创建时必须建立两项唯一治理职责

创建 thread 时，用户必须完成两项选择：

1. 选择一张 Agent 身份卡，由它产生一个 Agent 角色，并为该角色附加唯一的 `主持` 系统标签。
2. 选择一张已有的用户身份卡，或者新建一张用户身份卡，由它产生一个用户角色，并为该角色附加唯一的 `主管理员` 系统标签。

`主持` 负责理解、组织和持续推进整个 thread 协作。`主管理员` 全权负责本次 thread，拥有 thread 配置、权威目标确认和最高审批等唯一治理权。两项职责彼此不同：主持推动协作向前，主管理员对关键治理事项作出最高决定。

主管理员是唯一的系统标签，但不是 thread 中唯一的真人用户角色。创建后仍可有多个其他用户角色加入协作，并承担业务判断、提供资料或完成其他工作。

## Thread 必然有配置，但逐项配置是可选步骤

每个 thread 必然存在一组影响本次协作如何进行的配置。由于这些配置可以有默认值，用户创建 thread 时可以不逐项设置；跳过配置步骤表示接受默认配置，而不是 thread 没有配置。

当前想到的产品配置类别包括：

- 工作目录；
- 权限；
- 审批与自治程度；
- 轮次如何推进；
- 等待与超时；
- 并发；
- 失败后的恢复期望；
- 统计与预算。

这些只表示用户可能需要控制的产品范围。目前没有确认每类配置是否都必须出现、默认值是什么、由谁在什么时刻调整，也没有决定它们的具体表达方式。

## 其他初始角色是可选的

除创建时承载主持和主管理员标签的两个角色外，用户可以选择更多身份卡，让其他角色从 thread 开始时就加入；这不是创建 thread 的必要条件。

Thread 创建后，仍可根据协作需要让新的角色加入。创建时没有一次性选齐所有角色，不妨碍这项协作成立和继续推进。

## Thread 可以先存在，再在协作中形成目标

创建 thread 不要求用户先提交完整需求，也不要求权威目标已经得到确认。Thread 可以在权威目标确认前存在，早期协作本身就可以用于理解问题、补充背景、整理资料、识别规则和限制，并逐渐形成目标与预期成果。

目标、背景、资料、规则、限制、预期成果和协作方式等内容，在 thread 创建后通过 thread 内协作表达、质疑、补充和形成。这个过程不限定为主管理员与主持之间的多轮对话；所有已经加入的角色都可以参与讨论和头脑风暴。

因此，“thread 是围绕共同目标和预期成果的有界协作”不等于“创建前必须已经写好完整且不可改变的目标”。共同目标可以在协作早期逐渐清晰。

## 所有角色都能完善目标，只有主管理员能够确认

Thread 中的任意角色都可以提出、质疑或完善目标，也可以补充背景、资料、规则、限制、预期成果和协作方式。主持负责组织这些输入、推动讨论，并让协作持续接近一个可确认的目标。

只有主管理员能够确认哪个表述是当前权威目标。未经主管理员确认的提议、质疑和候选表述都可以继续影响讨论，但不能取代当前权威目标。

目标在 thread 生命周期中可以更新。每次更新都必须经过主管理员确认，才能成为新的当前权威目标。主管理员的确认权不妨碍其他角色持续提出异议和改进建议。

## 缺少合适角色时，默认先申请

协作过程中，如果主持判断现有角色不足以完成接下来的工作，默认行为是向主管理员申请引入新角色，由主管理员决定是否加入。

未来是否允许把 thread 配置为“主持可以自主引入新角色”，目前保持未决。这种自治是否真实需要、适用于哪些场景、应受哪些边界约束，都需要后续继续讨论。

## 系统标签表达 Thread 内的治理语义

系统标签附加在角色上，表达超越场景化身份、职位或分工的系统治理语义。一个角色在符合各标签资格与规则时可以组合多个系统标签；每个系统标签分别拥有自己的适用资格、唯一性、权限与规则，组合不会取消这些约束。

当前已经确认：

- `主持` 是唯一系统标签，一个 thread 同时只能有一个；当前只能附加在 Agent 角色上。
- `主管理员` 是唯一系统标签，一个 thread 同时只能有一个；当前只能附加在用户角色上。
- `管理员` 是非唯一系统标签，由主管理员设置；它可以让角色在主管理员授权下局部负责某个领域，但具体适用资格、责任、权限范围和使用场景都属于未来功能，尚未确认。

场景中的 CEO、顾问、程序员、运营、产品经理或游戏主持人等身份，不会因为名称听起来具有管理意味就自动获得这些系统标签。

## 这项共识暂时不意味着什么

- 不意味着创建 thread 前必须提交完整需求、最终目标或全部资料。
- 不意味着 thread 必须等到权威目标确认后才能存在或开始协作。
- 不意味着目标只能由主管理员或主持提出，也不意味着目标形成只能采用两人多轮对话。
- 不意味着创建时必须选择主持和主管理员之外的其他身份卡。
- 不意味着主管理员是 thread 中唯一的真人用户角色。
- 不意味着主持可以默认自主引入新角色；这一扩展仍未确认。
- 不意味着所有产品配置类别都要求用户逐项填写，也不意味着已经确定任何默认配置。
- 不意味着管理员的适用角色、具体责任和权限范围已经确定。
- 不意味着已经决定身份卡、角色、系统标签、配置或权威目标的数据结构、模块、接口、协议与实现方式。

主管理员何时以及如何作出确认、审批与授权，管理员未来负责哪些场景，以及主持自主引入角色是否值得支持，留给后续 Dreaming 继续讨论。
