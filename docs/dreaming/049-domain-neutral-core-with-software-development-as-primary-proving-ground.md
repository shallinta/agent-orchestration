# Dreaming 49：核心保持领域无关，软件开发是首要验证场景

日期：2026-08-31

状态：当前阶段共识，可继续修正

## 这次只讨论什么

用户最初以软件项目开发说明核心痛点，同时希望 Harness 未来也能用于自媒体创作、数据分析、金融投资及其他多角色协作场景。本次只讨论：软件开发应当成为 Harness 的产品边界，还是最重要的初始使用与验证场景。

本次确认，Harness 的核心产品语义应当保持领域无关。需求分析、技术设计、方案评审、编码、代码评审、测试和问题修复是软件开发场景中的协作表达，不是所有 thread 都必须采用的内置流程。软件开发仍然是最重要的初始使用与验证场景，但不会因此把 Harness 核心限定为软件研发工具。

本次不决定首个版本范围、行业模板、领域插件、预设角色、提示内容、工具接入、UI、协议、数据结构、技术架构或实现。

## 软件开发是问题来源和首要验证场景

项目最初来自一个具体而真实的软件开发体验：不同 Agent 分别擅长方案、执行、评审和修复，组合使用能够获得更好的结果，但真人必须持续复制上下文、分派工作和转达反馈。

因此，软件开发不是随意选择的演示案例。它提供了已被用户实际经历的痛点，也具有较清楚的成果、评审、返修和质量反馈链路，适合持续检验 Harness 是否真正减少人工协调并发挥不同 Agent 的比较优势。

在后续探索和迭代中，软件开发可以继续作为优先观察、试用和检验产品价值的场景。这个优先性来自真实需求与可获得反馈，不表示软件开发中的全部习惯都应被提升为跨领域规则。

## Harness 核心不预设软件开发流程

Harness 不把“需求分析—设计—开发—评审—测试—修复”建立为每个 thread 的固定流程，也不要求非代码项目把自己的工作强行映射成这些步骤。

自媒体创作可能使用选题、调研、撰稿、审校和发布等表达；数据分析可能围绕问题定义、数据获取、分析、复核和解释组织工作；编辑出版、游戏或其他场景还会采用完全不同的角色、责任和推进语言。这些差异属于具体 thread 内角色理解和组织的场景语义。

按照 Dreaming 39，Harness 不预设通用阶段或 Step 模型。软件开发中的阶段名、职位名、产物名和质量活动可以出现在身份卡、角色消息、委托、进展快照、知识内容或工作成果中，但不会仅因软件开发是首要场景就自动成为平台或 Harness 的系统语义。

## 通用核心承载场景化协作

当前已经确认的 thread、角色、系统标签、权威目标、普通消息、委托、结果吸收、独立评审、权限、审批、预算、进展快照和知识检索等产品语义，描述的是不同领域都可能出现的协作关系，而不是某个行业的固定步骤清单。

具体场景中的“程序员”“编辑”“研究员”“审稿人”“运营”等身份，由身份卡和 thread 内角色表达；“编码”“撰稿”“分析”“校对”等工作，可以通过普通沟通和委托承担；成果如何判断、需要什么评审以及何时请求用户决定，继续由相应目标、角色和治理关系确定。

领域无关不表示所有场景必须使用完全相同的词语或工作习惯。它要求核心语义能够承载场景差异，而不是让某个领域的流程成为其他领域必须遵守的隐性模板。

## 领域能力可以不同，但不改变核心边界

不同领域可能需要不同身份卡、专业 Agent、工具、技能、资料来源、工作空间、评审标准、权限与风险边界。软件开发也可能需要代码仓库、测试、构建或代码审查等专门能力。

这些领域能力可以让某个场景更好用，但不应反向改变 Harness 的通用协作含义。例如，代码评审可以是一项独立评审委托，但独立评审本身不只属于代码；作品审校、数据复核或研究评议也可以使用相同的协作责任关系，同时保留各自的专业内容。

本轮只确认领域能力与通用核心之间的产品边界，不决定未来通过模板、扩展、内置能力或其他方式提供领域支持。

## 领域无关不等于同时服务所有领域

保持核心领域无关，不要求第一个版本、每次迭代或同一套默认体验同时覆盖软件开发、自媒体、数据分析、金融投资和所有其他场景。

早期产品可以集中在软件开发中发现问题、获得反馈和形成可靠闭环。只要形成的核心概念与规则没有无必要地绑定代码领域，这种聚焦不违背领域无关方向。

同样，领域无关也不表示 Harness 对所有行业都已经有效、安全或合规。不同领域的专业准确性、风险、监管、责任和工具可靠性需要分别面对；特别是高风险活动，不能仅因可以使用通用角色与委托就推断产品已经适合实际采用。

是否以及何时扩展到某个具体领域，应根据真实用户问题、可验证价值和相应风险另行判断，不由“核心领域无关”自动产生路线图承诺。

## 软件开发可以获得便利，但不能成为强制模型

软件开发作为首要验证场景，未来可以拥有更便利的身份卡、协作指引、工作习惯或领域能力。领域无关不要求为了表面统一而拒绝这些场景优化。

边界在于：软件开发便利应当服务软件开发用户，不应让所有 thread 都出现开发、测试、代码评审等概念，也不应让其他领域只有伪装成软件项目才能完整使用 Harness。

因此，产品可以“优先把软件开发做好”，但不能把“软件开发流程就是 Harness 流程”作为前提。具体便利如何提供、是否内置以及何时建设，留给版本规划和设计阶段决定。

## 与既有共识的关系

Dreaming 3 已经确认多 Agent 的价值来自在特定用户、任务和约束下组合比较优势，而不是固定 Agent 品牌或固定角色分工。本轮进一步确认，“特定任务”可以来自不同领域，Harness 不预先把比较优势限定为软件开发能力。

Dreaming 4 和 Dreaming 5 的身份卡与角色抽象继续支持场景化身份。程序员、编辑、顾问或其他身份不是 Harness 的固定角色类型；同一底层 Agent 可以通过不同身份卡在不同 thread 中承担不同领域工作。

Dreaming 10 的委托表达一个 Agent 角色对另一个 Agent 角色的工作责任，不等同于软件项目任务。Dreaming 37 的独立评审也不是代码评审专用概念，可以承载不同领域中的重新检查与意见交付。

Dreaming 39 已经排除通用阶段模型，本轮进一步排除软件开发阶段成为隐含的通用推进模型。Dreaming 48 的免协调连续推进能力同样不依赖具体领域；它要求减少真人持续中转，但不规定协作必须推进哪些行业步骤。

## 这项共识暂时不意味着什么

- 不意味着第一个版本必须支持多个行业或同时验证多个领域。
- 不意味着软件开发不再是最重要的初始使用与验证场景。
- 不意味着软件开发不能拥有专门便利、身份卡、指引、工具或其他领域能力。
- 不意味着所有领域天然具有相同流程、风险、评审标准或成果形式。
- 不意味着通用角色与委托能力足以证明产品已经适合金融投资或其他高风险活动。
- 不意味着 Harness 会理解任一领域的专业内容或替代专业角色判断。
- 不意味着已经确定完整且永久不变的通用核心概念集合。
- 不意味着已经决定行业模板、扩展机制、领域插件、默认角色、提示内容、工具接入、UI、接口、协议或实现。

软件开发场景最先需要验证哪一种真实协作，以及领域便利与通用核心未来怎样组合，留给用户明确进入版本规划和设计阶段后讨论，不在本次 Dreaming 中提前决定。
