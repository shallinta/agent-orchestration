# Dreaming 52：身份卡是外部维护的简历，不自动改变既有角色

日期：2026-08-31

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 3 已经确认，不同 Agent 的质量、速度、价格、擅长领域和其他特征取决于用户的实际配置与经验，不能由产品品牌静态决定；Dreaming 5 又把身份卡定义为可复用模板，把加入 thread 后产生的角色定义为独立实例。

本次只讨论：身份卡上的能力与特征资料由谁负责形成和维护，Harness 是否负责从协作经历中评价 Agent，以及身份卡以后发生变化时是否自动改变已经存在的角色。

本次确认，身份卡是由平台用户负责提供和维护的声明性“简历”。Harness 使用这些资料支持角色协作，但不负责证明、评价或自动更新其中的能力描述。身份卡被用于创建角色后，原身份卡后续变化不会自动改变既有角色；若未来允许调整既有角色，也必须是平台用户针对该角色作出的明确行为，而不是模板变化的隐式传播。

本次不决定身份卡字段、格式、存储位置、编辑界面、导入导出、版本、市场、评价指标、更新建议、角色修改范围、变更交互、权限粒度或其他技术与产品设计。

## 身份卡是平台用户维护的声明性简历

名称、性格、回复风格、擅长方向、质量、速度、价格、模型、插件、记忆、环境和调用能力等资料，可以帮助主持或其他角色理解“这里有哪些人才、谁可能更适合当前工作”。这些资料来自平台用户对实际接入能力的认识，而不是 Harness 自动认证的客观事实。

平台用户可以根据自己的使用经验维护身份卡，也可以未来借助第三方资料、专门的身份卡管理工具、其他评价系统或 thread 经历沉淀出的建议进行维护。信息究竟怎样产生、怎样比较、是否采纳自动建议以及何时更新，属于身份卡维护方的责任，不属于 Harness 核心。

因此，Harness 面对的是平台用户已经选择提供的简历，而不是需要自己建立的 Agent 排行、能力测评或人才市场。身份卡中的陈述可以有主观性、时效性和误差，不能被 Harness 当成质量保证或客观真理。

## Harness 使用简历，不替平台用户评价人才

Harness 需要让获准使用身份卡信息的角色能够据此开展协作。例如主持可以参考身份卡所描述的专长、速度、价格和限制来选择角色，平台用户也可以据此决定把哪些身份卡加入 thread。

但 Harness 不通过调用次数、委托完成情况、评审意见、用户满意度或其他 thread 事实自行给身份卡打分，也不自动用一次协作结果覆盖平台用户的描述。它同样不负责证明某项擅长声明真实、比较不同 Agent 的绝对强弱，或者根据历史表现自行改变身份卡。

角色仍可在协作中对另一个角色的成果作出评价、评审或风险判断，这些是具体 thread 中的工作内容；它们不会仅因被记录就自动成为跨 thread 的身份卡评价。若未来有外围系统把这些经历整理为身份卡维护建议，是否采纳仍由平台用户决定。

## 身份卡变化不自动传播到既有角色

身份卡是模板，角色是它在特定 thread 中产生的独立实例。角色创建时依据的是当时被选用的身份卡资料；角色产生后，原身份卡在人才库中被编辑，不会让既有角色在没有明确行为的情况下改变名称、协作身份、能力描述、行为风格或其他参与依据。

这一边界保证同一张身份卡在不同时间、不同 thread 或同一 thread 多次使用时，可以产生彼此独立且可追溯的角色。否则，一次面向未来使用的简历调整可能同时、无声地改变多个正在协作的角色，使历史判断依据与当前表现无法解释。

身份卡修改默认只影响此后基于它创建的新角色。既有角色仍然可以继续以自己的 thread 内身份和上下文参与，原身份卡也不会因为某个角色的经历自动改变。

## 未来可以明确修改角色，但不是自动同步

完全禁止既有角色发生任何变化并非本轮共识。平台用户可能有合理需要修正某个角色的描述、连接能力或其他参与条件。若未来支持这种行为，它应当明确针对既有角色发生，并作为角色变化被理解，而不是解释为身份卡更新自动同步到了所有实例。

本轮只确认“默认不自动传播”和“变化必须明确”两条产品边界，不决定哪些角色内容可变、谁有相应 Thread 权限、变化是否影响在途工作、是否需要通知角色、能否选择性应用身份卡的新内容，或怎样保留变化前后的依据。

身份卡与角色因此不是永远断绝关系，也不是持续实时绑定。身份卡解释角色最初从何而来；角色创建后的协作生命、状态与明确变化属于它所在的 thread。

## 外围评价与身份卡工具可以存在，但不是 Harness 核心

未来可以建设专门的身份卡维护工具或系统，用于收集用户评价、汇总多个 thread 的经历、形成能力画像、维护第三方身份卡来源或提供人才市场。其他项目管理工具也可能承担跨 thread 的经验汇总，再向平台用户提供更新身份卡的参考。

这些方向与 Harness 有协作价值，但不会因此成为 Harness 核心必须解决的问题。Harness 核心聚焦一个 thread 生命周期内的角色协作；跨 thread 评价、身份卡资产治理和市场生态不能反向要求 Harness 判断成果质量或维护长期人才声誉。

本轮只保存这些外围可能性，不建立新的 Spark，也不形成路线图承诺。

## 与既有共识的关系

Dreaming 3 已经确认比较优势来自具体用户、模型、插件、记忆、环境与实际经验，用户标签并非客观真理。本轮进一步划定责任：这些认识由平台用户或其选择的外部工具维护，Harness 不自动验证或修正。

Dreaming 4 和 Dreaming 5 已经确认身份卡是模板、角色是 thread 内独立实例。本轮补足模板修改后的关系：角色创建后不会继续与原身份卡实时绑定，模板变化默认只服务未来实例。

Dreaming 11 的确定性边界继续有效。Harness 不根据委托结果和自然语言评价推断身份卡应该怎样变化；角色评价可以作为 thread 事实或工作内容存在，但不能未经平台用户明确行为就产生跨 thread 的简历更新效力。

Dreaming 51 按实际接入能力判断 Agent 是否可以参与，不按厂商或产品形态判断。本轮不要求 Harness 为此建立自动认证系统；平台用户仍负责选择和描述自己认为可用的完整 Agent 能力，调用边界故障则继续按既有规则作为 thread 事实处理。

## 这项共识暂时不意味着什么

- 不意味着身份卡中的能力、速度、价格或擅长声明已经被 Harness 验证。
- 不意味着身份卡只能手工编写，或未来不能由第三方工具、评价系统和 thread 经验辅助维护。
- 不意味着 Harness 必须建立 Agent 排行、评分、推荐、人才市场或跨 thread 声誉系统。
- 不意味着 thread 内的评审和评价没有价值，只是它们不会自动更新身份卡。
- 不意味着身份卡创建角色后永久不可编辑，或既有角色永远不能发生明确变化。
- 不意味着平台用户修改身份卡会自动修改任何已经存在的角色。
- 不意味着未来明确调整既有角色等同于修改原身份卡或同步所有同源角色。
- 不意味着已经决定身份卡归哪个具体产品存储、编辑或发布。
- 不意味着已经决定身份卡字段、版本、来源、评价方法、导入方式、修改权限、角色变化范围或交互设计。

身份卡需要向主持提供哪些最低协作资料，以及既有角色允许发生哪些明确变化，可以在后续 Dreaming 中继续讨论；不作为当前主线的自动下一问题。
