# Dreaming 47：Harness 保留最低限度成果痕迹，不记录工作空间变化历史

日期：2026-08-31

状态：当前阶段共识，可继续修正

## 这次只讨论什么

本次只讨论角色在本地目录、云端空间或其他工作环境中产生实际成果时，哪些内容应当进入完整 thread 记录，以及成果怎样沿既有协作责任被吸收和整理。

本次确认，thread 可以在自身上下文中关联本地 workspace 目录或其他类型的工作空间，但这种关联不会使 Harness 成为工作空间审计系统。Harness 不要求持续观察和记录角色工作过程中的每次文件增删改、工具操作或云端状态变化，只保留足以支持协作连续性和责任追溯的最低限度成果痕迹。

本次不决定成果交付格式、产物引用方式、证据表达、工作空间类型、外部操作分类、检测方式、存储结构、接口、协议、工具或实现。

## Thread 可以关联工作空间，但不接管工作空间历史

Thread 可以关联角色开展实际工作的空间，例如本地 workspace 目录或其他种类的云端空间。这项关联帮助角色理解工作发生在哪里、从哪里取得资料以及成果应当落到何处，是 thread 上下文的一部分。

关联工作空间不表示 Harness 必须掌握其中发生的全部变化。角色可以在自身权限范围内经历多次尝试、修改、撤销和重新整理，这些中间变化不因为发生在 thread 关联空间中就自动成为必须持久化的 thread 事件。

因此，Harness 不承担工作空间版本历史、全量操作审计或所有外部状态变化的保存责任。哪些工作空间可被关联、一个 thread 能否关联多个空间、角色怎样访问以及空间本身如何保留历史，均留待后续讨论或设计。

## 中间工作过程不自动进入完整记录

角色完成工作时，不需要把每一次文件增删改、工具调用、云端操作或失败尝试逐项报告给 Harness。Harness 也不因为完整记录需要可追溯，就持续收集这些低层过程。

这样可以避免大量中间噪声占据完整记录、知识维护和角色上下文，也避免主持重新成为所有工作过程的信息中转者。角色仍可在认为必要时通过普通消息说明某段过程、问题或风险，但这是角色基于协作需要作出的表达，不是所有工作的统一记录要求。

工作过程没有逐项进入 thread 记录，不表示它从未发生，也不表示相关工作空间没有留下自身历史。它只表示这些变化不属于 Harness 必须保存的协作事实范围。

## Harness 保留最低限度成果痕迹

当 Agent 角色交付委托结果时，它需要向发布者说明最终交付了什么、成果位于何处，以及足以支持接收和后续使用的必要依据。该交付作为角色消息和委托进展，自然进入完整 thread 记录。

最低限度成果痕迹包括：

- 角色最终作出的成果交付；
- 委托在协作中形成的状态与责任变化；
- 与交付、拒绝、取消、请求调整、失败或未决风险有关的必要角色消息；
- Harness 自己直接承载、执行或转发的外部操作事件。

最后一项只表示 Harness 对自己已经参与的行为保留事件记录，不表示它需要监控角色在工作空间中独立完成的全部操作，也不表示 Harness 会理解或评价外部操作的业务意义。

“最低限度”描述的是统一记录责任的边界，不禁止特定 thread、委托或角色在明确需要时提供更丰富的过程说明、证据和成果资料。

## 发布者吸收成果，重要影响才上浮主持

成果交付继续遵守 Dreaming 36 的结果吸收责任。委托结果默认交给发布者，由发布者理解成果、把它带回自身工作，并判断后续行动。

成果影响当前权威目标、整体推进、跨角色依赖、重要风险、资源使用或治理决定时，发布者再把整理后的结论、影响和必要依据明确同步主持。主持可以根据这些重要信息维护进展快照和知识检索层，也可以在权限范围内查询相关交付与历史。

主持不默认接收每项委托的全部成果，更不需要先接收所有中间产出、再替发布者完成记录和吸收。主管理员、主持或当前协作安排可以明确要求特定成果直接同步主持，但这是一项明确的协作要求，不是所有成果的默认路径。

## 接收和吸收不等于统一要求正式验收

发布者取得并理解成果，不应统一表述为已经正式验收。按照 Dreaming 10 和 Dreaming 36，委托可以要求发布者验收，也可以无需验收；两者都存在结果吸收责任。

需要验收的委托由发布者按照既有规则明确验收。无需验收的委托可以在目标角色完成后进入终态，但发布者仍需吸收对自身责任和上层工作有意义的成果。

因此，最低限度成果痕迹证明相关交付、状态或消息已经进入协作记录，不会自行产生质量认可、委托验收、目标完成或其他治理效力。是否进一步评审、验证或验收，继续遵守相应委托、目标与治理关系。

## 未成功工作保留责任痕迹，不保留全部中间产物

委托被拒绝、取消、请求调整、调用受阻或最终没有形成可用成果时，相关委托状态和必要消息仍然进入完整记录，使角色能够理解责任后来怎样变化以及为何没有正常交付。

这不要求 Harness 收集失败过程产生的全部临时文件、部分结果或外部痕迹。若某项残留结果、风险或外部影响对后续协作重要，相关角色有责任按照既有结果吸收与重要信息同步规则明确说明；Harness 不自行发现或判断其重要性。

## 对既有“完整记录”共识的细化

Dreaming 9 所说的完整 thread 记录，继续覆盖 Harness 已经承载或接收到的角色消息、委托、治理行为、确定性事件和其他协作信息。本轮明确细化它的外延：`完整`不表示 Harness 必须观察整个关联工作空间或外部世界，并把所有实际变化自动变成 thread 记录。

Dreaming 13 和 Dreaming 15 中的进展快照与知识检索层，继续以完整记录为事实来源；但它们只能整理已经进入记录的协作事实和角色表达，不能把未记录的工作空间变化当作 Harness 已知事实，也不能因为缺少逐项变化记录就推断相应工作从未发生。

Dreaming 36 的结果路由继续有效。完整记录中存在最终交付，不意味着主持必须被动接收每项结果；默认仍由发布者吸收，重要影响再同步主持。

## 这项共识暂时不意味着什么

- 不意味着 Harness 会持续扫描、监听或比较本地目录、代码仓库、云端空间或其他工作环境。
- 不意味着完整 thread 记录包含角色工作过程中的每项文件、命令、工具调用、尝试或外部状态变化。
- 不意味着工作空间自身不需要版本历史、审计或备份，只表示这些不是 Harness 的统一记录责任。
- 不意味着角色交付成果时无需说明成果内容、位置和必要依据。
- 不意味着只保留成功成果；拒绝、取消、调整、失败和重要未决影响仍需通过委托状态与必要消息保留责任痕迹。
- 不意味着所有最终成果都必须直接发送给主持或由主持亲自整理。
- 不意味着发布者接收和吸收成果就自动构成正式验收。
- 不意味着成果已经被记录就自动代表质量合格、委托验收、目标完成或治理确认。
- 不意味着已经决定成果交付格式、产物引用、证据要求、工作空间关联方式、外部操作范围、记录结构、UI、接口、协议、工具或实现。

成果在交付时至少需要哪些语义信息、不同成果怎样被引用和查看，以及特定高风险场景是否需要更强的过程记录，留给后续 Dreaming 或设计阶段讨论；不作为当前主线的自动下一问题。
