# Dreaming 51：可参与 Agent 需要程序化的 Agent 级工作边界

日期：2026-08-31

状态：当前阶段共识，可继续修正

## 这次只讨论什么

用户最初把主要编排目标描述为 CLI 类和可远程调用类 Agent，并排除桌面 App 类 Agent。在审视此前 Dreaming 后发现，这种按产品形态划分范围的说法还没有成为正式共识，也不能准确表达 Harness 真正需要的接入条件。

本次只讨论：什么样的 Agent 产品或服务可以成为 Agent 身份卡背后的参与能力，以及 Harness 是否应当把裸模型接口补造成 Agent。

本次确认，Agent 是否可参与，取决于被接入对象能否提供可靠调用、持续交互并取得结果的程序化边界，不取决于它表现为 CLI、远程服务、桌面 App 或其他产品形态。同时，被接入对象必须已经能够独立承担 Agent 级工作；Harness 不负责为裸模型补齐通用 Agent 循环。

本次不决定接入协议、适配方式、会话保存、上下文拼装、命令或 API 配置、能力声明、可靠性测试、兼容认证、失败恢复策略或其他技术实现。

## 产品形态不是参与资格

CLI 和远程 API 是当前最直观的程序化入口，但它们不是资格本身。一个主要通过桌面界面提供体验的 Agent，如果同时暴露了满足协作需要的可靠程序化边界，就不应仅因“它是桌面 App”而被排除。

反过来，一个产品即使提供命令行或 HTTP 接口，如果这个入口不能可靠接收工作、维持所需协作连续性并返回可使用结果，也不会仅因接口形态符合预期而自动成为可参与 Agent。

因此，本轮修正 Dreaming 0 中“主要编排 CLI 类和可远程调用类 Agent，不包含桌面 App 类 Agent”的初始表述。该表述仍作为历史原文保留；当前边界改为判断实际接入能力，而不是产品外观或主要交互界面。

## 角色需要逻辑上的持续协作能力

Agent 身份卡被加入 thread 后形成一个持续存在的角色。多次与该角色有关的工作和沟通，需要能够被关联到同一个逻辑角色，使它在 thread 中延续相关上下文，而不是每次都成为彼此无关的临时调用。

这种角色逻辑连续性是产品使用需要，不等于被接入 Agent 必须原生提供某一种 session 或 resume 能力。Agent 可以原生维护连续会话，也可以由它已有的接入服务或集成边界在多次调用间保留必要上下文。一个无原生会话的远程服务，只要最终接入能力能够维持角色所需的逻辑连续性，仍可以参与。

相反，只能产生彼此无关的一次性结果、无法承接同一 thread 角色后续沟通的调用边界，不足以支撑这里定义的 Agent 角色。具体需要保留哪些上下文、怎样防止上下文混杂或过度增长，留到设计阶段讨论。

## 被接入对象已经能够独立完成 Agent 级工作

程序化和可连续调用仍然只是必要条件。被接入对象还需要已经能够接收一项工作要求，自行完成该工作所需的分析与执行过程，并返回可供 thread 角色继续理解和吸收的结果；如果工作无法完成，也应能够返回明确的受阻或无法完成结果。

具体工作是否需要工具使用、环境操作、多步推理或内部恢复，因 Agent 和任务而异。本轮不规定统一内部能力清单，也不要求 Harness 观察其内部过程。边界在于：被接入对象本身已经作为一个 Agent 承担对外工作，而不是只提供下一段文本生成能力、等待 Harness 替它建立规划、行动、观察、判断和重试的通用循环。

Harness 可以为协作提供 thread 上下文、消息路由、权限边界、历史与知识查询、资源约束和自己明确承载的外部能力，但这些协作支持不会把缺少 Agent 级执行能力的裸模型接口自动变成可参与 Agent。

## 裸模型不是自动符合范围，已有 Agent 包装可以符合

裸 LLM API 本身不因能够接收文本并返回文本就自动属于可参与 Agent。若本项目为了接入裸模型而负责补齐通用 Agent 循环，就会从“编排已有优秀 Agent”扩张为通用 Agent 开发框架，重新承担用户希望借助成熟 Agent 产品避免自行建设的能力范围。

这不意味着某个底层模型永远不能参与。如果用户或第三方已经在模型外构建了能够独立承担 Agent 级工作的 Agent 服务、工具或其他可调用包装，那么判断对象是这个完整的接入能力，而不是其底层是否使用裸模型 API。只要完整能力满足程序化调用、角色逻辑连续性和结果取得边界，就可以作为 Agent 身份卡背后的候选能力。

同理，厂商品牌或产品名称也不自动证明资格。同一个产品在不同调用入口、模型、插件、工具、记忆和环境配置下可能具有不同能力，仍需要按照用户实际接入的完整能力理解，而不是把产品宣传或通用印象当成事实。

## “可靠边界”不等于永不失败或结果永远正确

可靠调用表示存在足以让 Harness 明确发起工作、关联输入输出并获得可作为本次调用结果使用的返回边界，不表示 Agent 永不出错、从不超时或每次结果都高质量。

按照 Dreaming 26，Agent 正常返回“无法完成”或“受到阻塞”仍是一次成功发生的沟通和工作结果；Harness 无法可靠启动、连接、恢复所需连续性或取得可用返回，才属于调用边界故障。是否适合参与也不能被简化为某次调用是否成功，而应理解为该接入能力是否总体具备被持续协作调用的产品边界。

Harness 不负责判断 Agent 的工作结论是否正确或充分，也不以替代 Agent 内部循环的方式弥补质量不足。具体如何描述、验证和呈现接入能力的可靠性与适用范围，留待后续讨论。

## 与既有共识的关系

Dreaming 1 确认项目要减少真人在多个 Agent 之间持续补位，Dreaming 3 确认价值来自组合不同 Agent 的比较优势。本轮进一步说明，这些 Agent 是已经具备对外工作能力的可调用参与能力，而不是由 Harness 临时补造的裸模型执行体。

Dreaming 4 和 Dreaming 5 已经区分 Agent 产品、身份卡和 thread 角色。本轮不把产品入口直接等同于角色，而是确认身份卡背后的完整 Agent 能力需要足以支持角色的持续协作；同一个 Agent 产品的不同配置仍可能形成不同身份卡与独立角色。

Dreaming 26 已经把成熟 Agent 的内部执行与恢复同 Harness 调用边界区分开。本轮把这一责任边界上升为参与范围：Harness 不进入 Agent 内部重建通用执行循环，只处理自己可以客观承载的协作与调用边界。

Dreaming 48 要求 Harness 支持免去真人逐轮协调的连续推进。如果接入对象只能进行互不相关的单次生成，或每一步都需要真人替其重新组织工作，就无法支撑这一核心能力。角色逻辑连续性因此是参与范围的一部分，但不预设具体会话实现。

Dreaming 49 的领域无关边界继续有效。Agent 级工作可以发生在软件开发、内容创作、数据分析或其他领域；本轮不把“Agent 级”限定为会写代码或必然使用某类工具。

## 这项共识暂时不意味着什么

- 不意味着只允许 CLI 或远程 API，也不意味着桌面 App 产品必然被排除。
- 不意味着任何提供 CLI、API、SDK 或文本输入输出的产品都自动符合参与范围。
- 不意味着 Agent 必须原生支持固定形式的 session、resume 或长期记忆。
- 不意味着 Harness 负责把裸模型 API 建设成通用 Agent，或自行实现另一套通用规划与工具循环。
- 不意味着使用裸模型作为底层的既有 Agent 服务不能参与；判断的是完整接入能力。
- 不意味着所有 Agent 必须具有相同工具、推理深度、内部重试或工作方式。
- 不意味着可靠边界要求调用永不失败、Agent 永不受阻或工作结果永远正确。
- 不意味着 Harness 负责评价 Agent 结果质量、验证厂商宣传或替代用户对身份卡能力的实际判断。
- 不意味着已经决定支持哪些具体 Agent、哪些入口作为内置预设，或首个版本包含什么。
- 不意味着已经决定适配器、协议、命令、API、会话、历史携带、可靠性检测、认证或扩展机制。

具体 Agent 能力如何被描述、验证和适配，以及内置支持与用户自定义接入之间怎样划分，留到后续 Dreaming 或设计阶段讨论；不作为当前主线的自动下一问题。
