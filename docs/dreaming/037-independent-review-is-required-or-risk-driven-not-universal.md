# Dreaming 37：独立评审按明确要求或语义风险发生

日期：2026-08-27

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 36 已经确认委托发布者怎样吸收结果并同步重要影响。本次继续讨论：结果形成后是否都要由另一个角色独立评审，以及谁决定需要评审。

本次确认，独立评审不是所有委托结果的统一必经步骤。存在明确评审要求时必须进行；没有明确要求时，由主持或委托发布者根据结果的重要性、风险、不确定性和可逆性等实际语义按需安排。

本次不决定评审类型、风险等级、强制规则表达、评审模板、通过标准、角色选择算法、通知、UI、接口、协议、数据结构、状态机、模块或实现。

## 独立评审不是所有成果的默认步骤

不同委托的质量风险并不相同。简单查询、低影响且容易纠正的工作，如果统一要求另一个角色再次检查，会增加调用次数、等待时间和资源消耗，却不一定带来相称的质量收益。

因此，Harness 产品不把“每项委托交付后必须交叉评审”设为普遍规则。没有明确要求时，一项结果可以由发布者直接吸收，并根据原委托是否需要验收继续处理。

这不削弱多 Agent 交叉评审的核心价值。独立评审应当集中用于它确实能够降低风险、暴露遗漏或提高判断可信度的场景，而不是为了形式完整机械发生。

## 明确要求评审时必须执行

权威目标、委托条件、主管理员的治理决定、当前阶段安排或其他当前有效的明确规则，可以要求某类成果在继续推进前完成独立评审。

存在这类要求时，主持或发布者不能因为时间、成本或主观上认为结果已经足够好而静默跳过。资源预算或角色可用性使评审暂时无法开展时，应按照既有治理边界暴露阻塞或请求决定，而不是把未评审结果伪装成已经满足要求。

“必须进行评审”只表示需要产生一次符合当前要求的独立评审，不自动表示必须获得赞同、零问题或某种固定的“通过”结论。某项规则如果还要求取得特定评审结论，必须另有明确表达；本轮不统一规定。

## 没有明确要求时由角色作语义判断

没有强制评审要求时，主持或委托发布者可以结合具体结果，判断独立评审是否值得发生。当前可考虑的因素包括成果的重要性、潜在影响、出错代价、不确定性、不可逆性、目标角色是否可能存在盲区，以及发布者自身是否具备足够判断能力。

这些只是帮助理解的候选因素，不是固定评分表或统一阈值。何时值得多花一次调用成本来换取额外信心，是角色基于工作内容作出的语义判断；Harness 不根据文本、文件数量、金额或其他表面特征自动决定。

可选评审仍受角色权限、审批策略和资源预算约束。预算充足不会自动触发评审，预算紧张也不会让 Harness 自行降低质量要求；主持和发布者需要在现有边界内作出安排。

## 独立评审通过单独委托发生

独立评审是一项新的工作责任，应当通过一项独立委托交给不同于原成果生产者的合适角色。评审角色获得足以开始评审的上下文，在自身权限内查询依据，并交付评审结果；这些行为继续遵守普通委托和 Dreaming 35 的起步上下文规则。

原目标角色对自己的成果进行复查可以是有价值的自检，但不属于这里所说的独立评审。独立性来自另一角色以评审责任重新检查成果，而不是原角色换一种说法再次确认自己。

同一成果需要多个角色各自独立评审时，应分别发布多项评审委托，每项仍只有一个目标角色。这沿用 Dreaming 10 的单一负责角色原则，不建立多人共同负责的一项评审委托。

## 评审委托与原委托保持独立

评审委托拥有自己的发布者、目标角色、交付结果、是否需要验收以及生命周期。它不会因为引用原成果，就自动成为原委托内部的隐藏步骤或把评审角色变成原委托共同负责人。

评审角色负责给出评审发现、判断和建议，不自动获得原委托的验收权。原委托发布者需要吸收评审意见，再根据原委托要求和适用治理决定是否验收、要求修改、补充调查或采取其他行动。

主持可以在有权限且适合的情况下安排评审；如果主持不是原委托发布者，评审结果仍需明确送达或同步给原发布者，使其履行原委托的结果吸收与验收责任。评审的发起不会把原发布者责任转交给主持。

评审发现问题也不会由 Harness 自动把原委托改为失败、拒绝或取消。它是一项需要角色理解和处理的工作结果；只有明确、有效的后续行为才改变原委托或推进安排。

## Harness 执行明确要求，不评价成果质量

Harness 可以记录并执行已经明确形成的评审要求、路由评审委托、持久化结果，并继续执行角色权限、审批策略与资源预算。

Harness 不理解成果质量，不判断结果是否可靠，不替角色选择评审者，也不从自然语言或成果内容中自动推断必须评审。是否存在语义风险、评审者是否真正合适、评审意见是否充分以及下一步怎样处理，仍由 Agent 或真人角色判断。

具体怎样让强制评审要求具有可确定执行的表达、怎样证明要求已经满足，以及评审与原委托状态怎样关联，属于后续设计问题，本次不深入。

## 这项共识暂时不意味着什么

- 不意味着所有委托结果都默认需要独立评审。
- 不意味着不强制评审的结果就不允许被评审。
- 不意味着原成果生产者的自检等同于独立评审。
- 不意味着独立评审必须由主持亲自完成，或主持必须接收全部原始评审内容。
- 不意味着评审角色会自动取得原委托验收权或共同负责原委托。
- 不意味着完成独立评审自动等于评审通过，也不意味着发现问题会自动改变原委托状态。
- 不意味着资源不足可以静默绕过当前有效的强制评审要求。
- 不意味着 Harness 会理解质量、风险、独立性或评审意见，并自动决定是否评审或怎样处理。
- 不意味着已经决定评审分类、风险等级、触发条件、通过标准、角色选择、模板、通知、UI、接口、协议、数据结构、状态机、模块或实现。

独立评审发现问题后，修改工作应当怎样回到原目标角色，以及评审—修改—复审怎样形成可持续但不过度僵化的闭环，留给后续 Dreaming 继续讨论。
