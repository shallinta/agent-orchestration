# Dreaming 38：委托终态只关闭工作责任，不关闭相关沟通

日期：2026-08-27

状态：当前阶段共识，可继续修正

## 这次只讨论什么

Dreaming 37 已经确认独立评审何时发生以及它与原委托的责任边界。本次继续讨论：委托、普通消息和角色持续沟通之间是什么关系，以及一项委托进入终态后究竟关闭什么。

本次确认，委托是一项独立跟踪的工作责任，不是承载一段对话的会话容器。委托终态永久关闭并冻结这项责任，但不会关闭相关话题、角色关系或普通沟通空间。

本次不决定委托状态枚举、状态转换、消息引用格式、历史关联结构、查询交互、通知、UI、接口、协议、数据结构、模块或实现。

## 普通消息不属于某项委托

角色之间的普通消息属于 thread 协作记录，不因为内容谈到了某项委托、询问了某项结果或延续了此前讨论，就成为该委托内部的一部分。

委托不会圈定一段专属对话，普通消息也不需要标记为“属于某项委托”。同一段角色沟通可以提到多个当前或历史委托，也可以从一项工作自然转向另一项话题；这些消息继续按照普通路由和完整记录规则存在。

角色可以在消息中明确引用某项委托，帮助其他角色定位背景和查询依据。引用表示这项历史责任与当前沟通相关，不会让消息加入委托生命周期、改变委托状态或自动形成新的工作责任。

Dreaming 10 已经确认，创建委托时的结构化发布消息需要和独立委托记录建立关联。本轮不否定这项创建证据关系；它只进一步明确，后续围绕委托发生的普通沟通不会因此成为委托的子记录或专属会话。

## 终态只终结可跟踪责任

委托进入终态后，表示这项独立跟踪的工作责任已经按照适用方式结束。Harness 必须保证终态委托不能重新启动，也不能再回到进行中、等待验收或其他非终态状态。

终态不可变保护历史责任的可追溯性：后来又发现问题、形成新认识或继续交谈，都不能改写“当时这项委托已经以某种结果结束”的事实。

这并不意味着相关成果永远正确、话题已经穷尽、角色不得再询问，也不意味着所有后续工作都已经完成。终态冻结的是委托自身的责任与状态，不是现实世界中的问题，也不是 thread 的持续协作。

## 终态后仍可继续普通沟通

委托发布者、目标角色、评审角色或其他具备相应消息权限的角色，可以在委托终态后继续讨论其内容、解释结果、追问依据、提出质疑、比较新情况，或把它作为共同经历和经验引用。

这些沟通不需要为了“允许继续说话”而重开旧委托。无论一项委托是否需要验收、通过何种方式进入终态，普通消息通道都不会随委托关闭。

终态后的追问和回复仍只是普通消息，不自动修改旧委托，也不自动产生新的持续责任。普通消息中即使出现“请再看一下”之类的请求，Harness 也不根据自然语言自行判断它是在延续旧委托或创建新委托。

## 新的可跟踪责任需要新委托

如果终态后出现相关或相似问题，并且角色希望形成一项新的、由唯一目标角色承担并持续跟踪的工作责任，就需要明确发布一项新委托。

新委托可以在描述中引用一个或多个历史委托，使目标角色知道哪些旧责任、交付、评审和讨论可能与当前工作有关。历史引用提供上下文线索，不会继承旧委托状态、目标角色、验收结果或责任，也不会把新旧委托合并成一项责任。

是否需要把后续交流升级为新的可跟踪委托，由拥有发布权限的角色根据工作需要作出语义决定。Harness 仍只从明确、机器可识别的委托发布行为创建新责任，不从普通消息内容推断。

## 历史委托上下文是公共查询能力的一部分

有相应角色权限的角色可以查询历史委托的内容、状态、结果和可访问的相关 thread 记录，取得理解当前工作所需的上下文。这属于 thread 历史记录、上下文和知识检索公共能力的一部分，不只为主持或原委托参与角色提供。

新委托引用历史委托，是帮助目标角色快速定位资料的相关性线索，不替代它在权限范围内主动查询，也不临时扩大或缩窄查询权限。

历史委托及其结果进入知识检索层，不会自动把其中的判断升级为当前事实或权威结论。角色需要时仍可回查完整记录，理解历史委托在当时怎样形成和结束。

## 评审沟通与修复决定遵守同一边界

评审角色完成独立评审后，只需要围绕评审责任与评审委托发布者沟通和交付意见，不负责直接与原成果生产者建立修复闭环。评审委托进入终态后，双方仍可以通过普通消息继续提问和讨论评审内容。

原委托发布者收到独立评审意见，或者通过自己的检查形成判断后，自行决定是否联系原目标角色、亲自修复、改变尚未终结的原委托状态、安排一次或多次修复，或采取其他行动。评审意见不会自动替它作出这些决定。

如果原委托已经进入终态，就不能为了修复而重开。需要形成新修复责任时，应发布新委托并按需引用原委托和评审委托；只需要继续解释或讨论时，使用普通消息即可。

## 验收属性不由委托用途决定

是否需要发布者验收，是每项委托由发布者设置的独立属性，不由委托属于开发、查询、修复还是评审等用途自动决定。

因此，评审委托既可以设置为需要验收，也可以设置为无需验收。需要验收时，评审发布者在结果交付后决定是否验收；无需验收时，评审角色完成后委托可以直接进入终态。两种情况下，角色都仍可继续通过普通消息讨论评审内容。

本轮明确否定“为了允许评审发布者继续追问，所有评审委托都必须需要验收”的推导。沟通能否继续与委托验收属性无关。

## Harness 保证边界，不理解对话意图

Harness 负责持久化普通消息和委托记录、执行明确路由、提供权限受控的历史查询，并确定性保证终态委托不可重启或修改为非终态。

Harness 不判断一条普通消息语义上属于哪项委托，不因角色继续讨论历史工作就改变委托，也不从“继续修改”“再看一下”等自然语言自动创建新责任。是否发布新委托、引用哪些历史责任以及怎样处理评审意见，仍由 Agent 或真人角色决定。

## 这项共识暂时不意味着什么

- 不意味着终态后角色不能继续讨论、追问或引用委托内容。
- 不意味着普通消息需要成为某项委托的子记录或专属对话。
- 不意味着消息引用历史委托会改变、重启或合并委托。
- 不意味着终态委托可以因为发现新问题、继续沟通或需要修复而重新打开。
- 不意味着终态后的每条相关消息都会自动产生新委托。
- 不意味着无需验收的评审委托结束后，评审发布者不能继续与评审角色交流。
- 不意味着评审角色负责直接指挥原成果生产者修复。
- 不意味着新委托引用旧委托就继承其角色、状态、验收或责任。
- 不意味着所有角色拥有相同的历史查询范围；实际可见内容仍受角色权限控制。
- 不意味着 Harness 会理解消息意图、自动关联对话、生成委托或判断修复方式。
- 不意味着已经决定委托状态枚举、消息引用、历史关联、检索、UI、接口、协议、数据结构、状态机、模块或实现。

当一个阶段中的委托、评审和修复逐渐完成后，主持怎样判断当前阶段已经足够、需要进入下一阶段或需要主管理员决定，留给后续 Dreaming 继续讨论。
