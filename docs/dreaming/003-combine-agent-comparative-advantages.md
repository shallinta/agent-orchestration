# Dreaming 3：组合不同 Agent 的比较优势

日期：2026-08-12

状态：当前阶段共识，可继续修正

## 这次只讨论什么

这次只讨论为什么需要多个 Agent，以及“多”本身是否构成价值。不讨论如何选择和分派 Agent，也不定义身份资料卡的字段或调度算法。

## 来自初始想法和补充说明的事实

- 不同 Agent 在推理质量、执行速度、擅长领域等方面可能各有长短。
- 调用价格是一个同样重要的现实因素。更强、更慢或更贵的 Agent 不一定适合承担所有工作。
- Codex 负责方案和评审、Claude Code 负责执行和返修，只是一个用户在特定配置下的真实例子，不是所有用户都适用的默认分工。
- 即使使用同一种 Agent 产品，不同模型、插件、长期记忆和其他配置也会使实际能力与表现产生明显差异。
- 每个用户需要根据自己的实际使用感受理解和标记可用的 Agent，而不能完全依赖产品名称或通用评价。

## 共同确认的核心需求

多 Agent 的价值不在参与者数量，也不在追求“多 Agent”这一形式，而在于有意识地组合不同 Agent 的比较优势。

这种比较优势至少可能来自：

- 思考和结果质量；
- 执行或响应速度；
- 调用价格与预算效率；
- 特定领域、任务类型或工作阶段的能力；
- 可用模型、工具和插件；
- 已积累的长期记忆和上下文；
- 用户在真实使用中观察到的其他特征。

项目希望让适合某类工作的 Agent 发挥局部长处，再通过分工、协作和交叉检查，争取获得单个 Agent 难以同时达到的质量、速度、成本和能力覆盖。

理想结果不是在所有维度都追求最高，而是在特定用户、特定任务和特定约束下形成更好的整体组合。

## 一个重要边界

比较优势不能静态绑定到 Agent 的品牌或产品类别。

“Codex 适合设计、Claude Code 适合执行”只描述了一个具体用户在一组具体模型、插件、记忆和使用条件下的经验。换一个用户、模型、安装环境、长期记忆或任务领域，结论可能完全不同。

因此，系统未来如果使用 Agent 特征进行协作，就必须容纳用户自己的经验判断，并允许这些判断随实际表现变化。这里尚未决定这种信息如何表示、如何验证或是否自动更新。

## 这项共识暂时不意味着什么

- 不意味着每个任务都必须调用多个 Agent。
- 不意味着更多 Agent 一定带来更好结果。
- 不意味着固定角色分工优于动态选择。
- 不意味着系统已经知道如何衡量质量、速度、价格或擅长领域。
- 不意味着用户标签是客观真理或永远不变。
- 不意味着 Agent 之间必须通过投票达成一致。

“身份资料卡描述的究竟是什么”“用户经验标签具有多大约束力”“如何从实际协作中修正认识”，都留给后续 Dreaming 分别讨论。
