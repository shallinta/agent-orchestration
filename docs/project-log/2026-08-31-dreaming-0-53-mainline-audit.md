# Dreaming 0–53 阶段性主线审计

日期：2026-08-31

性质：阶段性产品认识审计，不是新的 Dreaming、产品决策、版本范围或实现计划

## 为什么做这次审计

Dreaming 已经从最初痛点连续讨论到角色、thread、目标、委托、治理、上下文、自治、运行边界、客户端边界、Agent 参与资格和 Harness 公共协作能力。随着记录增多，需要重新回答三个问题：

1. 最初构想中的核心问题是否已经获得连贯回答；
2. 哪些内容属于 Harness 核心，哪些只是支撑能力、运行细节或相邻产品；
3. 当前是否仍有会动摇整体产品定义的缺口，而不是因为文档中存在“以后再讨论”就机械地继续展开。

本审计以 Dreaming 0 为历史输入，对照 Dreaming 1–53 的后续共识。发生冲突时始终以后编号记录为准；旧 Dreaming 不回写。审计只检查产品认识覆盖面，不判断实现难度，不形成 `v0.0.1` 范围。

## 总体结论

Dreaming 0–53 已经形成一条可以独立复述的核心产品主线：

> 用户希望组合多个成熟 Agent 的比较优势，却被迫持续承担上下文搬运、任务转达、反馈中转和推进催促。Harness 以 thread 为持续协作上下文，把身份卡实例化为彼此隔离的角色，由唯一 Agent 主持承担语义上的组织与推进，由唯一用户主管理员保留权威目标和最高治理决定。角色通过消息和 Agent 间委托协作，Harness 承载共同事实、公共协作能力和确定性约束，使 Agent 可以在权限、审批与预算允许时连续推进，而用户只在关键判断点重新介入。

这条主线同时具备明确边界：Harness 不替角色理解语义，不开发通用 Agent，不把裸模型补造成 Agent，不接管成熟 Agent 的全部内部工具，不审计工作空间中的所有变化，不拥有跨 thread 项目知识与身份卡评价，也不依赖某个 UI 才能成立。

因此，可以把当前视为“核心产品认识形成第一个阶段性闭环”的里程碑。它不表示所有需求已经讨论完毕，也不表示应立即进入版本规划；它表示后续 Dreaming 应由真实缺口、边界冲突或新用户场景驱动，而不再因为想象中可能存在更多功能就横向扩张。

## 对 Dreaming 0 最初构想的覆盖检查

### 已经被保留并澄清的核心意图

- **组合多个成熟 Agent 的能力。** Dreaming 3 将速度、质量、价格、领域能力、模型、插件、记忆和用户经验统一为相对比较优势；Dreaming 51 明确被接入对象已经能够承担 Agent 级工作。
- **减少真人充当消息转发员。** Dreaming 1、2 和 48 从痛点、期望角色和可感知体验三层确认了这项产品价值。
- **由主 Agent 持续组织协作。** “主 Agent”已经演进为附加唯一`主持`系统标签的 Agent 角色，并在 Dreaming 29–43 中形成从初始意图到完成提议的连续职责。
- **人保留关键签字与决策。** 唯一`主管理员`用户角色负责目标确认和最高治理判断；平台用户与 thread 内用户角色的权力来源已经分开。
- **身份卡支持不同协作者。** 身份卡与角色已经分离；身份卡由平台用户在 Harness 核心之外维护，Harness 不自动评价或更新。
- **消息、分派、评审与返修。** 普通消息、委托、独立评审、结果吸收、修复沟通和终态责任已经形成相互一致的产品语义。
- **并行、预算、审批和故障。** 已经形成产品约束关系，但没有提前收敛默认规则、状态结构或实现。
- **进展与知识沉淀。** 完整记录、进展快照、知识检索层、入场上下文和最低成果痕迹已经区分事实与派生视图。
- **用户加入 thread。** 用户不再被视为“特殊高权重 Agent”，而是通过用户身份卡产生用户角色，并可拥有主管理员或其他系统标签。
- **UI 与核心分离。** Harness 承载 thread 事实，Electrobun、Web、飞书、Telegram 等只是能力不等的访问入口。
- **非代码场景。** 核心保持领域无关，但软件开发继续作为最真实、最重要的初始验证场景。

### 已经被修正或收缩的初始表达

- **“每个需求一个 thread”不再是产品定义。** Dreaming 12 确认 thread 可跨多个连续权威目标，如何划分由用户决定。
- **“只接 CLI 和远程 Agent、排除桌面 App”不再按产品形态判断。** Dreaming 51 改为可靠的程序化 Agent 级工作边界。
- **脑暴不需要 Harness 特殊模式。** Dreaming 16 确认多角色讨论使用普通协作能力，由主持理解和组织具体互动方式。
- **完整记录不等于外部世界全量审计。** Dreaming 47 把范围限定为 Harness 承载或实际接收到的协作事实与最低成果痕迹。
- **Harness 不自动形成业务知识。** 快照和知识检索由 Agent 或真人进行语义维护，Harness 只负责确定性触发、保存和查询边界。
- **Harness 不代理 Agent 的全部动作。** Dreaming 53 只把 thread 公共协作事实和 Harness 自己提供的连接能力纳入其直接责任。
- **身份卡评价不属于 Harness。** Dreaming 52 把长期人才评价、自动画像与跨 thread 更新移到外围工具或未来相邻产品。

## 当前核心、支撑与外围的分层

### 第一层：已经闭环的 Harness 核心主干

这部分直接回答项目为什么存在以及一次 thread 如何产生价值：

1. 组合成熟 Agent 比较优势，减少真人持续协调；
2. 以身份卡创建 thread 内独立角色；
3. 每个 thread 同时具有唯一 Agent 主持和唯一用户主管理员；
4. 从初始意图开始，经目标确认、近期安排、消息与委托协作、结果吸收和风险评审，走向目标完成提议；
5. Harness 承载共同事实、公共协作行为与确定性约束，角色负责语义判断；
6. 在治理边界允许时，协作可以不依赖真人逐轮中转而连续推进；
7. 核心不依赖单一 UI、特定业务领域或特定 Agent 品牌。

任何后续产品描述若不能保持这条主干，或者重新要求用户持续转发消息，就应被视为偏离核心问题。

### 第二层：已经确认、但不需要继续横向展开的支撑能力

进展快照、知识检索、入场上下文、预算、审批等待、并发、待处理顺序、截止、调用故障、角色停用、定时任务、心跳检测和 Channel 分发都具有真实产品价值，也与主干兼容。

但其中大量未决问题是默认值、细分类别、具体交互或可靠性策略。它们不再构成“产品是什么”的空白。除非出现新的用户场景、矛盾或风险，不应只因为某份 Dreaming 结尾写着“以后再讨论”就逐条深入。

### 第三层：已经明确移出 Harness 核心的职责

- 跨 thread、跨项目的知识、进展和项目组合管理；
- 身份卡创建过程、能力评价、长期声誉、市场和自动更新系统；
- 自研通用 Agent，或为裸模型补齐规划与工具执行循环；
- 全量工作空间历史、外部世界状态和所有 Agent 工具调用审计；
- 所有 Agent 外部动作的统一代理网关；
- 固定的软件开发阶段、通用 DAG 或特殊脑暴流程；
- 由某一个 UI、消息 Channel 或客户端拥有 thread 事实。

这些方向有些已经记录为相邻产品或未来工具，有些是明确非目标。它们不能因未来可能有价值，就重新混入 Harness 核心职责。

### 第四层：已经保存、需要等设计阶段重新评估的实现线索

- 声明式与可编程 Agent 接入扩展；
- 主持标签附加职责提示；
- 委托记录与委托消息的创建顺序；
- 角色状态变化与等待通知的发布订阅思路；
- 调用结果无法确认时的恢复与幂等问题；
- 通过本地 MCP server 暴露 Harness 公共能力。

这些线索不应被当成当前架构决定。进入设计阶段时可以保留、替换或放弃。

## 后编号记录对早期认识的主要覆盖关系

当前没有发现一组无法用“后编号优先”解释的核心矛盾。需要阅读者特别注意的覆盖关系包括：

- Dreaming 12 修正 Dreaming 6 中 thread 与单项有界目标近似绑定的表达；
- Dreaming 9 修正 Dreaming 8 中把 Thread 配置权归于主管理员角色的表达；
- Dreaming 10 把委托从一般任务消息中独立出来，并限定一项委托只有一个目标角色；
- Dreaming 34 修正主持默认可以申请引入角色的无条件理解；
- Dreaming 36 把委托默认结果责任明确归回发布者，而不是一律回主持；
- Dreaming 39 移除 Dreaming 33 和 38 中“阶段”可能产生的平台通用语义；
- Dreaming 41 将委托发布、承接与验收限定在 Agent 角色之间；
- Dreaming 47 收窄 Dreaming 9 中“完整记录”可能被误读为外部世界全量记录的范围；
- Dreaming 51 修正 Dreaming 0 按 CLI、远程和桌面 App 形态划分 Agent 的方式；
- Dreaming 52 回答 Dreaming 3、4 中身份卡评价与持续变化的开放问题；
- Dreaming 53 进一步明确 Dreaming 11、26、47 和 50 之间的公共能力与 Agent 内部工具边界。

## 仍然存在的真正核心张力

### Agent 原生能力与角色约束的保证边界

Dreaming 18 把角色权限、审批策略和资源预算定义为自治程度的三项正交约束，Harness 应当确定性执行适用边界。Dreaming 53 又确认，成熟 Agent 可以保有 Harness 不逐项代理和观察的原生工具、插件、文件与外部服务能力。

两者之间存在当前最值得继续 Dreaming 的产品问题：

> 当 Agent 通过原生能力行动时，平台用户看到的“角色权限、审批和预算”究竟代表 Harness 能够强制保证的限制，还是其中一部分只能依赖 Agent 配置、运行环境或信任声明？

这不是单纯的权限实现问题，因为它会直接影响用户对“禁止访问某目录”“外部动作必须审批”“最多消费多少资源”等产品承诺的理解。若 Harness 无法观察或阻止某类原生能力，却仍把对应配置展示成已强制执行，就会产生虚假的安全感；若要求所有动作都经 Harness，又会推翻 Dreaming 53 并把产品扩张成通用工具代理。

后续可把这作为 Dreaming 54 的候选中心问题，讨论用户应获得什么层级的保证以及无法强制时应怎样诚实表达。本审计不替该讨论作出结论，也不讨论沙箱、进程、凭证或协议实现。

## 其他未决问题为什么暂不算核心缺口

- **Harness 公共能力的最小清单**可以从已经确认的消息、委托、查询、审批、知识和定时等产品概念中逐步选择，属于后续产品范围与设计，不会改变 Harness 的基本定义。
- **Agent 适配、会话恢复、MCP、调用协议和错误结构**属于设计问题，角色逻辑连续性与调用故障边界已经在产品层得到回答。
- **管理员标签的具体局部治理能力**是多真人协作扩展，单一主管理员与主持的核心治理关系已经成立。
- **定时、心跳、回复等待和停用的更多边缘行为**可以按真实使用问题继续讨论，不妨碍主协作旅程成立。
- **内置专用主持 Agent、身份卡工具和项目管理工具**属于未来产品方向，不是当前 Harness 核心缺口。
- **如何量化“用户可以离开”**已经明确不采用程序化验收，未来只能通过试验和用户体验观察继续认识。

## 阶段性里程碑判断

当前 Dreaming 已经走完“从最初痛点到完整核心产品定义”的第一段大道。接下来仍可以继续很久，但继续的意义将从“定义项目究竟是什么”逐渐转为：

- 解决少数会影响用户信任和产品承诺的边界张力；
- 根据具体用户场景补齐必要行为；
- 记录新的远期灵感或相邻产品，而不混入核心；
- 在用户明确决定时，为版本规划提供经过审计的需求来源。

因此，Dreaming 没有总量意义上的终点，但已经到达第一个可靠里程碑。下一步不应按编号惯性继续，而应优先讨论上述 Agent 原生能力与角色约束保证的张力；完成后再判断是否还有同等级核心问题。
