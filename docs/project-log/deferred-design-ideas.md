# 延后设计线索

这里保存 Dreaming 过程中自然出现、但尚未到设计阶段的实现方向。它们不是已确认方案，也不影响当前需求共识；未来进入设计阶段时再重新评估，届时可以修改或放弃。

## 参与者接入的扩展等级

为适配不同 CLI Agent 和远程 API，未来可以比较两个互补的扩展等级：

- 简单声明式接入：允许用户配置创建和继续会话等常规调用信息，适合行为规整的参与者来源。
- 可编程接入：用于处理会话标识解析、流式输出、复杂状态、鉴权、错误语义等仅靠简单配置难以表达的差异。

当前不决定两者是否都需要，也不设计配置格式、扩展接口或执行方式。

## 主参与者的额外职责提示

身份资料卡描述参与者本身；同一身份被选为某个 thread 的主参与者后，还需要获得属于主参与者角色的额外职责信息，例如理解整体目标、拆分与分派工作、吸收结果、判断下一步、识别需要用户决策的时刻，并持续推动协作走向预期成果。

一个自然出现的实现思路是：Harness 向数字主参与者发送信息时，除了依据其身份资料卡组织内容，还附加一段主参与者专属的固定提示词。当前只保存这条线索，不讨论提示词内容、注入时机、是否固定，或真人担任主参与者时如何对应。

## 委托独立记录与消息的创建顺序

Dreaming 10 确认结构化委托消息需要作为会话消息持久化，委托也需要独立持久化并与消息关联。讨论中自然出现了两种创建顺序：

- 消息先行：Harness 解析结构化委托消息后创建独立委托记录，再把记录 ID 关联或附加到消息。
- 记录先行：发布角色先调用 Harness 内部工具创建独立委托记录，再在结构化消息中携带记录 ID，Harness 据此识别这是一条委托消息。

这两种顺序目前都只是延后设计线索。本记录不比较优劣、不选择方案，也不决定结构化消息、内部工具、记录 ID 或关联方式的具体设计。

## 角色可用状态变化与等待通知

Dreaming 19 讨论审批等待期间的角色可用状态时，用户提出了几条未来实现线索：角色可用状态发生变化时产生事件；为明确选择等待的发信者注册恢复响应；或者使用发布订阅方式分发恢复可用的变化。

这些都只是未来进入设计阶段时重新评估的候选思路，不表示已经选择状态变化事件、注册响应、发布订阅或它们的组合，也不决定队列、并发、通知或消息重投的实现。
