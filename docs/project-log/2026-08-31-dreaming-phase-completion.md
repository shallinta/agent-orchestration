## 为什么现在可以完成

Dreaming 的目标不是穷举未来所有功能，也不是提前解决全部设计问题，而是回答项目最根本的产品问题：真实痛点是什么，本项目应当解决什么，理想协作怎样发生，需要哪些产品概念，以及责任和信任边界在哪里。

Dreaming 0–53 主线审计已经确认核心产品认识形成闭环，并找到当时唯一会影响产品承诺的核心张力：Agent 可以保留 Harness 无法逐项代理的原生能力，而角色权限、审批和预算又容易被误解为覆盖角色全部行为。Dreaming 54 进一步确认约束必须公开真实保证强度，使这项张力得到当前阶段足够可靠的回答。

审视其余显式未决事项后，没有发现另一个会动摇 Harness 核心定义的同等级空白。剩余问题主要是产品设计细节、技术实现选择、远期扩展，或者必须通过实际使用才能获得证据的问题。继续为了清空“尚未决定”而机械增加 Dreaming 编号，会让讨论重新横向扩张，偏离这一阶段的直接目的。

## Dreaming 形成的核心成果

### 1. 找到了真实问题和产品价值

项目要解决的不是缺少一个更聪明的 Agent，而是多个各有优势的成熟 Agent 不能自然维持共同工作，迫使真人持续重组上下文、编写提示词、转交任务、搬运反馈、催促进展并判断下一步。

Harness 的核心价值是承接这些协作空隙，使真人从持续在线的消息转发员和协调者，转变为关键判断点的决策者与最终责任人。产品必须支持在治理边界允许时无需真人逐轮中转的连续推进，否则只是连接了多个 Agent，并没有真正解决原问题。

### 2. 明确了 Harness 协调的基本单位

平台用户维护身份卡这份可复用的声明性“简历”；身份卡每次加入 thread 都产生一个只属于该 thread 的独立角色。同一张身份卡可以多次加入，同一种底层 Agent 也可以通过不同角色保持上下文和职责隔离。

Harness 协调的是 thread 内角色，而不是直接调度 Agent 产品名或平台用户账号。Agent 和真人都可以通过角色参与，但两者的能力与责任并不因此相同。

### 3. 明确了 thread 及其治理骨架

Thread 是由用户划定边界的持续协作上下文，不等同于聊天会话、固定时间段、单个需求或整个项目。一个 thread 可以先后承载多个权威目标，也可以在没有当前权威目标时继续保留；目标完成不会自动结束 thread。

每个 thread 同时只有一个附加`主持`系统标签的 Agent 角色，以及一个附加`主管理员`系统标签的用户角色。主持理解、组织并持续推进协作；主管理员在 thread 内确认和修改权威目标并承担最高治理判断。平台用户在 UI 或 API 中拥有的 Thread 配置权，不能与角色系统标签的权力混为一谈。

### 4. 形成了从初始意图到目标完成的协作旅程

Thread 创建后可以先接收模糊的初始意图。主持可以在目标确认前组织受约束的探索性协作；权威目标必须由主管理员明确确认，并至少说明预期结果与完成判断依据。

目标确认后，主持形成足以继续推进的近期安排，选择已有角色、组织消息和委托、发现能力阻塞、吸收整体进展并在有依据时提出目标完成。主管理员决定目标是否完成；目标完成不会自动改变未终结委托，也不会自动结束 thread。

### 5. 区分了普通沟通与持续工作责任

普通消息只承担沟通，不天然产生持续跟踪责任。委托是一个 Agent 角色要求唯一 Agent 目标角色完成工作并交付结果的独立责任；用户角色不发布、承接或验收委托。

委托发布者负责提供足够的起步上下文、吸收交付结果，并把影响整体推进的重要内容同步主持。独立评审通过新的评审委托发生；委托进入终态后永久冻结，但相关角色仍可通过普通消息继续讨论，新的工作责任需要另行发布委托。

### 6. 划清了角色语义判断与 Harness 确定性执行

理解意图、评价质量、判断风险、选择下一步和决定是否接受成果，属于 Agent 或真人角色。Harness 是确定性程序，只执行可以明确解析和校验的结构、身份、权限、路由、记录、审批、预算、并发、时间与故障策略。

多角色讨论不需要特殊的脑暴领域模型，软件开发也不成为固定的全局阶段模板。角色可以使用适合当前 thread 的讨论方式和推进语义，Harness 通过通用消息、委托与公共协作能力承载事实。

### 7. 确立了共同事实、知识和客户端边界

Harness 承载一个 thread 的共同协作事实；UI、命令行、Web、飞书或 Telegram 等只是能力可以不对等的访问入口。客户端不能拥有另一份并列的 thread 现实，也不能因为提供某个按钮或消息入口就创造权限。

完整记录是事实来源，进展快照、知识检索层和新角色入场上下文是可追溯但可能不完整的语义派生视图。Harness 保留最终交付、委托状态、必要消息和自己直接参与的外部操作，但不扩张为工作空间或外部世界的全量审计系统。

### 8. 明确了自治与用户信任的真实边界

角色权限、审批策略和资源预算共同形成实际自治范围。能够由 Harness 或可靠外部机制真正阻止的限制才是强制约束；只能通过提示词或角色说明要求 Agent 遵守的是弱约束；Harness 无法观察或控制的原生能力必须如实标明未覆盖。

产品不强求代理成熟 Agent 的全部工具，也不能把弱约束包装成强制保证。约束的保证来源、覆盖范围和变化必须透明，已经宣称的强制能力不可静默降级。

### 9. 确认了产品范围与主要边界

Harness 使用已经具备可靠程序化 Agent 级工作边界的成熟 Agent，不按 CLI、API 或桌面产品形态机械划分资格，也不负责把裸模型补造成通用 Agent。

核心保持领域无关，软件开发是最重要的初始使用与验证场景。跨 thread 项目管理、身份卡长期评价、自研通用 Agent、通用工具代理、外部世界全量审计和固定行业流程不属于当前 Harness 核心。

## Dreaming 完成不意味着什么

- 不意味着所有 Dreaming 记录都会实现或拥有相同优先级。
- 不意味着所有默认值、边缘行为、交互细节和异常策略都已经决定。
- 不意味着已经选定 `v0.0.1` 范围、技术架构、协议、存储、运行时或 UI。
- 不意味着产品认识不会再变化；新的实践证据可以在后续阶段推翻当前结论。
- 不意味着现在必须立即进入实现，也不意味着为了保持讨论状态而继续补充抽象需求。

## 留给后续阶段的问题类型

后续仍有大量工作，但它们不再阻塞 Dreaming 完成：

1. **需要选择的问题**：首个真实使用场景、首个验证闭环、版本范围和取舍。
2. **需要设计的问题**：角色与 Agent 的接入、公共能力边界、数据与状态、协议、权限表达、恢复策略和交互流程。
3. **需要实践回答的问题**：多 Agent 连续推进是否真的减少人工协调，主持在什么情况下表现可靠，哪些弱约束足够实用，哪些能力必须升级为强制约束。
4. **需要未来需求驱动的问题**：管理员细分治理、多真人协作、跨 thread 项目管理、身份卡评价工具和更多行业便利。

这些问题应在新的讨论阶段、产品设计、版本规划或实际试验中按需处理，而不是因为它们存在就继续延长 Dreaming。
