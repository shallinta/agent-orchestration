# 立项记录：多 Agent 编排 Harness

日期：2026-08-12

## 原始目标

构建一个以 CLI Agent 和远程可调用 Agent 为主要编排对象的 Harness/引擎，不包含桌面 App 类 Agent。它首先服务项目开发流程，但核心能力应适用于任何需要多 Agent 合作的场景。

理想状态下，用户只负责需求输入和重要节点决策。需求分析、设计、方案评审、开发、代码评审、测试、问题查询和修复等步骤，由主 Agent 根据不同参与者的能力、速度和成本进行拆分与分派。不同 Agent 可以交叉评审，也可以围绕复杂问题共同分析和讨论。

## 现实痛点

当前人工协作方式已经证明“强模型做方案和评审、快模型做受约束的执行”可以兼顾质量与速度，但使用者需要承担大量机械工作：

1. 让 Codex 形成方案并拆分任务。
2. 把任务和约束复制给 Claude Code 执行。
3. 再让 Codex 查看结果并进行评审。
4. 把评审问题转发给 Claude Code 修复。
5. 重复上述过程，直到满足质量要求。

项目要验证的是：这条协作链能否被自动化，同时保持上下文完整、过程可审计、失败可恢复、关键副作用可控。

## 初始概念

### Agent 身份资料卡

用户可以自行添加 Agent，并描述其名称、性格、回复风格、发言权重、擅长方向、特征属性和调用方法。调用方法分为 CLI 与远程接口两类；CLI 优先预设 Codex CLI 和 Claude Code CLI。

资料卡既包含运行所需配置，也包含提供给协作上下文的角色描述。早期版本是否需要所有字段，仍待验证。

### Thread

每个需求通常对应一个新的 thread 生命周期。用户首先指定主 Agent。主 Agent 负责整体推进、任务拆分和分派、外部调用建议、进展记录与资料沉淀；Harness 负责可靠执行和持久化。

用户可以随时加入 thread 对话，可视为一个特殊的高权重身份，但始终拥有高于普通 Agent 的决策权限。

### Harness 与主 Agent

初步倾向是把推理与执行控制分开：主 Agent 给出结构化意图和协作建议，Harness 掌握流程状态、Agent 调用、并发、权限、定时行为和外部副作用。两者的精确边界是首个版本的关键设计问题。

### 通信与 UI

Harness 核心不依赖前端。输入、输出和事件通过固定协议传递，使 Electrobun、Web、文件系统、飞书或 Telegram 等消费者能够按需接入。

前端计划参考 Electrobun，并考虑以 `shallinta/electrobun-app-starter` 为基础，但只会在核心闭环跑通后开始。OpenClaw 可作为通道与核心解耦方面的架构参考，而不是必须照搬的实现。

### 进展检查点

一个 thread 应有持续更新的进展视图。Harness 在固定时间或状态检查点汇总新事件，生成或更新该 thread 的进展文档。用户可通过协议、UI 或文件系统查看。

### 多 Agent 讨论

未来可能支持广播、轮流发言、两两对话、主持人协调等模式。具体模式和效果尚不明确，应通过小规模实验决定，而不是现在固化完整机制。

### 知识沉淀

项目希望把跨需求复用的公共经验和业务逻辑逐渐沉淀下来。需要区分 thread 内进展、已验证的项目知识和可能过时的临时判断，避免未经验证的 Agent 输出直接污染长期知识。

## 推进原则

- 从最核心的一小段能力开始，而不是一次完成平台设计。
- 每轮都经历想法讨论、设计对齐、文档记录、实现验证和反馈复盘。
- 版本从 `v0.0.1` 开始维护。
- 优先复用顶级厂商 Agent 的能力，不把“自研通用 Agent”作为项目目标。
- 未来可以研发专门适合编排场景的主 Agent，并以内置身份资料卡提供，但不是当前前提。

## 当前假设

- 第一个真实用户就是项目作者本人，因此可先做单机、单用户方案。
- 开发场景最适合成为第一个验证领域，因为现有人工工作流和痛点最明确。
- 追加式 thread 事件可能适合作为事实来源，进展文档则是事件派生视图。
- 第一个版本应优先验证 Agent 间上下文传递与评审返修闭环，而不是 UI 或通用工作流配置能力。

以上均为当前假设，尚未成为正式设计结论。

## 待澄清问题

1. `v0.0.1` 是否允许 Agent 直接修改真实工作区，还是先运行在只读或影子模式。
2. 主 Agent 是动态决定下一步，还是先由 Harness 的确定性状态机推进。
3. 首个闭环是否固定为“规划 → 执行 → 评审 → 返修 → 用户确认”。
4. 首版是否同时接入 Codex CLI 和 Claude Code CLI，还是用一个真实适配器加一个测试替身。
5. Thread 的最小恢复语义是什么：仅保留审计记录，还是允许进程中断后继续。
6. 哪些指标能证明项目确实减少了人工转发，同时没有牺牲质量。
